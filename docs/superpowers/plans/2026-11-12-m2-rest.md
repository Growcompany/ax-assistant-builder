# M-2 마무리 구현 계획: 골든셋 v1, 긴 조항 나누기, 다시 재기

**목표:** M-2 축소판에서 남은 약점 세 가지를 다룬다. (1) 44문항이라 리랭커 이득이 통계적으로 유의하지 않았다 → 골든셋을 약 150문항으로 늘린다. (2) 골든셋에 조항 번호·정식 상품명으로 묻는 질문이 없어 "hybrid가 dense보다 나은 경우"를 재지 못했다(ADR 0002가 잠정인 이유) → 그런 질문을 넣는다. (3) 긴 조항이 리랭커 입력 512토큰에서 잘려 답이 든 뒷부분을 못 봤다(bank-005·012·042·044) → 긴 조항을 항 단위로 나눈다.

**범위 결정(2026-11-12):** 저장소 주인이 남은 일을 고르는 것과 골든셋 주인 확인 판단을 에이전트에게 위임했다("너가 알아서 잘 골라서 나머지도 해봐"). 그래서 이 계획의 골든셋에는 **사람 검수가 없다**. 문서에는 "주인이 판단을 에이전트에게 위임했다"고 적고 "사람 검수"라고 쓰지 않는다.

**미루는 것:** LLM-judge와 Claude 모델 비교(유료 API 호출이 필요하고 승인을 받지 않았다), 다른 로컬 LLM 비교(수 GB를 받아야 하고 8GB GPU가 임베딩·리랭커·Ollama로 이미 찬다).

**Spec:** `docs/superpowers/specs/2026-11-09-company-assistant-builder-design.md` 5장(평가). 앞선 계획 `2026-11-11-m2-slim.md`, 실험 기록 `docs/experiments/2026-11-11-{golden-audit,refusal-detection,reranker}.md`, ADR 0002·0006.

## Global Constraints

- 단위 테스트는 네트워크·GPU·모델 없이 통과한다. 실제 모델은 `@pytest.mark.slow`와 수동 실험으로만.
- 기존 실험 기록의 숫자는 고치지 않는다. 새 측정은 새 실험 기록에 쓴다.
- 변수 하나씩: 골든셋 변경(v0 → v1), 분할 변경(지금 → 항 단위), 리랭커 유무의 효과를 따로 보고한다.
- 평균만이 아니라 문항 단위로 뒤집힌 문항 번호를 적고, 비교에는 정확 맥니마 검정 p값을 그대로 적는다. 유의하지 않으면 유의하지 않다고 쓴다.
- 기존 API 경로·필드·상태 코드와 M-1 계획의 Interfaces를 깨지 않는다. 필드 추가만 한다.
- 원문(법령·약관)은 커밋하지 않는다. 골든셋에는 질문·정답·근거 위치만 둔다.

## Review Focus

1. 새 문항의 정답이 원문과 다르거나, 정답이 다른 문서에도 있어 채점이 박해지는 문항이 섞이지 않는다(독립 대조로 확인).
2. 범위 밖 문항은 13개 문서 어디에도 답이 없다(코퍼스 검색으로 확인).
3. 항 단위로 나눈 청크도 조항 라벨이 그대로라 기존 골든셋 근거가 같은 규칙으로 맞는다. 나눈 조각에는 조항 머리("제11조(대리인 거래)")가 붙어 맥락을 잃지 않는다.
4. 분할 방식이 바뀌면 기존 색인이 오래된 것으로 표시된다(조용히 섞이지 않는다).
5. 부칙의 긴 "다른 법률의 개정" 청크를 나누어 잡음 청크가 크게 늘지 않는다(청크 수 변화를 보고한다).

## Task 25: 긴 조항 나누기

**Files:** `src/axbuilder/ingest/chunking.py`, `src/axbuilder/settings.py`, `src/axbuilder/api/app.py`(색인 정보와 stale 판정), `src/axbuilder/eval/run.py`, `tests/ingest/`, `tests/api/`, `.env.example`

**Interfaces (Produces)**

```
chunk_document(doc, max_chars: int | None = None) -> list[Chunk]
chunk_by_article(doc, max_chars: int | None = None) -> list[Chunk]
  max_chars 가 None 이면 지금과 바이트까지 같은 결과.
  조항 청크 본문이 max_chars 를 넘으면 항(①②…) 경계에서 나누어 max_chars 안으로 묶는다.
  한 항이 넘으면 호("1." 등 줄 맨 앞 번호) 경계, 그래도 넘으면 글자 수로 자른다.
  둘째 조각부터 본문 앞에 조항 머리 줄(예: "제11조(대리인 거래)")을 붙인다. article 라벨은 그대로.
Settings.max_chunk_chars (AXB_MAX_CHUNK_CHARS, 기본 None = 지금과 같음)
index.json 에 "chunking": {"max_chars": N | null} 을 남기고, 지금 설정과 다르면 index.state = "stale".
  예전 index.json(필드 없음)은 max_chars = null 로 읽는다(지금 기본과 같으므로 stale 아님).
eval.run --max-chunk-chars N  (보고서 config 에 chunking 기록, 파일 이름에 -mN)
```

- `max_chars` 값은 측정으로 정한다: 두 리랭커 토크나이저(KURE-nano, bge-v2-m3)로 질문 + 조각의 토큰 수를 재서, 조각의 95%가 512토큰 안에 드는 글자 수를 고른다(토크나이저만 CPU로 불러 잰다).
- 청크 수 변화(문서별, 본문/부칙)를 보고한다.
- 기본값은 실험 뒤에 정한다(ADR 0007). 이 Task에서는 기본을 바꾸지 않는다.

## 변경 기록

계획과 다르게 된 것이다(2026-11-12, Task 24~26). 위 본문은 고치지 않았다.

1. **새 문항의 유형 수 (Task 24).** Task 24 표의 유형 수(lookup 44, table 12, multi_doc 14, out_of_scope 14)를 더하면 84인데, 같은 절은 새 문항을 100개(bank-051 ~ bank-150)로 적었다. 합계 84는 계획의 실수로 보고 100개를 지켰다. 표의 비율대로 늘려 lookup 52, table 14, multi_doc 17, out_of_scope 17이다. 태그 최소 수는 모두 넘었다(`article_ref` 18, `product_name` 12, `negative_answer` 26). → [제작 기록](../../eval/golden-v1-build.md)의 "계획과 다른 점"
2. **`Evidence.anchor`와 답 문구 기준 채점을 더했다 (Task 24).** 계획에 없던 일이다. 채점(`matches`)은 근거의 조항 라벨만 봐서, Task 25로 나눈 조각은 답이 없어도 같은 라벨이라 맞고, 상품설명서(문서 단위 근거)는 그 문서 6청크 중 아무거나 맞았다. 그래서 근거마다 답이 든 원문 문구(10~40자)를 달고 `matches_strict`·`recall_at_k_strict`·`reciprocal_rank_strict`와 보고서의 `Recall@k(답 문구)`·`MRR(답 문구)` 열을 더했다. 필드·함수 추가만이고, 기존 `matches`·`recall_at_k`·`reciprocal_rank`(M-1 Interfaces)와 답 문구가 없는 골든셋의 보고서 모양은 그대로다. 이 일 때문에 Task 25 브랜치를 Task 24 브랜치에 먼저 합쳤다. Task 26의 기록은 답 문구 기준을 본문으로 쓰고 라벨 기준을 함께 적는다. → [제작 기록](../../eval/golden-v1-build.md)의 "답 문구"
3. **긴 조항을 나누는 단계와 범위 (Task 25).** Interfaces는 항 → 호 → 글자 수였고, 구현은 항 → 호 → 목 → 줄 → 글자 수다. 부칙, 첫 조항 앞 머리말, 조항이 없는 문서의 고정 길이 청크는 나누지 않는다(Review Focus 5의 잡음 청크를 늘리지 않으려고. 800자보다 긴 부칙 12개는 리랭커 입력에서 계속 잘린다). `AXB_MAX_CHUNK_CHARS`의 범위(200~20,000)와 `axb serve`의 `청크 분할: …` 시작 줄을 더했다. → [Task 25 학습 노트](../../learning/task-25-article-split.md)
4. **독립 대조 뒤의 결정 (Task 24).** 대조자가 2문항을 고쳤다(bank-118에 `negative_answer`, bank-131 정답 첫머리). 애매함 10문항은 위임받은 에이전트가 정했다. 유형이 갈린 5문항(bank-070, 071, 075, 078, 079)은 lookup 그대로, bank-094는 질문의 전제를 고쳤다("잔액 0원인 … 입출금 한 번 없이". 정답·근거·답 문구는 그대로). 부분 대체 근거 3문항(083, 088, 117)과 태그가 갈린 127은 그대로다. → [제작 기록](../../eval/golden-v1-build.md)의 "대조 뒤 결정"
5. **답변 평가의 세 번째 조건 (Task 26).** 계획은 "검색에서 가장 좋은 조합"이었는데, 실제로 쓴 hybrid + KURE + 800자는 검색 표의 최고값이 아니다. 맞힌 문항은 dense + KURE + 800자와 같고 답 문구 MRR은 dense 쪽이 0.012 높다. 기본 검색기 hybrid를 유지한 채 고른 조합이고, 권한 확인(역할 `상담원`)도 이 조합으로 했다. → [골든셋 v1 기록](../../experiments/2026-11-12-golden-v1.md)
6. **프롬프트 실험을 더했고 채택하지 않았다 (Task 26).** 계획에 없던 실험이다. 부정문 정답의 과잉 거절이 많아(여섯 실행 모두 Fisher p ≤ 0.016) hybrid + KURE에서 시스템 프롬프트에 한 줄을 더해 두 번 돌렸다. 부정문 과잉 거절은 판정기 기준 5·7 / 25에서 2·2 / 25로 줄었지만, 거절이 정해진 문구를 잃어(21·23 → 11·10) 판정기가 놓친 거절이 인용을 단 채 나갔고, 과잉 거절이 풀린 18건 중 3건이 틀린 답이었으며, 문항 단위 순효과가 없었다(11 / 11, 12 / 10). 그 줄은 저장소에 넣지 않았다. 답변 실행은 계획의 6회와 권한 확인 1회에 이 2회를 더해 9회다. → [답변 기록](../../experiments/2026-11-12-answers-v1.md)
7. **결과 문서를 하나 더 냈다 (Task 26).** 계획은 실험 기록 두 개(골든셋 v1, 분할)였고, 답변 평가는 [답변 기록](../../experiments/2026-11-12-answers-v1.md)으로 따로 냈다.
