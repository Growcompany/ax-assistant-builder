# M-2 축소판 구현 계획: 골든셋 대조, 거절 판정, 리랭커 실험

**목표:** v0.2.0의 평가에서 가장 약한 세 곳을 고친다. (1) 골든셋이 검수 전이다 → 원문 전수 대조. (2) 거절 정확도가 판정 규칙 때문에 틀리게 나온다 → 바꿔 말한 거절을 잡는다. (3) "dense가 hybrid보다 좋았다"에서 멈췄다 → 리랭커를 붙여 비교한다.

**범위 결정(2026-11-11, 저장소 주인):** 설계 문서의 M-2 전체(골든셋 150~200문항, LLM-judge, 모델 비교)가 아니라 이 세 가지만 한다. 나머지는 미룬다.

**Spec:** `docs/superpowers/specs/2026-11-09-company-assistant-builder-design.md` 5장(평가), 7장(스택: 리랭커 후보). 조사 근거 `docs/research/11-korean-rag-stack-2026.md`.

## Global Constraints

- 단위 테스트는 네트워크, GPU, 모델 다운로드 없이 통과한다. 실제 모델은 `@pytest.mark.slow`와 수동 실험으로만.
- 기준선 기록 `docs/experiments/2026-11-10-baseline.md`의 숫자는 고치지 않는다. 새 측정은 새 실험 기록에 쓴다.
- 한 번에 변수 하나만 바꾼다. 골든셋 수정, 거절 판정 변경, 리랭커 추가의 효과를 각각 따로 보고한다.
- 44문항(답변 지표는 50문항)에서 한두 문항 차이는 잡음이다. 평균만이 아니라 "어느 문항이 뒤집혔는지"를 문항 번호로 적는다.
- 기존 API의 경로, 필드, 상태 코드와 M-1 계획의 Interfaces를 깨지 않는다. 필드 추가만 한다.
- 리랭커 모델은 `nlpai-lab/KURE-Reranker-nano`(약 0.6GB)를 기본 후보로, `BAAI/bge-reranker-v2-m3`(약 2.3GB)를 비교 대상으로 쓴다(설계 문서 7장). 받기 전에 `df -h /c`를 확인한다. 설치 승인은 2026-11-11에 받았다.
- 기본 검색기를 바꾸는 결정은 실험 결과를 본 뒤 ADR로 남긴다. 실험 Task에서 기본값을 바꾸지 않는다.

## Review Focus

1. 부분 답변("A는 자료에 없지만 B는 3일입니다")이 거절로 잘못 판정되어 정상 답이 사라지지 않는다.
2. 근거가 있는 질문의 정답에 "…할 수 없습니다"가 들어가는 경우(예: "중도해지할 수 없습니다 [1]")를 거절로 보지 않는다.
3. 리랭커가 권한 필터를 우회하지 않는다. 리랭커에 들어가는 후보는 이미 역할로 걸러진 청크뿐이다.
4. 긴 청크(최대 11,452자)가 리랭커 입력 길이에서 잘릴 때 조용히 잘리지 않고 몇 개가 잘렸는지 기록된다.
5. 리랭커 모델이 없거나 불러오지 못할 때 읽을 수 있는 오류가 나고, 리랭커를 쓰지 않는 기본 경로는 영향이 없다.

## Task 20: 바꿔 말한 거절 판정

**Files:** `src/axbuilder/generation/refusal.py`(새), `src/axbuilder/generation/answer.py`, `src/axbuilder/eval/metrics.py`, `src/axbuilder/eval/run.py`, `tests/generation/test_refusal.py`(새), `tests/fixtures/refusal_outputs.jsonl`(새), `scripts/rescore_refusals.py`(새)

**배경:** `answer()`는 응답이 정해진 문구(`제공된 자료로는 확인할 수 없습니다.`)로 시작할 때만 `refused=True`다. 기준선에서 범위 밖 6문항 중 4개는 모델이 문구를 바꿔 거절했고 지표는 0.333이었다. 사람이 읽으면 6개 모두 답을 피했다.

**Interfaces (Produces)**

```
refusal.py
  class RefusalKind(StrEnum): EXACT = "exact"; PARAPHRASE = "paraphrase"; NONE = "none"
  def classify_refusal(text: str) -> RefusalKind
    EXACT      = 지금의 _is_refusal과 같은 판정(정규화 후 글자·숫자가 없거나 정해진 문구로 시작)
    PARAPHRASE = 답 전체가 "자료에 없다/확인할 수 없다"는 말뿐이고, 질문에 대한 긍정 진술이 없다
    NONE       = 그 밖(부분 답변 포함)

Answer 에 필드 추가: refusal_kind: RefusalKind (기본 NONE)
answer(): EXACT 와 PARAPHRASE 모두 refused=True, text=REFUSAL_TEXT, citations=[] 로 정규화한다.
          모델이 쓴 원래 문장은 Answer.llm.text 에 그대로 남는다.

metrics.py
  def refusal_correct(refused: bool, qtype: str) -> bool        # 그대로
평가 보고서 항목에 추가: refusal_kind, raw_answer(정규화 전 모델 출력)
요약에 추가: refusal_accuracy_strict (EXACT 만 거절로 셈 = 기존 규칙)
```

**판정 설계의 원칙**
- **정밀도 우선.** 정상 답을 거절로 바꾸면 사용자는 답을 잃는다. 애매하면 NONE이다.
- 규칙 기반으로 만든다(LLM을 한 번 더 부르지 않는다). 문장 단위로 나눠, 모든 문장이 "없음·확인 불가" 서술이거나 그 이유 설명(자료에 무엇이 있는지 나열)일 때만 PARAPHRASE다. 질문에 답하는 긍정 진술(수치, 절차, 조건)이 하나라도 있으면 NONE이다.
- 규칙은 실제 출력으로 검증한다. `reports/bank/`의 LLM 실행 보고서 3개(각 50문항, 항목의 `answer`)에서 모델 출력 150개를 모아 `tests/fixtures/refusal_outputs.jsonl`로 만들고(원문 문서가 아니라 모델 출력과 질문 id뿐이라 커밋 가능한지 확인: 법령 원문을 길게 인용한 출력이 있으면 그 항목은 요약으로 대체), 각 출력에 정답 라벨(`refusal` / `answer` / `partial`)을 단다. 라벨 기준과 애매한 항목은 `docs/eval/refusal-labels.md`에 적고, 애매한 항목은 Task 19의 주인 확인 목록에 덧붙인다.
- 보고할 것: 이 150개에서 판정기의 정밀도·재현율(거절 클래스), 혼동 행렬, 틀린 항목 전부.

**테스트(명세)**
- 고정 문구와 그 변형(기존 `_is_refusal` 테스트 전부)이 EXACT.
- 기준선의 바꿔 말한 거절 4건(bank-045, 046, 047, 050의 실제 출력)이 PARAPHRASE.
- Review Focus 1, 2의 문장들이 NONE: 부분 답변, "…할 수 없습니다"가 정답인 경우, 거절 문구가 맨 뒤에 붙은 답, 인용만 있는 답.
- fixture 150개에서 정밀도 0.98 이상(거절로 판정한 것 중 라벨이 `refusal`인 비율). 재현율은 단언하지 않고 보고한다.
- `answer()`가 PARAPHRASE를 정규화하고 `refusal_kind`를 채운다. `/ask`와 `/v1`의 응답 모양은 그대로다(필드 추가 없음. `refused`만 달라진다).
- `scripts/rescore_refusals.py <보고서.json>`: 저장된 보고서의 `answer`로 새 판정을 다시 계산해 전후 표를 낸다(모델 재실행 없음).

**실험 기록:** `docs/experiments/2026-11-11-refusal-detection.md` — 같은 출력 150개에 대한 전(strict) → 후, 범위 밖 행과 과잉 거절의 변화, 틀린 판정, 한계(규칙은 이 모델·이 문구에 맞춰졌다).

## Task 21: 리랭커 비교 실험

**Files:** `src/axbuilder/retrieval/rerank.py`(새), `src/axbuilder/eval/run.py`, `tests/retrieval/test_rerank.py`(새), `pyproject.toml`(필요하면), `docs/experiments/2026-11-11-reranker.md`(새), `docs/adr/0006-reranker.md`(새)

**Interfaces (Produces)**

```
rerank.py
  class Reranker(Protocol):
      name: str
      def score(self, question: str, passages: list[str]) -> list[float]     # 길이 = len(passages), 클수록 관련
  class CrossEncoderReranker:                                                 # sentence-transformers CrossEncoder, 처음 쓸 때 불러온다
      def __init__(self, model_name: str, max_length: int = 512, batch_size: int = 16) -> None
      truncated: int                                                          # 잘린 입력 수(누적)
  class RerankRetriever:                                                      # Retriever 프로토콜을 만족한다
      def __init__(self, base: Retriever, reranker: Reranker, candidates: int = 30) -> None
      def search(self, question, k, access_levels=None) -> list[ScoredChunk]
        base.search(question, candidates, access_levels) → reranker.score → 점수 내림차순(동점은 base 순위) → 앞 k개

eval.run
  --reranker {none,kure-nano,bge-v2-m3}   (기본 none)
  --candidates N                           (기본 30, 리랭커에 넘기는 후보 수)
  보고서 config 에 reranker, candidates, rerank_truncated 를 남긴다.
```

리랭커에 넣는 글은 임베딩과 같은 청크 본문이다. 제목·조항을 앞에 붙일지는 실험 조건으로 다루지 않는다(변수 하나만).

**테스트(명세)** — 가짜 `Reranker`로: 순서가 점수대로 바뀐다, 동점은 base 순위를 유지한다, `k > candidates`·빈 후보·후보 1개, `access_levels`가 base에 그대로 전달되고 리랭커는 걸러진 청크만 받는다, `candidates < k`면 base에서 k개를 받는다, 점수 개수가 안 맞으면 오류. `CrossEncoderReranker`는 모델 없이 생성만 되고 첫 호출 때 불러온다(불러오기 실패 시 읽을 수 있는 오류). 실제 모델 테스트는 `slow`.

**실험 설계** (GPU, k = 5와 10, 역할 `준법감시`, Task 19에서 고친 골든셋)

| 축 | 값 |
|---|---|
| base | bm25, dense, hybrid |
| 리랭커 | 없음, KURE-Reranker-nano, bge-reranker-v2-m3 |
| 후보 수 | 30 (기본), 50 (리랭커가 있을 때만) |

보고할 것: 전체·조항 단위·문서 단위 Recall@5·MRR 표, 질문당 지연(리랭커 포함), VRAM 최대, 잘린 입력 수, 그리고 **base 대비 문항 단위 변화**(새로 맞힌 문항, 새로 놓친 문항의 번호와 이유 한 줄). 기준선의 실패 사례(bank-029: BM25 후보에 없어 hybrid가 놓침, bank-006·010·017)가 어떻게 됐는지 따로 적는다.

**결정(ADR 0006):** 결과가 어느 쪽이든 쓴다. 리랭커를 기본으로 켤지, 선택 기능으로 둘지, 넣지 않을지와 근거(정확도 이득 대 지연·VRAM·설치 크기). 44문항이라는 표본의 한계를 결론의 강도에 반영한다.
