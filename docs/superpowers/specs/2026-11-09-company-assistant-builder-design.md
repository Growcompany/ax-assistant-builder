## 1. 의도와 이유

**한 줄 요약**
> 어떤 회사든 자료를 올리면, 그 회사 전용 어시스턴트 에이전트를 자동으로 구성하고 평가 리포트까지 만들어 주는 플랫폼. 폐쇄망(로컬 모델)에서도 동작한다.

**무엇을 위한 프로젝트인가**
학사 학위로 **AI/AX 엔지니어 직무**(대기업 IT서비스·은행/금융·빅테크 응용직·중견 SI/MSP/AX/FDE)에 지원하기 위한 **메인 포트폴리오 1개**.

**왜 이 형태인가** — 조사(01~09)에서 확인된 사실:
- 학사가 들어갈 수 있는 직무는 "모델 연구"가 아니라 **"AI를 고객사 업무에 붙이는" AX·응용 직무**다 (석·박사 요구: 연구직 28%, AX 3%).
- AX 엔지니어·FDE가 실제로 하는 일: **고객사 자료 받기 → 과제 정의 → 구현 → 평가 → (온프레미스) 배포**. 이 플랫폼이 그 과정 자체를 제품으로 만든다.
- AI 솔루션사가 실제 파는 제품과 같은 형태 (사내 문서 RAG 플랫폼, 규정·약관 Q&A, 업무 에이전트).
- 금융·공공 고객의 추가 요구: **폐쇄망, 개인정보 마스킹, 문서 권한(ACL), 근거 인용·환각 통제, 구버전 문서 처리**.
- 모든 직군 공통 요구: RAG 직접 설계, **정량 평가**, 에이전트, 배포·운영, 고객 문제 정의.

**성공 기준 (사용자 관점)**
1. 서류 검토자가 README를 **8분 안에** 보고 "고객사 자료로 어시스턴트를 만들고, 수치로 검증하고, 폐쇄망까지 고려한 사람"이라고 판단한다.
2. 사용자가 **모든 결정과 코드를 설명할 수 있다** — 구현은 Claude 에이전트 팀이 하되, 작업마다 학습 노트와 결정 기록(ADR)을 남겨 면접 꼬리질문에 답할 수 있게 한다.
3. **2027 상반기 공채(보통 3~4월) 전에** 완성. 12월~1월 공고(메가존클라우드 신입공채, NIA 등)에는 **중간 버전**으로 지원 가능.

## 2. 역할 분담 (2026-11-09 변경: "너가 진행해봐" — Claude 에이전트 팀이 구현)

처음에는 "전부 내가 + Claude 리뷰"로 정했으나, 같은 날 사용자가 구현 전체를 Claude에게 맡겼다. 대신 **사용자가 설명할 수 있어야 한다**는 목표는 유지한다.

| | 사용자 (책임자·검수자) | Claude 에이전트 팀 |
|---|---|---|
| 코드 (`src/`, `tests/`, `scripts/`, CI) | 학습 노트로 이해, 궁금한 점 질문 | **구현** (작업별 브랜치·PR, TDD) |
| 리뷰 | PR 기록 확인 | 구현 에이전트와 **별도의 리뷰 에이전트**가 PR마다 리뷰, 지적·대응을 PR에 기록 |
| 학습 | `docs/learning/` 노트 읽기 | 작업마다 **학습 노트**: 핵심 개념, 왜 이렇게 했는지, 면접 예상 질문과 답 |
| 결정 | 방향·우선순위 결정 | 선택지와 근거 제시, ADR 작성 |
| 평가 데이터 | **골든셋 표본 검수, 사람 채점** (LLM-judge 보정에 필요) | 초안 생성, 검수용 표 준비 |
| 외부 설치·키 | Ollama 설치 승인, API 키 입력 (직접) | 설치 명령 안내 |

- 작업 흐름: 계획 → 구현 에이전트(브랜치) → PR → 리뷰 에이전트 → 수정 → CI 통과 → 머지. **PR·리뷰 기록 자체가 포트폴리오**다(2026 공채의 AI 활용 역량 — AI 결과물 검증 능력).
- 전문가 에이전트 정의는 `.claude/agents/`, 저장소 공통 규칙은 `CLAUDE.md`.
- README에 "AI 코딩 에이전트로 구현하고, 사람이 방향·검수·평가를 맡았다"는 사실과 검증 방식을 정직하게 적는다.

## 3. 시나리오 (고객 PoC 형식)

### 3.1 플랫폼 사용 흐름
1. **회사(워크스페이스) 만들기** — 회사 이름, 산업, 역할(예: 상담원/준법감시/관리자)
2. **자료 올리기** — PDF, Word, HWPX, TXT/Markdown, 엑셀·CSV
3. **자동 구성** (사람이 확인·수정)
   - 문서 종류 판별: 조항형 규정 / 매뉴얼 / FAQ / 표 중심 문서
   - 종류별 분할 방식 선택 (조항 단위, 제목 단위, 질문-답변 단위 등)
   - 회사 전문용어 사전 추출 → 형태소 분석 사용자 사전
   - 답할 범위·거절할 범위, 사람에게 넘길 질문 유형 초안
   - 문서별 접근등급 제안
   - 엑셀·CSV는 조회 도구로 등록
4. **자동 평가** — 자료에서 평가 질문 초안 생성 → 사용자 검수 → 정답률·인용 정확도·실패 유형 **온보딩 리포트**
5. **회사 전용 에이전트 사용** — 채팅 UI·API, 역할별 권한, 인용, 거절, 사람에게 넘기기

### 3.2 데모 회사 *(작성자 판단, 데이터 확보 상황에 따라 조정)*

| 워크스페이스 | 자료 | 평가 데이터 | 역할 |
|---|---|---|---|
| **가상 은행 (대표)** | 금융 법령·감독규정(국가법령정보 API), 은행연합회 표준약관, 시중은행 상품설명서(다운로드 스크립트), 직접 쓴 **가상 내부 지침** 5~10개, 금감원 상품 비교 데이터(오픈API) | 자체 골든셋 150~200문항 (사용자 검수) | 금융 보안 기능 전부 시연 |
| 공공기관 | `allganize/RAG-Evaluation-Dataset-KO` 공공 도메인 문서 | 데이터셋에 포함된 사람 작성 질문 | 이식성 증명 |
| 3번째 (커머스 또는 법률) | 같은 데이터셋의 다른 도메인 | 데이터셋 포함 | 이식성 증명 |

> allganize 데이터셋을 쓰면 **사람이 만든 평가셋**이 이미 있으므로, "자동 생성 평가셋이 사람 평가셋과 얼마나 같은 결론을 내는가"를 측정할 수 있다 (차별화 실험).

### 3.3 대표 데모 시나리오 (가상 은행)
- 가상 고객: "OO은행" 고객상담센터·준법감시팀 (가상임을 명시)
- `상담원`: 공개 문서만 / `준법감시`: 공개 문서 + 가상 내부 지침
- 상담원이 약관·규정 질문 → 조항·페이지 인용 답변, 근거 없으면 거절, 판단이 필요한 질문은 담당자에게 넘김

## 4. 범위

### 4.1 반드시 (Must)

**M1. 워크스페이스와 문서 수집·파싱**
- 모든 데이터(문서, 색인, 설정, 평가셋, 로그)는 **워크스페이스 단위로 분리** — 처음부터 이 구조로 만든다
- 포맷: PDF(표 포함), DOCX, TXT/MD, CSV/XLSX. HWPX는 Should
- 문서 메타데이터: 문서유형, 발행기관, **시행일~폐지일**, **접근등급**, 원본 출처
- 원본 파일·색인은 저장소에 커밋하지 않고 **다운로드·재현 스크립트**로 관리

**M2. 자동 구성 (온보딩)**
- 문서 종류 판별 → 분할 방식 선택 (규칙 기반 + LLM 판별 비교)
- 용어 사전 추출 → Kiwi 사용자 사전
- 범위·거절·HITL 규칙 초안과 시스템 프롬프트 초안 생성
- 결과는 워크스페이스 설정 파일(YAML 등)로 저장 → 사람이 수정 가능, 버전 관리

**M3. 검색**
- Kiwi 형태소 BM25 + 한국어 dense 임베딩 → **RRF 하이브리드** → 리랭커
- **접근등급(ACL) 사전 필터** — 권한 없는 문서는 검색 단계에서 제외
- 버전 정책: 기준일은 **오늘**, **현행본만 답변 근거**, 구버전은 "개정 전 조문" 참고로만 표시

**M4. 답변 생성**
- 문장별 **조항·페이지 인용**, 근거 부족 시 **거절**
- 현행본에 근거가 없고 구버전에만 있으면 "현행 규정에서는 확인되지 않음" + 개정 전 조문 참고

**M5. 평가 체계 (핵심 차별점)**
- **자동 평가셋 생성**: 문서에서 질문·정답·근거 위치 초안 생성 → 사용자 검수
- 가상 은행 골든셋 150~200문항. 질문 유형과 정답 행동:
  - 단순 조회 / 표·수치 / 다중 문서 → 정확한 답 + 올바른 인용
  - 범위 밖 → 거절
  - **판단 필요 → 사람에게 넘김**
  - 권한 밖 (상담원이 내부 지침 질문) → 내부 지침 미인용
  - 구버전 함정 → 현행본 근거, 구버전 미인용
- 검색 지표: Recall@k, MRR, nDCG / 답변 지표: 정답률, faithfulness, **인용 정확도**, **거절·HITL 정확도**
- **LLM-judge 신뢰도**: 30~50문항은 사용자가 직접 채점 → judge 일치율 보고. 비교 실험 내내 **judge 모델은 하나로 고정**
- **Ablation**: BM25 / dense(임베딩 2~3종) / 하이브리드 / +리랭커 / 분할 방식 2~3종
- **모델 종류별 비교** (사용자 요청 "종류별로"): Claude Opus 5.5 · Sonnet 5.5 · Haiku 5.5 · 로컬 7~8B 모델 → 정답률·인용·지연·질의당 비용 표 → 이를 근거로 **라우팅 정책** 제안 (예: 단순 질문은 저가·로컬, 어려운 질문은 상위 모델)
- **이식성 표**: 워크스페이스 3곳의 정확도 + 자동 평가셋 vs 사람 평가셋 결론 비교
- **CI 회귀 테스트**: 저작권 문제 없는 소규모 고정 세트(법령 + 가상 지침)로 검색 지표만 측정, API 호출 없음

**M6. 에이전트 (LangGraph)**
- 질의 분류 → {문서 검색 RAG | 데이터 조회 도구(CSV/엑셀, 금융 상품 비교) | 판단 필요 → 사람에게 넘김 | 범위 밖 → 거절}
- **근거 검증 노드** → 실패 시 질의 재작성 후 재검색(최대 2회) → 그래도 안 되면 사람에게 넘김
- 분류 기준:
  - **범위 밖**: 워크스페이스 주제와 무관 (예: 날씨, 투자 종목 추천)
  - **판단 필요**: 주제 안이지만 개별 사안의 판단·결정 요구 (예: "이 민원은 보상해야 하나요?") → 관련 조항은 보여주되 결론은 담당자에게
  - 분류 단계 HITL과 검증 실패 HITL은 응답에 사유를 구분해 표시
- 분류·범위 규칙은 **워크스페이스 설정**에서 읽음 (회사마다 다름)

**M7. 보안·거버넌스**
- **한국어 PII 마스킹**: 주민등록번호, 계좌번호, 카드번호, 전화번호, 이메일 — 입력·로그 양쪽
- **감사 로그**: 워크스페이스·역할·질의·검색 문서·답변·판정 (마스킹 후 JSONL)
- **프롬프트 인젝션 방어** — 업로드 문서 안에 숨은 지시문 포함 (간접 인젝션)
- 인젝션·PII 유출·권한 우회 **테스트셋**과 통과율

**M8. 폐쇄망 모드**
- 설정 하나로 `cloud`(Claude API) ↔ `local`(Ollama 로컬 LLM + 로컬 임베딩 + 로컬 벡터DB) 전환
- local 모드는 **외부 네트워크 호출 0건**을 테스트로 보장
- 자동 구성·자동 평가셋 생성도 local 모드에서 동작해야 함 (품질 차이는 표로 공개)

**M9. 서빙·운영**
- FastAPI: 워크스페이스 CRUD, 문서 업로드·색인, 질의, 평가 실행, 헬스체크
- **Docker Compose 원커맨드** — 대상 환경은 **사용자 PC (GPU, Windows + WSL2)**
- 요청별 트레이스: 단계별 지연, 토큰, 비용 추정
- 부하 테스트로 p50/p95 지연

**M10. 데모와 문서**
- Streamlit UI: 워크스페이스 만들기 → 업로드 → 자동 구성 확인 → 평가 리포트 → 채팅(역할 전환, 인용, 거절·HITL 표시)
- README: 결과 중심 한 줄 → 데모 GIF → 아키텍처 → 핵심 결정 5개 → 결과 표 → 원커맨드 실행 → 한계
- **고객 PoC 리포트 예시** (가상 은행 온보딩 리포트)
- **결정 기록(ADR)**, 실험 노트
- **Claude 리뷰 반영 기록** (PR 설명에 리뷰 지적과 대응 정리 — 2026 공채의 AI 활용 역량 평가 대비)

### 4.2 여유 있으면 (Should)
- S1. **MCP 서버**로 워크스페이스 검색 도구 노출 (롯데이노베이트·현대오토에버·IBM 공고 키워드)
- S2. HWPX 파서 (공공기관 문서)
- S3. 공개 데모 배포 (cloud 모드, 법령 + 가상 지침 + allganize 데이터만)
- S4. CPU 경량 실행 프로필 (GPU·API 키 없이 검토자가 실행)
- S5. 질문 속 날짜 기준 조회 ("2023년 기준 규정은?")
- S6. 제조사 워크스페이스 (공개 매뉴얼 확보 시)

### 4.3 하지 않는 것 (Non-goals)
- 모델 사전학습·파인튜닝
- 실제 고객 데이터·개인정보
- 진짜 멀티테넌트 SaaS (회원가입, 결제, 테넌트별 인증) — 워크스페이스는 **데이터·설정 분리**까지만
- 대규모 운영(Kubernetes), 정교한 프론트엔드

### 4.4 이러면 실패 (Anti-goals)
- 수치 없는 "아무 문서나 넣는 챗봇"으로 끝나는 것 — 범용성 때문에 깊이를 잃는 것
- 사용자가 설명하지 못하는 코드
- 저작권 있는 원문·색인이나 개인정보를 GitHub에 올리는 것
- 유료 API 없이는 동작하지 않는 구조

## 6. 모델과 비용 (사용자 답변 "종류별로" 반영)

| 모델 | 단가 (입력/출력, 100만 토큰당) | 질의당 | 200문항 1회 |

| Opus 5.5 | $4 / $20 | 약 $0.06 | 약 $12 |

| Haiku 5.5 | $0.10 / $0.50 | 약 $0.002 | 약 $0.3 |
| 로컬 | 0 | 0 (대신 느림) | 0 |

- 운영 방식 *(작성자 판단)*: 일상 개발·반복 실험은 **로컬 + 100문항 부분집합**, 4종 전체 비교는 **마일스톤마다 1회** (총 3~4회) → 전체 기간 API 비용 약 **$150~250** 예상
- 비용은 실제 사용량 로그로 매주 갱신하고, 예상을 크게 넘으면 사용자와 다시 정함

## 11. 작성자가 정한 것 (사용자 확인 권장)
1. 데모 워크스페이스: 가상 은행(대표) + allganize 데이터셋 기반 2곳. 제조사는 공개 자료 확보 시
2. 구버전은 법령·감독규정 연혁본만, 답변 근거는 현행본만
3. 분류 4갈래(검색 / 데이터 조회 / 판단 필요 → 사람 / 범위 밖 → 거절)와 각각의 기준
4. Docker Compose 대상은 사용자 PC, 검토자용 경량 실행은 Should
5. "종류별로" = 모델 4종 비교 실험을 평가에 포함 (해석 확인 필요), 전체 API 비용 약 $150~250 예상
6. 기술 스택 (7장)
7. 진짜 멀티테넌트(회원가입·인증)는 하지 않고 워크스페이스는 데이터·설정 분리까지만
