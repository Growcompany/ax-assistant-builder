## 핵심 개념

**8분 안에 읽히는 README = 역피라미드**
서류 검토자는 위에서부터 읽다가 아무 데서나 멈춥니다. 그래서 가장 중요한 것을 맨 위에 둡니다.
1. **결과 한 줄**: 무엇을 만들었고 결과가 얼마였는지 숫자로 씁니다. "강력한", "고성능" 같은 형용사는 쓰지 않습니다.
2. **데모**: 실제로 동작한다는 증거입니다. GIF가 없어서 API로 한 번 실행한 출력을 그대로 실었습니다.
3. **아키텍처**: 그림 하나와 표 하나로 "어디에 무엇이 있는지"를 보여 줍니다.
4. **결정과 근거**: 왜 이렇게 했는지 설명합니다. 면접 질문은 여기서 나옵니다.
5. **결과 표 → 실행 → 한계**: 검증하려는 사람을 위한 부분입니다.

설명이 긴 부분(실제 출력 전문, 데모 코드)은 `<details>`로 접어서 기본 화면을 짧게 유지했습니다.

**ADR(Architecture Decision Record)**
결정 하나를 1쪽으로 남기는 문서입니다. Michael Nygard가 제안한 형식(맥락·결정·결과)에 **대안**을 더했습니다.
- **맥락**: 그때 어떤 제약이 있었는지 적습니다.
- **결정**: 무엇을 골랐는지 코드의 실제 이름과 기본값까지 적습니다.
- **대안**: 무엇을 왜 버렸는지 적습니다.
- **결과**: 좋아진 점과 치른 대가를 적습니다.

결정이 바뀌면 옛 ADR을 고치지 않고 새 ADR로 대체합니다(superseded). 그래야 "그때는 왜 그렇게 판단했는지"가 남습니다. 이 저장소의 ADR에는 `면접에서 "왜 이렇게 했냐"고 물으면` 절을 더했습니다.

**결과를 과장하지 않고 쓰는 법**
이번에 지킨 규칙입니다. 8·9번과 7번의 일부는 PR 리뷰 지적을 받고 고쳤습니다.
1. **수치는 실험 기록에서 그대로 옮깁니다.** 다시 계산하거나 반올림을 바꾸지 않습니다. 옮긴 뒤에는 README·ADR의 소수가 모두 실험 기록에 있는지 스크립트로 대조했습니다. 예외는 데모 금리처럼 출처가 따로 있는 값뿐입니다.
2. **조건을 숫자 옆에 둡니다.** 골든셋 v0, 사람 검수 없음, 50문항(근거 있는 44문항), 한 번 실행, 역할 하나 같은 조건입니다.
3. **분모를 밝힙니다.** Recall은 44문항, 거절 정확도는 50문항, 인용 정밀도는 인용이 있는 39문항이 분모입니다. out_of_scope의 인용 정밀도 0.000은 1문항의 값입니다.
4. **차이가 잡음보다 큰지 씁니다.** 44문항에서 한 문항은 약 0.023입니다. dense와 hybrid의 Recall@5 차이는 한 문항입니다.
5. **기대와 반대인 결과를 숨기지 않습니다.** "하이브리드가 낫다"는 계획과 달리 dense가 더 좋았습니다. 그런데도 기본값을 hybrid로 둔 이유를 따로 적고, 그 결정이 "잠정"이라는 점을 밝혔습니다(ADR 0002).
6. **지표가 측정하지 못하는 것을 씁니다.** 문서 단위 근거는 Recall을 부풀립니다(조항 근거만 있는 25문항은 0.78~0.82). 거절 판정은 바꿔 말한 거절을 놓칩니다(범위 밖 6문항 중 4개). 인용 정밀도는 위치만 보기 때문에 내용 오류는 잡지 못합니다.
7. **데모도 골라 싣지 않습니다.** 데모 4문항 중 완전히 맞은 것은 하나(신용카드 연회비 거절)뿐입니다. 하나는 오답입니다(금리 2.55%, 정답 2.80%). 하나는 권한 필터는 맞게 동작했지만 거절 문구를 바꿔 말해서 시스템이 답변으로 셌고(`refused=false`), 무관한 인용이 붙었습니다. 나머지 하나는 대체로 맞지만 인용 하나가 틀렸습니다. 이 결과를 판정과 함께 그대로 실었습니다. 실패를 설명할 수 있다는 점이 평가 체계를 만든 이유를 보여 줍니다.
8. **설계 의도와 측정된 동작을 구분합니다.** "근거가 없으면 정해진 문구로 거절한다"는 설계 의도입니다. 측정에서는 범위 밖 6문항 중 4개가 문구를 바꿔 말했습니다. 그래서 "거절하도록 했다"라고 씁니다. 보안도 마찬가지입니다. 막은 것(HWPX 해제량·DTD, PDF 해제량·레이아웃 객체 수)과 아직 못 막은 것(PDF 파싱 CPU 시간)을 나눠 적습니다. 코드가 강제하지 않는 것(서버를 127.0.0.1에만 띄우기)은 "띄워야 한다"는 규칙으로 씁니다.
9. **누가 했는지 정확히 씁니다.** 가상 문서 6개와 코드는 에이전트가 썼습니다. 이것을 사람이 한 일(방향, 승인)과 섞어 "제가 직접 썼다"고 하면 꼬리 질문 하나에 무너집니다.

**"실제로 따라 해서 되는 명령만" — 새 폴더 clone 검증**
작업 폴더에는 이미 설치된 패키지, 모델 캐시, `data/`가 있습니다. 그래서 README에 빠진 단계가 있어도 드러나지 않습니다. 이를 확인하려고 `$TEMP` 아래 새 폴더에 clone하고, 새 가상환경에 README 명령 그대로 `.[dev]`를 설치해 `pytest -q`까지 실행했습니다. 코퍼스는 다시 내려받지 말라는 지시가 있었습니다. 그래서 새 폴더에서는 기존 원문 폴더를 `AXB_DATA_DIR`로 지정해 BM25 평가 명령만 실행했고, 기준선 수치(0.841 / 0.746)가 그대로 나오는지 확인했습니다. torch·임베딩·Ollama 단계는 2GB가 넘는 다운로드라 새 폴더에서 다시 하지 않았습니다. 대신 이미 설치된 환경에서 실행해 확인했고, 이 사실을 PR에 밝혔습니다.

## 면접 예상 질문과 답

### 이 프로젝트를 2분 안에 설명하는 대본

> "회사 문서를 넣으면 그 회사 전용 RAG 어시스턴트를 만들어 주는 플랫폼을 만들고 있습니다. 첫 버전은 가상 은행 하나이고, 문서 13개를 씁니다. 법령·고시 5개, 공정위 표준약관 2개, 그리고 실존하지 않는 'AXB은행'의 상품설명서와 내부 지침 6개입니다. 이 6개는 실제 은행 문서를 쓸 수 없어서 에이전트가 새로 쓴 가상 문서입니다.
>
> 흐름은 이렇습니다. 문서를 조항 단위로 나누고, Kiwi 형태소로 만든 BM25와 한국어 임베딩 검색을 RRF로 합칩니다. 로컬 4B 모델에는 근거 5개만 주고, 조항 번호를 인용해 답하되 근거가 없으면 정해진 문구로 거절하도록 했습니다. 권한은 검색 단계에서 걸러서 상담원에게는 내부 지침이 아예 보이지 않습니다. 금융 고객의 폐쇄망을 생각해서 로컬 모델이 기본이고, Claude로도 바꿀 수 있게 LLM을 프로토콜 하나 뒤에 두었습니다.
>
> 이 프로젝트의 중심은 평가입니다. 정답과 근거 조항을 단 50문항 골든셋으로 검색기 세 가지를 비교했습니다. 결과는 예상과 달랐습니다. 하이브리드가 아니라 dense 단독이 Recall@5 0.886으로 가장 좋았습니다. 문항별로 보니 RRF가 두 검색기 모두에 나온 청크를 우선하는 구조 때문이었습니다. 문서 단위 근거가 Recall을 부풀린다는 점, 거절 판정이 바꿔 말한 거절을 놓친다는 점도 실험 기록에 그대로 남겼습니다. 다만 골든셋은 사람이 검수하지 않았고 차이가 한 문항이라, 기본값을 바로 바꾸지 않았습니다. 그 뒤 150문항으로 다시 비교했을 때도 dense와 hybrid는 차이가 없어서, 기본값은 잠정적으로 hybrid로 두었습니다.
>
> 구현은 AI 코딩 에이전트 팀이 하고, 저는 방향과 우선순위를 정하고 설치·비용을 승인했습니다. 골든셋은 사람이 검수하지 않았고, 다른 에이전트가 원문과 전수 대조하게 했습니다. 작업마다 구현을 맡지 않은 별도 리뷰 에이전트가 PR을 리뷰합니다. 에이전트가 작업마다 학습 노트를 남기게 해서, 제가 모든 결정을 제 말로 설명할 수 있게 했습니다."

주의할 점이 있습니다. 이 대본의 수치는 Task 11 당시 골든셋 v0 기준입니다. 지금 말할 때는 README의 평가 결과(골든셋 v1) 수치를 쓰고, 골든셋은 사람이 검수하지 않았다는 점을 함께 말합니다.

면접 전에 직접 해 둘 일도 있습니다. 실험 기록의 "거절 지표를 출력으로 다시 읽은 결과" 표에 나온 문항을 `reports/bank/`의 보고서에서 직접 읽어 봅니다. 원래 README에 있다가 [실험 기록 모음](../experiments/README.md)으로 옮긴 데모 코드도 한 번 직접 실행해 봅니다. 대본의 숫자를 자기 눈으로 확인해 두면 꼬리 질문에도 흔들리지 않습니다.

**Q1. README 첫 줄에 왜 하이브리드가 아니라 dense가 더 좋았다는 숫자를 넣었나요?**
첫 줄은 결과를 말하는 자리라서 실제로 측정한 숫자를 그대로 넣었습니다. 계획과 다른 결과를 숨기면 면접에서 결과 표를 함께 볼 때 신뢰를 잃습니다. 저는 오히려 "왜 하이브리드가 졌는지"를 문항 단위로 분석한 것이 이 프로젝트의 강점이라고 생각합니다.

**Q2. 그럼 왜 API 기본값은 여전히 하이브리드인가요?**
차이가 44문항 중 한 문항이고, 골든셋은 사람이 검수하지 않았습니다. 그리고 조항 번호처럼 BM25가 강한 질문은 이번 골든셋에 없습니다. 이 상태로 기본값을 바꾸면 검증이 덜 된 50문항에 맞추는 셈이 될 수 있습니다. 그래서 ADR에 잠정 결정이라고 밝히고, 더 큰 골든셋에서 dense 계열이 이기면 바꾼다는 기준을 적어 두었습니다. M-2에서 150문항(근거가 있는 127문항)으로 다시 비교했을 때 두 검색기는 차이가 없었습니다. 그래서 바꿀 근거가 없었고, 사람이 검수한 표본도 없어서 hybrid를 그대로 두었습니다.

**Q3. ADR은 왜 쓰나요? 커밋 메시지나 PR 설명으로는 부족한가요?**
PR 설명은 "무엇을 바꿨나"가 중심이고, 여러 PR에 흩어집니다. ADR은 결정 하나에 대한 맥락, 버린 대안, 치른 대가를 1쪽으로 모읍니다. 그래서 몇 달 뒤 "왜 이렇게 했지?"라는 질문에 바로 답할 수 있습니다. 결정이 바뀌면 고치지 않고 새 ADR로 대체하기 때문에 판단의 이력도 남습니다.

**Q4. README의 실행 방법이 실제로 되는지 어떻게 확인했나요?**
작업 폴더에는 이미 설치된 패키지와 데이터가 있어서 빠진 단계가 보이지 않습니다. 그래서 README를 쓴 에이전트가 임시 폴더에 새로 clone하고, 새 가상환경에 README 명령 그대로 설치해 테스트까지 실행하게 했습니다. 코퍼스 평가 명령은 기준선과 같은 수치가 나오는지도 확인하게 했습니다. 다운로드가 큰 GPU·LLM 단계는 에이전트가 기존 환경에서 확인했고, 그 차이를 PR에 밝혔습니다.

**Q5. AI 에이전트가 구현했다면, 본인의 역할은 무엇인가요?**
제 역할은 방향과 우선순위를 정하고, 설치와 비용을 승인하는 것입니다. 에이전트의 결과물을 그대로 믿지 않도록 검증 구조도 두었습니다. 구현을 맡지 않은 별도 리뷰 에이전트, 네트워크 없이 실행되는 CI, 재현 명령이 붙은 실험 기록이 그것입니다. 골든셋은 다른 에이전트가 원문과 전수 대조했고, 사람이 검수하지 않았다는 점은 README에 밝혀 두었습니다. 작업마다 학습 노트를 남겨서 모든 결정을 제 말로 설명할 수 있게 했습니다.
