## 핵심 개념

**8분 안에 읽히는 README = 역피라미드**
서류 검토자는 위에서부터 읽다가 아무 데서나 멈춘다. 그래서 가장 중요한 것을 맨 위에 둔다.
1. **결과 한 줄**: 무엇을 만들었고 얼마였는지를 숫자로 쓴다. "강력한", "고성능" 같은 형용사는 쓰지 않는다.
2. **데모**: 실제로 돈다는 증거다. GIF가 없어서 API로 한 번 실행한 출력을 그대로 실었다.
3. **아키텍처**: 그림 하나와 표 하나로 "어디에 무엇이 있는지"를 보여 준다.
4. **결정과 근거**: 왜 이렇게 했는지 알려 준다. 면접 질문이 여기서 나온다.
5. **결과 표 → 실행 → 한계**: 검증할 사람을 위한 부분이다.

설명이 긴 부분(실제 출력 전문, 데모 코드)은 `<details>`로 접어서 기본 화면을 짧게 유지했다.

**ADR(Architecture Decision Record)**
결정 하나를 1쪽에 남기는 문서다. Michael Nygard가 제안한 형식(맥락·결정·결과)에 **대안**을 더했다.
- **맥락**: 그때 어떤 제약이 있었나
- **결정**: 무엇을 골랐나. 코드의 실제 이름과 기본값까지 적는다
- **대안**: 무엇을 왜 버렸나
- **결과**: 좋아진 점과 치른 대가

결정이 바뀌면 옛 ADR을 고치지 않고 새 ADR이 대체한다(superseded). 그래야 "그때는 왜 그렇게 판단했는지"가 남는다. 이 저장소의 ADR에는 "면접에서 물으면 할 대답" 절을 더했다.

**결과를 과장하지 않고 쓰는 법 (이번에 지킨 규칙. 8·9와 7의 일부는 PR 리뷰 지적을 받고 고친 것)**
1. **수치는 실험 기록에서 그대로 옮긴다.** 다시 계산하거나 반올림을 바꾸지 않는다. 옮긴 뒤 README·ADR의 소수가 모두 실험 기록에 있는지 스크립트로 대조했다(예외는 데모 금리처럼 다른 출처가 있는 값뿐).
2. **조건을 숫자 옆에 둔다.** 골든셋 v0, 사람 검수 전, 50문항(근거 있는 44문항), 한 번 실행, 역할 하나.
3. **분모를 밝힌다.** Recall은 44문항, 거절 정확도는 50문항, 인용 정밀도는 인용이 있는 39문항이 분모다. out_of_scope의 인용 정밀도 0.000은 1문항의 값이다.
4. **차이가 잡음보다 큰지 쓴다.** 44문항에서 한 문항은 약 0.023이다. dense와 hybrid의 Recall@5 차이는 한 문항이다.
5. **기대와 반대인 결과를 숨기지 않는다.** "하이브리드가 낫다"는 계획과 달리 dense가 더 좋았다. 그런데도 기본값을 hybrid로 둔 이유를 따로 적고, 그것이 "잠정"임을 밝혔다(ADR 0002).
6. **지표가 못 재는 것을 쓴다.** 문서 단위 근거는 Recall을 부풀린다(조항 근거만 있는 25문항은 0.78~0.82). 거절 판정은 바꿔 말한 거절을 놓친다(범위 밖 6문항 중 4개). 인용 정밀도는 위치만 보고 내용 오류는 못 잡는다.
7. **데모도 고르지 않는다.** 데모 4문항 중 완전히 맞은 것은 하나(신용카드 연회비 거절)뿐이다. 하나는 오답(금리 2.55%, 정답 2.80%)이다. 하나는 권한 필터는 맞게 동작했지만 거절 문구를 바꿔 말해 시스템이 답변으로 셌고(`refused=false`), 무관한 인용이 붙었다. 하나는 대체로 맞지만 인용 하나가 틀렸다. 이것을 판정과 함께 그대로 실었다. 실패를 설명할 수 있다는 것이 평가 체계를 만든 이유를 보여 준다.
8. **설계 의도와 측정된 동작을 구분한다.** "근거가 없으면 정해진 문구로 거절한다"는 설계 의도다. 측정에서는 범위 밖 6문항 중 4개가 문구를 바꿔 말했다. 그래서 "거절하도록 했다"로 쓴다. 보안도 같다. 막은 것(HWPX 해제량·DTD, PDF 해제량·레이아웃 객체 수)과 아직 못 막은 것(PDF 파싱 CPU 시간)을 나눠 적는다. 코드가 강제하지 않는 것(서버를 127.0.0.1에만 띄우기)은 "띄워야 한다"는 규칙으로 쓴다.
9. **누가 했는지 정확히 쓴다.** 가상 문서 6개와 코드는 에이전트가 썼다. 사람이 한 일(방향, 승인, 검수)과 섞어 "제가 직접 썼다"고 하면, 꼬리 질문 하나에 무너진다.

**"실제로 따라 해서 되는 명령만" — 새 폴더 clone 검증**
작업 폴더에는 이미 설치된 패키지, 모델 캐시, `data/`가 있다. 그래서 README에서 빠진 단계가 있어도 드러나지 않는다. `$TEMP` 아래 새 폴더에 clone하고, 새 가상환경에 README 명령 그대로 `.[dev]`를 설치해 `pytest -q`까지 돌렸다. 코퍼스 다운로드는 다시 받지 말라는 지시가 있었다. 그래서 새 폴더에서는 기존 원문 폴더를 `AXB_DATA_DIR`로 가리켜 BM25 평가 명령만 돌렸다. 기준선 수치(0.841 / 0.746)가 그대로 나오는지 확인했다. torch·임베딩·Ollama 단계는 2GB가 넘는 다운로드라 새 폴더에서 다시 하지 않았다. 이미 설치된 환경에서 실행해 확인했고, 그 사실을 PR에 밝혔다.

## 면접 예상 질문과 답

### 이 프로젝트를 2분 안에 설명하는 대본

> "회사 문서를 넣으면 그 회사 전용 RAG 어시스턴트를 만들어 주는 플랫폼을 만들고 있습니다. 첫 버전은 가상 은행 하나로, 법령·고시 5개와 공정위 표준약관 2개, 그리고 실존하지 않는 'AXB은행'의 상품설명서와 내부 지침 6개, 모두 13개 문서를 씁니다. 이 6개는 실제 은행 문서를 쓸 수 없어서 에이전트가 새로 쓴 가상 문서입니다.
>
> 흐름은 이렇습니다. 문서를 조항 단위로 나누고, Kiwi 형태소로 만든 BM25와 한국어 임베딩 검색을 RRF로 합칩니다. 로컬 4B 모델에는 근거 5개만 주고, 조항 번호를 인용해 답하되 근거가 없으면 정해진 문구로 거절하도록 했습니다. 권한은 검색 단계에서 걸러서 상담원에게는 내부 지침이 아예 보이지 않습니다. 금융 고객의 폐쇄망을 생각해서 로컬 모델이 기본이고, Claude로도 바꿀 수 있게 LLM을 프로토콜 하나 뒤에 두었습니다.
>
> 이 프로젝트의 중심은 평가입니다. 정답과 근거 조항을 단 50문항 골든셋으로 검색기 셋을 비교했습니다. 결과는 예상과 달랐습니다. 하이브리드가 아니라 dense 단독이 Recall@5 0.886으로 가장 좋았습니다. 문항별로 보니 RRF가 두 검색기 모두에 나온 청크를 우선하는 구조 때문이었습니다. 문서 단위 근거가 Recall을 부풀린다는 점, 거절 판정이 바꿔 말한 거절을 놓친다는 점도 실험 기록에 그대로 남겼습니다. 다만 골든셋이 아직 사람 검수 전이고 차이가 한 문항이라, 다음 단계에서 150문항 이상으로 늘리고 리랭커와 가중 RRF를 비교해 기본값을 정합니다.
>
> 구현은 AI 코딩 에이전트 팀이 하고, 저는 방향과 우선순위를 정하고, 설치·비용을 승인하고, 에이전트가 만든 골든셋 15문항을 표본으로 검수했습니다. 작업마다 구현과 다른 리뷰 에이전트가 PR을 리뷰합니다. 에이전트가 작업마다 학습 노트를 남기게 해서, 제가 모든 결정을 제 말로 설명할 수 있게 했습니다."

주의: 마지막 문단의 "골든셋 15문항을 검수했습니다"는 검수(`docs/eval/golden-v0-review-sheet.md`)를 끝낸 뒤에만 사실이다. 끝내기 전에는 이 대본을 쓰지 않는다.

면접 전에 직접 해 둘 것: 실험 기록의 "거절 지표를 사람이 다시 읽은 결과" 표에 나온 문항을 `reports/bank/`의 보고서에서 직접 읽어 본다. README의 데모 코드도 한 번 직접 돌려 본다. 대본의 숫자를 자기 눈으로 확인해 두면 꼬리 질문에 흔들리지 않는다.

**Q1. README 첫 줄에 왜 하이브리드가 아니라 dense가 더 좋았다는 숫자를 넣었나요?**
첫 줄은 결과를 말하는 자리라서 실제로 잰 숫자를 그대로 넣었습니다. 계획과 다른 결과를 숨기면, 면접에서 결과 표를 볼 때 신뢰를 잃습니다. 오히려 "왜 하이브리드가 졌는지"를 문항 단위로 분석한 것이 이 프로젝트의 강점이라고 생각합니다.

**Q2. 그럼 왜 API 기본값은 여전히 하이브리드인가요?**
차이가 44문항 중 한 문항이고, 골든셋은 아직 사람 검수 전입니다. 그리고 조항 번호처럼 BM25가 강한 질문은 이번 골든셋에 없습니다. 이 상태로 기본값을 바꾸면 검수 전 50문항에 맞추는 것이 될 수 있습니다. 그래서 잠정 결정이라고 ADR에 밝혔습니다. M-2에서 150~200문항으로 다시 비교해 dense 계열이 이기면 바꾼다는 기준도 적어 두었습니다.

**Q3. ADR은 왜 쓰나요? 커밋 메시지나 PR 설명으로는 부족한가요?**
PR 설명은 "무엇을 바꿨나" 중심이고, 여러 PR에 흩어집니다. ADR은 결정 하나에 맥락, 버린 대안, 대가를 1쪽으로 모읍니다. 그래서 몇 달 뒤 "왜 이렇게 했지?"에 바로 답할 수 있습니다. 결정이 바뀌면 고치지 않고 새 ADR로 대체해서 판단의 이력이 남습니다.

**Q4. README의 실행 방법이 실제로 되는지 어떻게 확인했나요?**
작업 폴더에는 이미 설치된 패키지와 데이터가 있어서 빠진 단계가 보이지 않습니다. 그래서 README를 쓴 에이전트가 임시 폴더에 새로 clone하고, 새 가상환경에 README 명령 그대로 설치해 테스트까지 돌리게 했습니다. 코퍼스 평가 명령은 기준선과 같은 수치가 나오는지도 확인하게 했습니다. 다운로드가 큰 GPU·LLM 단계는 에이전트가 기존 환경에서 확인했고, 그 차이를 PR에 밝혔습니다. 저는 그 PR 기록을 읽고 확인 범위를 검토했습니다.

**Q5. AI 에이전트가 구현했다면, 본인의 역할은 무엇인가요?**
방향과 우선순위 결정, 설치·비용 승인, 그리고 검수입니다. 에이전트의 결과물을 그대로 믿지 않도록 검증 구조를 두었습니다. 구현과 다른 리뷰 에이전트, 네트워크 없이 도는 CI, 재현 명령이 붙은 실험 기록, 그리고 에이전트가 만든 골든셋을 제가 표본 15문항으로 검수하는 단계입니다(대기 중). 작업마다 학습 노트를 남겨서 모든 결정을 제 말로 설명할 수 있게 했습니다.
