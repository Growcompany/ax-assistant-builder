# Task 14 — 웹 화면

계획은 [`2026-11-10-web-ui.md`](../superpowers/plans/2026-11-10-web-ui.md) 1부이고, 결정 기록은 [ADR 0004](../adr/0004-web-ui-static.md)에 있습니다. 커밋은 `6708c20`(조회 API, 정적 파일 제공)과 `8163fed`(화면)입니다.

## 이 작업이 하는 일

서버 하나만 띄우면 브라우저에서 "워크스페이스 고르기 → 문서 올리기 → 색인 → 역할을 골라 질문 → 인용한 원문 확인"까지 할 수 있습니다. 작업은 백엔드와 프런트엔드 두 부분으로 나뉩니다.

**백엔드(14-A)** — 화면에 필요한 API를 더했습니다. 기존 API의 경로·필드·상태 코드는 바꾸지 않고 새 API만 더했습니다.

| API | 하는 일 |
|---|---|
| `GET /workspaces` | 워크스페이스 목록을 id 오름차순으로 반환합니다. 문서 수와 색인 상태(`none`·`ready`·`stale`)도 함께 담습니다 |
| `GET /workspaces/{id}` | 위 내용에 문서 목록을 더합니다. `indexed`는 그 문서가 지금 색인에 들어 있는지를 나타냅니다 |
| `POST /workspaces/{id}/ask` | 응답에 `passages`를 더했습니다. `passages[i]`는 `citations[i]`가 가리키는 청크의 원문입니다 |
| `POST /demo-workspace` | 저장소에 있는 가상 은행 문서 6개로 워크스페이스 `demo`를 만듭니다. 색인은 하지 않습니다 |
| `GET /`, `GET /static/…` | 화면 파일을 제공합니다. CSP·nosniff 머리글을 붙입니다 |

**프런트엔드(14-B)** — `src/axbuilder/api/static/`에 HTML 하나, CSS 하나, ES 모듈로 된 JS를 두었습니다. 빌드 도구는 쓰지 않습니다. 화면은 왼쪽 사이드바(워크스페이스 목록, 서버 상태), 워크스페이스 화면(질문 탭, 문서 탭), 인용을 누르면 열리는 근거 패널로 이루어져 있습니다. 워크스페이스가 하나도 없으면 첫 화면에서 다음에 할 일(예시 불러오기, 직접 만들기)을 보여 줍니다.

구현 세션의 에이전트가 2026-11-11에 실제 서버와 `qwen3.5:4b-q4_K_M`으로 브라우저에서 다음 흐름을 확인했습니다. 예시 워크스페이스를 불러오고, 색인하고(69청크), 질문한 뒤 근거 패널을 열고, 같은 질문을 역할만 바꿔 다시 물었습니다. 준법감시 역할은 내부 지침 제11조를 인용했고, 상담원 역할은 근거가 없다며 거절했습니다.

## 핵심 개념

**XSS와 `textContent`.** 화면에 나오는 문서 제목, 답변, 인용 원문은 남이 쓴 글입니다. 이것을 `innerHTML`로 넣으면 브라우저가 글자를 마크업으로 해석해서 `<img onerror=…>` 같은 코드가 실행됩니다. `textContent`나 `createTextNode`로 넣으면 글자 그대로 보입니다. 이 화면은 DOM을 만들 때 늘 도우미 함수 `h()` 하나를 거치고, 이 함수는 문자열을 항상 텍스트 노드로 붙입니다.

**답변을 마크업 없이 꾸미기.** 답변에는 `**굵게**`, `- 목록`, 인용 번호 `[1]`이 섞여 있습니다. 마크다운 라이브러리로 HTML 문자열을 만들어 넣으면 위 규칙이 깨집니다. `answer.js`는 문자열을 정규식으로 잘라 토큰 배열(`text`·`bold`·`cite`)을 만들고, 토큰마다 노드를 하나씩 만듭니다. `[n]`은 1 ≤ n ≤ 인용 수일 때만 누를 수 있는 인용이 되고, 그 밖의 번호는 글자 그대로 남습니다.

**CSP(Content-Security-Policy).** 서버가 응답 머리글로 브라우저에 "이 페이지는 어디서 온 자원만 쓴다"를 알립니다. `default-src 'self'`이면 같은 출처의 파일만 불러오고, 인라인 `<script>`와 `style=""`은 막힙니다. 코드 규칙이 한 번 깨져도 스크립트가 실행되지 않게 막는 두 번째 벽입니다. 대신 화면 코드도 인라인 스크립트나 스타일을 쓸 수 없습니다. 그래서 첫 화면을 그리기 전에 테마를 적용하는 짧은 스크립트도 별도 파일(`theme-init.js`)로 두었습니다.

**`nosniff`와 MIME 타입.** `X-Content-Type-Options: nosniff`는 브라우저가 내용을 보고 형식을 추측하지 못하게 합니다. 그러면 서버가 알려 주는 `Content-Type`이 정확해야 합니다. Windows에서는 `mimetypes`가 레지스트리를 읽어 `.js`를 `text/plain`으로 알려 줄 때가 있는데, 그러면 브라우저가 모듈 스크립트를 실행하지 않습니다. 그래서 `app.py`에서 `.js`·`.css`·`.svg`의 형식을 직접 등록합니다.

**색인 상태 `stale`.** 색인한 뒤에 올린 문서는 답에 나오지 않습니다. 사용자는 "올렸는데 왜 안 나오지" 하고 헷갈리게 됩니다(Review Focus 3). 그래서 `index/index.json`에 색인에 넣은 `doc_id` 목록을 남기고, 지금 문서 목록과 다르면 `stale`로 표시합니다. 목록이 없는 예전 `index.json`이나 깨진 파일도 `ready`가 아니라 `stale`로 읽습니다. 확실하지 않을 때는 다시 색인하라고 안내하는 편이 안전하기 때문입니다. 임베딩 모델이 바뀐 색인도 `stale`입니다.

**`passages`와 권한.** 근거 패널에 원문을 보여 주려면 청크 본문이 필요합니다. `chunk_id`로 원문을 주는 API를 따로 만들면 권한 밖 문서의 본문을 가져갈 길이 생깁니다. 그래서 원문은 **그 질문에서 그 역할로 검색된 청크** 안에서만 찾아 `ask` 응답에 함께 넣습니다(`answer_with_usage`). 색인 전체에서 찾지 않습니다.

**상태와 이벤트.** 프레임워크가 없어서 무엇이 바뀌면 무엇을 다시 그릴지를 직접 정해야 합니다. `state.js`에는 상태 객체 하나와 `on(이벤트, 함수)`/`emit(이벤트)`가 있습니다. `actions.js`가 서버를 부르고 상태를 바꾼 뒤 `emit`하면, 그 이벤트를 구독한 화면 조각이 다시 그려집니다. 대화 기록은 메모리에만 두므로 페이지를 새로 고치면 사라집니다.

## 왜 이렇게 했나 (대안과 비교)

- **Streamlit 대신 정적 화면.** 프로세스와 의존성이 늘지 않고, 외부 요청 없이 화면이 뜨고, 화면 구성을 직접 정할 수 있습니다. 대신 상태 관리 코드를 직접 짰고 프런트엔드 단위 테스트가 없습니다. React+번들러, HTMX와의 비교는 [ADR 0004](../adr/0004-web-ui-static.md)에 있습니다.
- **프런트엔드 테스트 대신 파이썬 정적 검사.** [`test_static_ui.py`](../../tests/api/test_static_ui.py)는 `static/`의 파일을 텍스트로 읽어서 `innerHTML`·`eval(`·외부 URL·인라인 이벤트 속성 같은 것이 있으면 실패합니다. `index.html`이 참조하는 파일과 JS의 상대 경로 `import`가 실제로 있는지도 확인합니다. 번들러가 없으면 깨진 import가 브라우저에서야 드러나기 때문입니다. 이 검사가 보장하는 것은 위험한 API를 쓰지 않았다는 것뿐입니다. 동작이 맞는지는 브라우저에서 직접 확인합니다.
- **예시 워크스페이스도 업로드와 같은 경로로.** `create_demo`는 파일을 직접 복사하지 않고 `add_document()`를 부릅니다. 그래서 형식·서명·파싱 검사를 똑같이 거치고 저장되는 모양도 같습니다. 도중에 실패하면 그때까지 만든 것을 모두 지웁니다. 반쯤 만든 `demo`가 남으면 다시 눌러도 409가 나서 화면에서는 고칠 방법이 없기 때문입니다.
- **색인을 열지 않는 조회 API.** 목록 화면이 뜰 때마다 Qdrant나 임베딩 모델을 열면 느리고 GPU도 씁니다. 그래서 `index.json`만 읽습니다. 이 파일은 쓸 때 통째로 바꿔 끼우므로, 잠금 없이 읽어도 반쯤 쓴 내용을 읽을 일이 없습니다.
- **오류는 그 자리에 문장으로.** LLM이 꺼져 있어도(503) 화면이 멈추지 않고, 이유와 할 일(`ollama serve`)을 보여 줍니다(Review Focus 4). `errors.js`가 상태 코드와 상황(질문, 업로드, 색인)에 맞춰 안내 문장과 다음 동작(다시 시도, 다시 색인)을 정합니다.
- **등급은 직접 고르게.** 업로드 양식의 `access_level`에는 기본값이 없습니다. 기본값이 `public`이면 등급을 고르지 않고 올린 내부 문서가 모두에게 보이기 때문입니다. 서버(`UploadMeta`)와 화면 모두 이렇게 했습니다.
- **정적 파일은 패키지 데이터로.** `pyproject.toml`에 `"axbuilder.api" = ["static/**"]`를 넣어서 `pip install`로 설치한 뒤에도 화면이 뜹니다. 테스트에서 `importlib.resources`로 `index.html`이 들어 있는지 확인합니다.

## 면접 예상 질문과 답

**Q1. 왜 React나 Streamlit을 쓰지 않았나요?**
이미 FastAPI 서버가 있으니, 그 서버에서 정적 파일까지 제공하면 프로세스도 의존성도 늘지 않습니다. 폐쇄망 고객을 생각하면 외부 요청이 0건이어야 했고, 인용을 누르면 원문이 열리는 화면도 직접 구성하고 싶었습니다. 대신 상태 관리를 직접 짰고 프런트엔드 단위 테스트는 없습니다. 화면이 더 커지면 다시 따져 볼 결정입니다.

**Q2. 문서 제목에 스크립트가 들어 있으면 어떻게 되나요?**
글자 그대로 보입니다. 서버에서 온 글자는 텍스트 노드로만 넣고, 답변의 굵게·목록·인용 표시도 문자열을 토큰으로 잘라 노드를 직접 만듭니다. 그 위에 CSP가 인라인 스크립트를 막고, `innerHTML` 같은 API가 코드에 들어오면 실패하는 테스트를 CI에서 실행합니다. 한 겹이 뚫려도 다음 겹에서 막히도록 했습니다.

**Q3. 프런트엔드 테스트 없이 품질을 어떻게 확인했나요?**
세 가지로 나눠서 확인했습니다. 화면이 쓰는 API는 파이썬 테스트로 검증합니다. 위험한 코드 패턴과 깨진 파일 참조는 정적 검사 테스트가 잡습니다. 실제 동작은 구현을 맡은 에이전트가 실제 서버와 모델을 띄우고 브라우저에서 처음부터 끝까지 눌러 보며 확인했습니다. 화면 동작의 회귀를 자동으로 잡지 못한다는 한계는 남아 있습니다.

**Q4. 근거 원문을 보여 주는 API를 따로 두지 않은 이유는요?**
`chunk_id`로 원문을 주는 API는 권한 검사를 한 번 더 해야 하고, 그 검사를 빠뜨리면 내부 문서가 새는 길이 됩니다. 그래서 원문은 질문 응답에 함께 넣되, 그 질문에서 그 역할로 검색된 청크 안에서만 찾습니다. 권한 밖 청크는 검색 단계에서 이미 빠졌으므로 응답으로 나갈 수 없습니다. public 역할로 물었을 때 `passages`에 내부 문서 본문이 없는지 확인하는 테스트도 있습니다.

**Q5. 색인 상태를 왜 세 가지로 나눴나요?**
문서를 올려도 다시 색인하기 전에는 답에 나오지 않기 때문입니다. 그래서 색인에 들어간 문서 목록을 남겨 두고, 지금 문서 목록과 다르면 `stale`로 알립니다. 판단할 정보가 없는 예전 파일이나 깨진 파일도 `stale`로 봅니다. "최신"이라고 잘못 말하는 것보다 다시 색인하라고 하는 편이 안전합니다.
