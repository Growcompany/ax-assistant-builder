# Task 3 — 워크스페이스와 가상 은행 코퍼스

## 이 작업이 하는 일

- `src/axbuilder/settings.py`: `Settings.from_env()`는 `AXB_*` 환경변수 6개(데이터 폴더, LLM 모드, 로컬·클라우드 모델, Ollama 주소, 임베딩 모델)를 읽고, 값이 없거나 비어 있으면 기본값을 씁니다.
- `src/axbuilder/workspace.py`: `Workspace(id, name, industry, roles)`와 `WorkspaceStore(root)`입니다. 설정을 `root/{id}/workspace.yaml`에 저장하고, 조회하고, 나열합니다. id는 `^[a-z0-9-]{2,32}$`만 허용합니다.
- `src/axbuilder/ingest/loaders.py`: `.hwpx`(공정위 표준약관 형식) 읽기를 추가했습니다.
- `src/axbuilder/ingest/chunking.py`: `chunk_document`가 **doc_type과 관계없이** 조항 머리가 2개 이상이면 조항 단위로 자릅니다. `부칙` 뒤의 조항은 `"부칙 제N조"`로 표시합니다.
- `src/axbuilder/ingest/law_html.py`: 국가법령정보센터 본문 HTML을 조문 줄 텍스트로 바꿉니다.
- `src/axbuilder/corpus.py`와 `scripts/download_corpus.py`: `sources.yaml`(13개)을 검증해 읽고, url 문서 7개를 받아 `data/workspaces/bank/raw/`에 저장합니다. `raw/manifest.json`에는 sha256과 받은 시각을 남깁니다.

```
corpus/bank/sources.yaml ─load_sources─▶ [CorpusSource × 13]
   url 7개 ─GET─▶ HTML → law_html_to_text → raw/{doc_id}.txt     ┐
                  HWPX(ZIP) 그대로        → raw/{doc_id}.hwpx    ├─ raw/manifest.json
   path 6개 ─────▶ 저장소의 corpus/bank/{synthetic,internal}/*.md ┘
source_file(s) ─▶ load_document ─▶ chunk_document ─▶ [Chunk(article="제4조의2" | "부칙 제1조" | None)]
```

## 핵심 개념

**경로 조작(path traversal) 방어**
워크스페이스 id와 doc_id는 그대로 폴더·파일 이름이 됩니다. `../etc`가 들어오면 `data/workspaces/../etc/`처럼 데이터 폴더 밖을 읽고 쓰게 됩니다. 이를 막으려면 위험한 문자를 빼는 블랙리스트가 아니라 **허용할 문자만 정하는** 화이트리스트를 써야 합니다. `[a-z0-9-]{2,32}`에는 `/`, `\`, `.`이 없어서 어떤 조합으로도 상위 폴더로 갈 수 없습니다. 여기에 두 가지를 더 챙겼습니다.
- `re.match(r"^...$")`의 `$`는 끝의 `\n` 앞에서도 맞습니다. 그러면 `"bank\n"`이 통과하므로 `re.fullmatch`를 씁니다(테스트로 고정).
- `con`, `nul`은 정규식을 통과하지만 Windows가 장치 이름으로 예약해 두어서 폴더로 만들 수 없습니다. 그래서 따로 막습니다.
- 검사는 디스크를 건드리기 **전에**(`WorkspaceStore.path`) 합니다. `sources.yaml`의 `path`에도 같은 원칙을 적용합니다. 상대 경로만 받고 `..`·절대 경로·드라이브 문자·역슬래시는 거부하며, 마지막으로 `resolve()` 결과가 저장소 안인지 한 번 더 확인합니다(심볼릭 링크 대비).

**설정과 코드의 분리**
모델 이름, 서버 주소, 데이터 위치를 코드에 박아 두면 바꿀 때마다 코드를 고쳐야 하고, 개발 PC·CI·서버마다 값도 다릅니다. 그래서 값은 환경변수로 받고 코드에는 기본값만 둡니다(12-factor app의 "config" 원칙). 비밀값(`ANTHROPIC_API_KEY`)은 일부러 `Settings`에 넣지 않았습니다. SDK가 환경변수에서 직접 읽기 때문에, 설정 객체를 로그나 API 응답에 찍어도 키가 새지 않습니다(테스트로 고정). 빈 값(`AXB_LLM_MODE=`)은 "설정하지 않음"으로 봅니다. `.env`에 빈 줄을 남겨 둔 경우에는 잘못된 값이라는 오류를 내기보다 기본값을 쓰는 편이 낫기 때문입니다.

**HWPX 구조**
HWPX는 한컴오피스의 개방형 형식(OWPML, KS X 6101)이고, 실체는 **ZIP 안의 XML**입니다. 본문은 `Contents/section0.xml, section1.xml …`에 나뉘어 있고, 문단은 `hp:p` > `hp:run`(글자 모양이 같은 구간) > `hp:t`(글자) 구조입니다. 구현하면서 세 가지를 신경 썼습니다.
1. 구역은 번호를 숫자로 보고 정렬합니다. 이름순으로 정렬하면 `section10`이 `section2`보다 앞에 오기 때문입니다.
2. 표 안의 글자가 두 번 나오지 않게 합니다. 셀 안의 문단(`hp:tbl > hp:tc > hp:subList > hp:p`)은 바깥 문단 **안에** 중첩되어 있어서, "문단의 모든 하위 글자"를 모으면 셀 내용이 두 번 나옵니다. 그래서 각 `hp:t`를 **가장 가까운 상위 `hp:p`**에만 붙입니다.
3. 업로드된 파일의 압축 폭탄(zip bomb)을 막습니다. ZIP은 1MB가 수 GB로 풀릴 수 있습니다. 그래서 구역을 **1MB씩 풀어 읽으며** 실제로 푼 바이트를 세고, 합계가 50MB를 넘으면 그 자리에서 거절합니다. 처음에는 헤더에 적힌 크기(`file_size`)의 합을 검사했는데, PR 리뷰에서 이 방어가 우회됐습니다. 헤더는 공격자가 마음대로 적을 수 있고, `zf.read()`는 구역 전체를 한 번에 푼 **다음에** 헤더 크기로 자르기 때문입니다. 헤더에는 109바이트라고 적었지만 실제로는 300MB가 풀리는 파일을 만들었습니다. 크기가 306KB인 이 파일로 재현해 보면, 예전 코드는 최대 메모리를 602MiB 쓰고 새 코드는 2.6MiB를 씁니다. 회귀 테스트는 풀면 64MB가 되는 파일을 읽을 때의 최대 메모리를 `tracemalloc`으로 측정합니다. 압축 방식은 stored와 deflate만 받습니다. `zipfile`은 deflate일 때는 요청한 양까지만 풀지만, bzip2·lzma는 한 번 읽을 때 풀 양에 상한이 없습니다. 한컴오피스는 deflate만 씁니다. 푼 조각은 바로 XML 파서에 넣어서(`XMLParser.feed`) 원본 바이트를 통째로 들고 있지 않습니다. XML 자체의 엔티티 폭탄(billion laughs)은 이 환경의 expat 2.7.5가 막습니다. **(정정, Task 10) 앞 문장은 틀렸습니다.** expat의 방어는 100배 증폭까지 허용합니다. 그래서 Task 10 보안 리뷰에서 DTD 내부 엔티티를 넣은 4.6KB HWPX가 텍스트 66MB로 풀렸습니다. 지금은 `loaders.py`의 `_RejectDTD`가 구역 XML에서 DTD를 발견하면 엔티티를 정의하기 전에 거부합니다([Task 10 학습 노트](task-10-api.md)). 깊게 중첩된 XML은 재귀 대신 스택으로 처리해서 `RecursionError`를 피했습니다.

**알려진 한계**
- 법령 HTML에는 과거 개정의 부칙이 모두 들어 있습니다. 은행법은 본문 조항 청크(117개)보다 부칙 조항 청크(138개)가 더 많고, `부칙 제1조(시행일)`이 개정마다 반복됩니다. 검색 잡음이 될 수 있어서 "현행 부칙만 남기기"를 M-2 분할 실험 후보로 둡니다.
- **Task 8(골든셋) 주의:** 부칙 조항 라벨은 한 문서 안에서도 겹칩니다. `부칙 제1조`가 개정마다 있기 때문입니다. 그래서 정답 근거(`Evidence.article`)는 본문 조항으로 잡고, 라벨이 겹치는 법령의 부칙은 쓰지 않습니다. 예외가 하나 있습니다. 골든셋 bank-026의 근거는 가상 지침 `guide-counseling`의 `부칙 제2조`입니다. 이 문서는 부칙이 하나뿐이라 라벨이 겹치지 않습니다. 본문 제2조와 부칙 제2조를 구별하는지 확인하는 문항이고, Task 8의 "라벨마다 청크가 정확히 1개" 검사가 이 조건을 지킵니다.
- 다른 법률 개정 지시문은 줄 모양만 보고 판별합니다. `제33조의5 및 제33조의6을 각각 다음과 같이 신설한다.`처럼 조문 **여러 개**를 새로 쓰면 두 번째 조문은 여전히 부칙 조항으로 잡힙니다. 이 코퍼스에는 이런 경우가 없습니다.
- 행정규칙 HTML 끝의 별지 목록(`[별지 2] 과징금납부통지서` 등)은 마지막 부칙 청크 끝에 붙습니다. 장 제목(`제2장 …`)이 앞 조항 끝에 붙는 문제(Task 2)도 그대로입니다.
- 긴 조항도 더 자르지 않습니다. 가장 긴 청크는 금소법 부칙 제13조(11,452자)와 은행법 부칙 제9조(9,243자)입니다. 둘 다 다른 법률을 개정하는 부칙이고, 지시문을 앞 조항에 합치면서 길어졌습니다. Task 4에서 임베딩 모델의 입력 길이를 확인해야 합니다.

## 면접 예상 질문과 답

**Q1. 워크스페이스 id로 경로 조작 공격을 어떻게 막았나요?**
id가 그대로 폴더 이름이 되기 때문에, 허용 문자를 소문자·숫자·하이픈으로 제한하는 화이트리스트를 썼습니다. 슬래시와 점이 없으니 상위 폴더로 갈 수 없습니다. 정규식은 `fullmatch`로 검사해서 끝 줄바꿈으로 우회하는 것을 막았고, 디스크에 접근하기 전에 검사합니다. 출처 목록의 파일 경로도 상대 경로만 받고, 최종 경로가 저장소 안인지 `resolve()`로 한 번 더 확인합니다.

**Q2. API 키는 왜 Settings에 넣지 않았나요?**
설정 객체는 디버깅할 때 로그에 찍거나 상태 API로 내보내기 쉽습니다. 거기에 키가 들어 있으면 그 순간 유출됩니다. Anthropic SDK가 환경변수에서 키를 직접 읽으므로, 이 저장소의 코드가 키를 들고 다닐 이유가 없었습니다. `repr`과 JSON에 키가 나오지 않는다는 것도 테스트로 고정했습니다.

**Q3. HWPX를 읽을 때 표 중복과 zip bomb은 어떻게 처리했나요?**
HWPX에서 표는 문단 안에 들어 있고, 셀 안에 다시 문단이 있습니다. 바깥 문단의 하위 글자를 모두 모으면 셀 글자가 두 번 들어가기 때문에, 글자 요소마다 가장 가까운 상위 문단에만 붙였습니다.
zip bomb은 처음에 ZIP 헤더에 적힌 압축 해제 크기의 합으로 막았는데, 리뷰에서 헤더를 위조한 306KB 파일이 메모리를 600MB 쓰는 것이 재현됐습니다. 헤더는 믿을 수 없는 입력이고, `zf.read()`는 전부 푼 뒤에 자르기 때문입니다. 지금은 1MB씩 풀면서 실제로 푼 양을 세고, 출력 상한을 걸 수 없는 bzip2·lzma 구역은 거절합니다. 같은 파일에서 최대 메모리가 2.6MB로 줄었고, `tracemalloc`으로 최대 메모리를 확인하는 회귀 테스트도 넣었습니다.

**Q4. 공정위 약관 원문은 왜 저장소에 없나요?**
법령과 고시는 저작권법 제7조에 따라 보호받지 않습니다. 하지만 공정위 표준약관 게시물에는 공공누리 표시가 없고 공정위 정책상 사전 협의 대상이라 재배포 권리가 불명확합니다. 그래서 출처 URL과 다운로드 스크립트만 커밋하고, 받은 파일은 sha256과 함께 git 밖에 둡니다. 다른 사람도 같은 스크립트로 같은 파일을 받았는지 해시로 확인할 수 있습니다.

**Q5. 받은 약관을 실제로 열어 보니 무엇이 달랐나요?**
가상 주택담보대출 설명서는 금소법 기준으로 "대출 금액에 따른 철회 제한은 없다"고 쓰면서 근거로 약관 제4조의2도 인용합니다. 그런데 약관 원문 제4조의2 제2항에는 "2억원을 초과하는 담보대출은 철회할 수 없다"가 남아 있었습니다. 조 번호는 맞지만 법과 약관의 내용이 서로 다른 지점입니다. 그래서 평가 질문을 만들 때 정답 근거는 법 기준으로 두고, 이 차이는 "오래된 근거" 유형 질문의 소재로 쓰자고 PR에 보고했습니다.
