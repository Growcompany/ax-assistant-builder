# Task 24 — 골든셋 v1 (150문항)과 답 문구 기준 채점

## 이 작업이 하는 일

- `corpus/bank/golden.jsonl`을 50문항에서 150문항으로 늘렸다. 새 100문항(bank-051 ~ 150)은 lookup 52, table 14, multi_doc 17, out_of_scope 17이다. 그중 조항 번호로 묻는 질문 18(`article_ref`), 정식 상품명으로 묻는 질문 12(`product_name`), 정답이 부정문인 질문 26(`negative_answer`, 독립 대조에서 bank-118을 더함), 근거가 내부 지침뿐인 질문 8(`internal_only`)이 있다.
- v0의 애매한 3문항(bank-042·006·032)을 저장소 주인이 위임한 판단대로 고쳤다(`docs/eval/golden-v0-owner-check.md`).
- 스키마: `GoldItem.tags`(선택), `Evidence.anchor`(선택, 답이 든 짧은 원문 문구). `validate_golden`은 모르는 태그와 빈 anchor를 알린다.
- 지표: `metrics.matches_strict`, `recall_at_k_strict`, `reciprocal_rank_strict`. `eval.run` 보고서에 `by_tag`, 그리고 anchor가 있으면 `Recall@k(답 문구)`·`MRR(답 문구)` 열이 생긴다.
- 제작 기록: `docs/eval/golden-v1-build.md`(문항별 근거 위치·인용·답 문구·겹침, 범위 밖 검색어, BM25 결과). 다른 에이전트가 원문과 전수 대조했고(수정 2문항, 애매함 10문항) 결과는 같은 문서 맨 아래 "독립 대조 결과"에 있다.

```
golden.jsonl ─ load_golden ─▶ GoldItem(tags, evidence[anchor]) ─ validate_golden ─▶ []
     │
     ├─ matches(chunk, ev)        : 문서 + 조항 라벨이 같다           → Recall@k, MRR (예전과 같음)
     └─ matches_strict(chunk, ev) : 위 + 청크 본문에 anchor가 있다    → Recall@k(답 문구), MRR(답 문구)
```

## 핵심 개념

**표본 크기와 검정력.** 두 검색기를 문항 단위로 비교할 때 정확 맥니마 검정은 "한쪽만 맞힌 문항"(불일치 쌍)만 본다. 불일치가 5 대 0이어도 양측 p = 0.0625라 0.05에 못 미친다. 44문항에서는 불일치가 3~8개뿐이라 리랭커 이득이 방향은 같아도 유의하지 않았다(Task 21). 문항이 세 배가 되면 같은 효과에서 불일치 쌍도 대략 세 배가 되어, 같은 크기의 차이를 검정이 알아볼 가능성(검정력)이 커진다. 그래도 차이가 작으면 150문항으로도 유의하지 않을 수 있다.

**태그와 유형은 다른 축이다.** 유형(qtype)은 "답이 어디에 어떻게 있나"(조항 하나, 표 한 칸, 두 문서, 없음)이고, 태그는 "질문이 어떤 성격인가"(조항 번호로 묻나, 상품명으로 묻나, 정답이 부정문인가)다. 한 문항이 태그를 여러 개 가질 수 있어, 태그별 표는 행을 더해도 전체가 되지 않는다.

**대체 근거.** 같은 내용이 다른 문서·조항에도 있으면, 검색이 그것을 가져와 답이 맞아도 라벨이 아니라 0점이 된다. 스키마에 "이것도 정답" 칸이 없으므로 만들 때 피했다. 핵심어(예: `위약금`, `3영업일`)를 전체 청크에서 찾아 두 곳에 있으면 질문을 좁히거나 버렸다.

**답 문구(anchor) 기준 채점.** 근거 라벨은 "어느 조항인가"까지만 말한다. 긴 조항을 항 단위로 나누면(Task 25) 조각이 모두 같은 라벨을 물려받고, 상품설명서처럼 조항이 없는 문서는 6청크 중 아무거나 맞는다. 그래서 근거마다 답이 든 짧은 원문 문구를 달고, 그 문구가 든 청크만 정답으로 세는 지표를 따로 둔다. 기본 분할에서 상품설명서 근거의 정답 청크는 6개 → 1개(4개는 겹침 때문에 2개)로 준다.

## 왜 이렇게 했나 (대안과 비교)

- **태그를 `list[str]`로 두고 검증에서 거르기 vs `Literal`.** `Literal`이면 오타 하나로 파일 전체를 못 읽는다. 문자열로 읽고 `validate_golden`이 모르는 태그를 목록으로 알리면 한 번에 다 고칠 수 있다(근거 오타를 막은 `extra="forbid"`와 같은 생각).
- **답 문구 vs 글자 위치(span) 라벨.** 글자 위치는 정확하지만 원문이 조금만 바뀌어도(개정, 로더 수정) 깨지고 사람이 읽고 고치기 어렵다. 짧은 원문 문구는 사람이 읽을 수 있고, 공백만 맞추면 분할 방식이 달라도 같은 규칙으로 맞춰 볼 수 있다. 대신 근거마다 문구가 하나라, 정답이 여러 항에 걸치면 고른 항이 든 조각만 정답이 된다(한계로 적었다).
- **기존 지표를 고치지 않고 엄격 지표를 더하기.** `matches`·`recall_at_k`는 M-1의 약속(Interfaces)이고, 지난 실험 기록의 숫자가 그것으로 계산됐다. 바꾸면 과거 수치와 비교할 수 없다. 그래서 두 기준을 나란히 보고한다. anchor가 없는 골든셋이면 엄격 지표 필드와 열이 아예 생기지 않는다.
- **조항 번호 질문에서 "제" 생략을 섞기.** 사람은 "9조", "21조의2"라고도 쓴다. BM25 결과를 보면 "34조"(bank-060)는 놓쳤고 "제N조" 꼴 7문항은 모두 찾았다. 표현 차이가 검색에 영향을 준다는 것을 잴 수 있게 일부러 섞었다.
- **새 문항 수를 100으로 지키기.** 계획 표의 유형 수를 더하면 84였다. 계획이 여러 곳에서 100개(bank-051 ~ 150)를 말해, 표의 비율을 그대로 100개로 늘렸다(계획과 다른 점으로 적었다).

## 코드 읽는 순서

1. `src/axbuilder/eval/dataset.py`: `TAGS` → `Evidence.anchor` → `GoldItem.tags` → `validate_golden`의 태그·빈 anchor 검사.
2. `src/axbuilder/eval/metrics.py`: `matches_strict` → `_recall`·`_reciprocal_rank`(두 기준이 같은 계산을 쓴다) → `*_strict`.
3. `src/axbuilder/eval/run.py`: `run_eval`의 `strict`(anchor가 하나라도 있나) → `_record`의 엄격 값 → `_SUMMARY_KEYS` → `format_markdown`의 열과 태그 행.
4. `tests/eval/test_dataset.py` 아래쪽: 저장소 골든셋 분포·태그 최소 수·`internal_only`와 문서 등급, 실제 청크 대조(기본 분할과 800자 분할에서 anchor 찾기).
5. `docs/eval/golden-v1-build.md`: 만든 방법, 버린 문항, 문항별 표.

## 면접 예상 질문과 답

**Q1. 골든셋을 왜 50문항에서 150문항으로 늘렸나요?**
리랭커를 붙였을 때 Recall이 12개 조합 모두 같은 방향으로 올랐는데도 정확 맥니마 검정의 p값이 0.063~0.453이었습니다. 이 검정은 한쪽만 맞힌 문항만 보는데, 44문항에서는 그런 문항이 3~8개뿐이라 5 대 0이어도 p = 0.063입니다. 효과가 있어도 표본이 작아서 못 알아보는 것, 즉 검정력이 낮은 상태였습니다. 채점하는 문항이 44개에서 127개로 늘면 같은 효과에서 불일치 문항도 늘어 검정이 알아볼 가능성이 커집니다. 한 문항의 무게도 2.3%p에서 0.8%p로 줄어듭니다. 다만 늘린다고 유의해진다는 보장은 없고, 차이가 작으면 150문항으로도 유의하지 않다고 보고할 것입니다.

**Q2. 조항 번호로 묻는 질문은 왜 따로 넣었나요?**
ADR 0002에서 "hybrid가 dense보다 나은 경우가 있나"를 확인하려 했는데, v0에는 BM25가 강한 질의가 없어서 답할 수 없었습니다. "은행법 제38조", "AXB 든든 정기예금"처럼 문서에 글자 그대로 있는 말은 단어 일치 검색이 잘 찾고, 의미 벡터 검색은 숫자·고유명사에 약할 수 있습니다. 그래서 조항 번호 18문항과 상품명 12문항에 태그를 달고 보고서에 태그별 행을 만들었습니다. BM25만 돌린 지금 결과에서도 조항 번호 질문의 Recall@5는 0.944로, 조항 번호·상품명이 없는 새 lookup 22문항(0.773)보다 높습니다. "34조"처럼 "제"를 뺀 질문 하나는 놓쳐서, 표현 차이의 영향도 볼 수 있습니다. dense·hybrid 비교는 Task 26에서 같은 문항으로 합니다.

**Q3. 정답이 부정문인 문항은 왜 넣었나요?**
거절 판정기 때문입니다. 모델이 "자료로는 확인할 수 없습니다"라고 하면 거절로 보는데, "공동명의로는 가입할 수 없습니다", "만기일 이후에는 입금할 수 없습니다"처럼 정답 자체가 "~할 수 없다"인 경우가 있습니다. 실제로 리뷰에서 "미성년자는 가입 대상에 포함되지 않습니다"라는 정답 문장을 처음 규칙이 거절로 잘못 본 적이 있습니다. 그때는 합성 문장으로만 확인했고 실제 모델 출력에는 그런 꼴이 거의 없었습니다. 그래서 정답이 부정문인 25문항을 넣었고, Task 26에서 실제 모델 출력으로 판정기의 오탐을 셉니다.

**Q4. 사람 검수가 없는 골든셋을 어떻게 믿을 수 있다고 설명하나요?**
믿을 수 있는 범위를 나눠서 말합니다. 기계로 확인한 것은 네 가지입니다. 정답의 근거 인용이 원문에 글자 그대로 있는지, 근거 라벨이 실제 945청크 중 정확히 하나와 맞는지, 답 문구가 두 가지 분할 모두에서 근거 청크에 들어 있는지, 범위 밖 질문의 핵심어가 코퍼스에 없는지입니다. 이건 테스트로도 고정했습니다. 정답이 하나뿐인지, 고객이 실제로 이렇게 말하는지는 기계로 못 봅니다. 그래서 만든 에이전트와 다른 에이전트가 원문과 전수 대조하게 했습니다. 대조에서 정답의 사실 오류는 없었고, 원문에 없는 단정으로 시작한 정답 하나(bank-131)와 빠진 태그 하나(bank-118)를 고쳤으며, 판단이 갈리는 10문항은 고치지 않고 이유를 적었습니다. 같은 계열 모델이라 같은 오독을 놓칠 수 있다는 한계도 함께 적습니다. 주인이 판단을 위임했다는 사실은 기록하지만, 그것을 "사람 검수"라고 부르지 않습니다.

**Q5. 답 문구 기준 채점은 왜 더했나요?**
채점이 근거의 조항 라벨만 봐서 두 군데에서 점수가 후해졌기 때문입니다. 첫째, 긴 조항을 항 단위로 나누면 조각이 모두 같은 라벨을 물려받아, 답이 없는 앞 조각이 상위에 와도 정답으로 셉니다. 둘째, 상품설명서는 조항이 없어 그 문서의 아무 청크나 정답이었습니다. 그래서 근거마다 답이 든 짧은 원문 문구를 달고, 그 문구가 든 청크만 맞게 세는 지표를 더했습니다. BM25 기본 분할에서 MRR이 라벨 기준 0.752, 답 문구 기준 0.659입니다. 차이는 모두 상품설명서 문항에서 나왔고, 정답 청크가 6개에서 1개로 줄어든 결과입니다. 800자 분할에서는 라벨 기준 MRR이 거의 그대로(0.751)인데 답 문구 기준은 0.634로, 라벨 기준만 보면 분할의 손해를 못 봤을 것입니다. 기존 지표는 과거 실험과 비교하려고 그대로 두고 두 기준을 나란히 보고합니다.
