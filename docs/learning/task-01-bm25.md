# Task 1 — 형태소 토크나이저 + BM25 직접 구현

## 이 작업이 하는 일

- `src/axbuilder/models.py`: 검색 단위 `Chunk`(바꿀 수 없는 `frozen` 모델)와 검색 결과 `ScoredChunk(chunk, score)`.
- `src/axbuilder/retrieval/tokenizer.py`: `tokenize(text)` — Kiwi로 형태소를 나누고 **내용어만** 남긴다.
- `src/axbuilder/retrieval/bm25.py`: `BM25Index` — 라이브러리 없이 직접 만든 키워드 검색. `build(chunks)`로 색인, `search(query, k, access_levels)`로 검색.

```
"예금자보호법에 따른 보호한도는 얼마인가요?"
  공백 토큰화 → ["예금자보호법에", "따른", "보호한도는", "얼마인가요?"]   ← "보호 한도"와 하나도 안 맞음
  tokenize()  → ["예금자", "보호", "법", "따르", "보호", "한도", "얼마"]
```

## 핵심 개념

**형태소 분석과 품사 필터**
한국어는 조사·어미가 단어에 붙는 언어라서 공백으로 자르면 "한도는", "한도가", "한도를"이 서로 다른 단어가 된다. Kiwi는 문장을 형태소로 나누고 품사 태그를 붙인다. 검색에 의미가 있는 태그만 남긴다.

| 남김 | 태그 | 예 |
|---|---|---|
| 명사 | `NNG`·`NNP`·`NNB` (`NN`으로 시작) | 예금자, 보호, 원 |
| 동사·형용사 | `VV`·`VA` (원형으로 바뀜) | 따른 → `따르` |
| 어근·외국어·숫자 | `XR`·`SL`·`SN` | OTP → `otp`, 3 |
| 수사·일련번호 | `NR`, `W_SERIAL` | 1억원 → `1`·`억`·`원`, `1588-9999`, `2024.01.01` |
| **버림** | 조사 `J*`, 어미 `E*`, 부호 `S*`, 대명사 `NP`, 감탄사 `IC` 등 | 는, 에, ㄴ가요, ? |

**보완 1 — 단독 조사 불용어**: 문맥 없이 `"은?"`만 오면 Kiwi는 "은"을 명사(은, silver)로 읽는다. 그래서 **명사(`NN*`)로 태깅된** 1음절 조사 형태(은·가·을·의·과·로·요, 분석 조각 으·르)만 버린다. 품사를 함께 보므로 동사 "가서"의 `가/VV`는 남는다. "는·이·에·와·도"는 단독으로 와도 Kiwi가 `NP`·`IC`·`JX`로 태깅해 품사 필터에서 이미 빠지고, 목록에 넣으면 의존명사 "30도"의 `도/NNB`, "말한 이가"의 `이/NNB`까지 지워서 뺐다.
**보완 2 — 영어 소문자화**: "OTP"와 "otp"가 같은 단어로 맞도록 `SL` 토큰은 소문자로 바꾼다.
**보완 3 — 수사·일련번호**: 계획의 태그 목록에는 없지만 `NR`이 없으면 "1억원"과 "1천만원"이 둘 다 `["1", "원"]`이 되고, Kiwi가 `W_SERIAL` 한 토큰으로 묶는 전화번호·날짜는 통째로 사라진다. 은행 문서는 금액·시행일 질문이 많아서 둘 다 남긴다.

**TF-IDF와 BM25**
둘 다 "질문 단어가 이 문서에 **많이** 나오고(TF), 전체 문서에선 **드물수록**(IDF) 점수가 높다"는 생각이다. BM25는 TF-IDF의 두 약점을 고친다.

1. **빈도 포화 (k1)**: TF-IDF는 단어가 10번 나오면 1번보다 10배 점수다. BM25는 `tf·(k1+1)/(tf+k1·…)`라서 몇 번 나온 뒤부터는 거의 안 오른다(최대 k1+1배).
2. **길이 정규화 (b)**: 긴 문서는 우연히 단어를 많이 포함한다. `|D|/avgdl`로 평균보다 긴 문서의 점수를 깎는다.

```
IDF(q)      = ln( (N - n(q) + 0.5) / (n(q) + 0.5) + 1 )
score(D, Q) = Σ_q IDF(q) · f(q,D)·(k1+1) / ( f(q,D) + k1·(1 - b + b·|D|/avgdl) )
```

IDF의 `+ 1`은 Lucene(Elasticsearch)이 쓰는 형태다. `+1`이 없는 원래 식(rank_bm25의 `BM25Okapi`)은 절반 넘는 문서에 나오는 단어의 IDF가 **음수**가 되어 별도 하한(epsilon)이 필요하다. `+1`을 넣으면 항상 양수라서 "단어가 맞으면 점수 > 0"이 보장되고, "점수 0인 청크는 뺀다"는 규칙이 단순해진다.

**k1·b를 바꾸면 생기는 일**
- **k1을 올리면** 같은 단어가 여러 번 나올수록 점수가 더 오래 오른다(포화가 늦다). k1=0이면 빈도를 무시하고 "나왔다/안 나왔다"만 본다.
- **b를 올리면** 긴 청크를 더 깎는다. b=1이면 길이로 완전히 나누고, b=0이면 길이를 무시해 단어를 많이 담은 긴 조항이 유리해진다.
- 기본값 k1=1.5·b=0.75는 rank_bm25 기본값(Elasticsearch는 k1=1.2·b=0.75)이다. 조항 단위 청크는 길이 차이가 커서 b의 영향이 크므로 Task 9 평가셋으로 확인할 대상이다.

**역색인(inverted index)**
`build()`에서 단어 → `[(청크 번호, 빈도)]` 목록(postings)을 만든다. 검색 때는 질문 단어가 들어 있는 청크만 계산하므로 청크가 많아져도 빠르다. IDF와 길이 정규화 값(`k1·(1-b+b·|D|/avgdl)`)도 색인할 때 미리 계산한다.

| `Kiwi()`를 모듈에서 한 번 생성 | 호출마다 생성, 지연 생성 | 사전 로딩에 이 PC에서 약 1.2초. 한 번 만든 뒤에는 문장 100개 토큰화가 0.06초 |
| 명사로 태깅된 1음절 조사만 불용어 | 1음절 명사 전부 버리기, 품사 무시하고 형태만 비교 | 전부 버리면 "법·금·원·조"처럼 뜻 있는 1음절 명사까지 사라지고, 형태만 보면 "가서"의 동사 "가"까지 지운다. 대가는 "금과 은"의 "은"(silver)을 잃는 정도 |
| 접근 등급 필터를 **top-k 전에** | 상위 k개를 뽑은 뒤 거르기 | 뒤에서 거르면 권한 밖 청크가 상위를 차지할 때 k개보다 적게(심하면 0개) 나온다. 단, 권한 밖 청크는 **결과에서만** 빠지고 IDF(`N`, `n(q)`)와 `avgdl` 통계에는 그대로 들어간다(아래 한계 참고) |
| `kiwipiepy>=0.24,<0.25` | 버전 고정 안 함 | 불용어 목록, "예금자"를 한 단어로 보는 분석, 테스트의 토큰 수가 모두 Kiwi 0.24 분석 결과에 기대고 있다. 새 버전이 코드 변경 없이 CI나 검색 품질을 바꾸지 않게 상한을 둔다 |
| `access_levels=None`은 필터 없음, `[]`는 결과 없음 | `[]`도 필터 없음으로 취급 | 권한 목록이 비었는데 전부 보여 주면 위험하다. 비었으면 아무것도 안 보이는 쪽(fail closed)이 안전하다 |
| 동점은 색인 순서로 정렬 | 정렬 기준 없음 | 같은 질문에 항상 같은 순서 → 평가 결과가 재현된다 |

**알려진 한계** (다음 작업에서 다룸)
- 복합명사: Kiwi는 "예금자"를 한 단어로 본다. 그래서 질문 "예금 보호"는 "예금자 보호" 청크의 "예금자"와 맞지 않는다. 분석도 일관되지 않다("예금자보호법" → 보호/법, "개인정보보호법" → 보호법). 워크스페이스 용어 사전, dense 검색과의 하이브리드(Task 5)로 보완한다.
- 권한 밖 청크도 통계에 들어간다: 공개 청크 3개에 "대출"이 든 내부 청크 2개를 더하면, `access_levels=["public"]`로 검색해도 공개 청크의 "대출" 점수가 0.981 → 0.569로 바뀐다(직접 측정). 점수를 사용자에게 보여 주면 "내 권한 밖에 이 단어가 든 문서가 있다"를 짐작할 수 있다(위험은 낮다고 보지만 추측). 막으려면 등급별로 색인이나 통계를 따로 둔다.
- `access_levels=None`은 **필터 없음(fail open)** 이 기본값이다. 사용자 요청을 처리하는 하이브리드 검색(Task 5)과 API(Task 10)는 항상 등급 목록을 명시해서 넘겨야 한다.
- 조사만 있는 질문 중 아직 토큰이 남는 경우: `"까지?"` → `까/VV`, `"보다?"` → `보/VV`, `"랑?"` → `랑/NNP`, `"는요?"` → `늘/VV`, `"만?"` → `만/NR`, 물음표 없는 `"도"` → `도/NNG`. 동사·수사를 형태만 보고 지우면 내용어가 사라지므로 두었다. 이런 질문은 BM25 결과가 엉뚱할 수 있으니 하이브리드(Task 5)에서 dense 결과로 보완한다.
- `W_SERIAL`은 문서와 질문의 표기가 같을 때만 맞는다: `2024.01.01`과 "2024년 1월 1일"(`2024`·`년`·`1`·`월`…)은 서로 안 맞는다. 금액·날짜 질문 성능은 Task 9 평가셋에서 확인한다.
- 색인은 메모리에만 있다. 저장·재시작 때 다시 만드는 일은 API 작업(Task 10)에서 정한다.

## 코드 읽는 순서

1. `src/axbuilder/models.py` — `Chunk`, `ScoredChunk`
2. `src/axbuilder/retrieval/tokenizer.py` — 태그 접두 목록 → 불용어 → `tokenize()`
3. `src/axbuilder/retrieval/bm25.py` — `build()`(토큰화 → postings → IDF → 길이 정규화) → `search()`(점수 합산 → 권한 필터 → 정렬 → 상위 k)
4. `tests/retrieval/test_tokenizer.py`, `tests/retrieval/test_bm25.py` — 특히 `test_score_matches_formula`(손으로 계산한 값과 비교)와 `test_b_controls_length_normalization`(b=0이면 길이 무시)

## 면접 예상 질문과 답

**Q1. 한국어 BM25에 왜 형태소 분석이 필요한가요?**
한국어는 조사·어미가 붙어서 공백으로 자르면 "한도는"과 "한도"가 다른 단어가 됩니다. 색인과 질문을 같은 형태소 분석기로 나누고 조사·어미를 버려야 키워드가 맞습니다. 동사도 원형("따른" → "따르")으로 바뀌어 활용형이 달라도 맞습니다.

**Q2. TF-IDF와 BM25는 뭐가 다른가요?**
BM25는 단어 빈도가 늘어도 점수가 일정 수준에서 포화되고(k1), 문서 길이를 평균과 비교해 정규화합니다(b). 그래서 같은 단어를 반복한 문서나 아주 긴 문서가 부당하게 상위로 오는 것을 막습니다.

**Q3. k1과 b를 바꾸면 어떻게 되나요?**
k1이 크면 빈도가 많을수록 계속 점수가 오르고, 0이면 단어가 있는지만 봅니다. b가 1에 가까우면 긴 문서를 많이 깎고, 0이면 길이를 무시합니다. 기본값을 쓰되, 조항 길이 편차가 큰 코퍼스라서 평가셋으로 b를 확인할 계획입니다.

**Q4. "은?" 같은 질문에서 무엇이 문제였나요?**
품사 필터만 쓰면 Kiwi가 문맥 없는 "은"을 명사(silver)로 읽어서 토큰이 남았습니다. 실제로 돌려 보고 발견했고, 명사로 태깅된 단독 조사 형태만 불용어로 버려서 빈 결과를 돌려주게 했습니다. 처음엔 품사와 상관없이 형태만 비교했는데, 그러면 "30도"의 의존명사 "도"나 "가서"의 동사 "가"까지 지워져서 명사 태그일 때만 적용하도록 좁혔습니다. 하이브리드 검색에서는 BM25가 비면 dense 결과만으로 답합니다.

**Q5. 라이브러리 대신 직접 구현한 이유와 검증 방법은?**
식을 설명할 수 있고, 권한 필터를 순위 계산 단계에 넣기 위해서입니다. 검증은 작은 예제에서 손으로 계산한 점수와 `pytest.approx`로 비교하고, b=0일 때 길이가 다른 두 청크의 점수가 같아지는지로 길이 정규화를 확인했습니다.
