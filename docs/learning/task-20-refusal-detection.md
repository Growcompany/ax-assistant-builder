# Task 20 — 바꿔 말한 거절 판정

## 이 작업이 하는 일

- 문제: `answer()`는 모델의 답이 정해진 문구(`제공된 자료로는 확인할 수 없습니다.`)로 시작할 때만 거절로 봤다. 그런데 작은 모델(qwen3.5:4b)은 "제공된 자료로는 달러 환율을 확인할 수 없습니다."처럼 **문구를 바꿔** 거절한다. 그러면 (1) 평가에서 거절이 답변으로 세어지고(범위 밖 6문항 중 2개만 거절로 잡혀 0.333), (2) 화면에는 거절인데 무관한 인용이 붙어 나간다.
- 한 일:
  - `src/axbuilder/generation/refusal.py`: `classify_refusal(text) -> RefusalKind`. `EXACT`(정해진 문구, 기존 규칙 그대로) / `PARAPHRASE`(문구를 바꾼 거절) / `NONE`(답변, 부분 답변).
  - `answer()`: `PARAPHRASE`도 `EXACT`처럼 `refused=True`, 정해진 문구, 인용 없음으로 정규화한다. 모델이 쓴 원래 문장은 `Answer.llm.text`에 남는다. `Answer.refusal_kind`를 더했다. API 응답 모양은 그대로다.
  - 평가: 문항 기록에 `refusal_kind`, `raw_answer`, 요약에 `refusal_accuracy_strict`(EXACT만 거절로 센 예전 방식)를 더했다.
  - `scripts/rescore_refusals.py`: 저장된 보고서를 새 규칙으로 다시 채점해 전후 표를 낸다. 모델을 다시 돌리지 않는다.
  - `tests/fixtures/refusal_outputs.jsonl`: 실제 모델 출력 150개와 정답 라벨. `docs/eval/refusal-labels.md`에 라벨 기준.
- 결과(`docs/experiments/2026-11-11-refusal-detection.md`): 150개에서 정밀도 1.000(34/34), 재현율 0.829(34/41). 범위 밖 거절은 2/6 → 6/6, 2/6 → 6/6, 4/6 → 5/6. 전체 거절 정확도는 거의 그대로(0.860 → 0.880, 0.860 → 0.860, 0.900 → 0.900)인데, 그 이유가 이 작업에서 가장 배울 만한 부분이다(아래).

## 핵심 개념

**정밀도와 재현율 (거절 클래스 기준)**
- 정밀도 = 판정기가 "거절"이라고 한 것 중 진짜 거절의 비율. 낮으면 **정상 답이 거절 문구로 바뀌어 사라진다.**
- 재현율 = 진짜 거절 중 판정기가 잡은 비율. 낮으면 **거절인데 모델 원문과 인용이 그대로 나간다.**
- 두 실수의 값이 다르다. 답을 지우는 쪽이 훨씬 나쁘다. 그래서 정밀도를 먼저 지키고 재현율은 되는 만큼만 올렸다.

**문장 단위 규칙**
답을 문장으로 나눠 **모든 문장이 "없음 서술"** 일 때만 PARAPHRASE다. 문장 하나가 없음 서술이려면:
1. 끝 서술어가 정해 둔 꼴이다: `확인/답변/판단할 수 없`, `…하기 어렵`, `포함/명시/언급/기재되어 있지 않`, `다루고 있지 않`, `정보/내용/규정/근거/자료 … 없`.
2. 숫자가 없다(인용 표시 `[1]` 제외).
3. "…지만/…으나"로 꺾이면 앞 절이 자료 설명(`…을 다루고 있으나`)이다.

그리고 첫 문장이 `자료`나 `문서`를 가리켜야 한다.

- 어간을 `확인/답변/판단`으로 묶은 이유: "…할 수 없습니다"를 다 받으면 "만기 전에는 **중도해지할 수 없습니다** [1]"라는 정답이 거절이 된다.
- 숫자를 막은 이유: "[1]에는 연체이자율이 연 3%p라고 명시되어 있지만 … 은 언급되지 않았습니다"는 거절 이유처럼 생겼지만 3%p가 질문 절반의 답이었다. 판정기는 질문을 보지 않으므로 그 수치가 답인지 알 수 없다. 모르면 답변 쪽에 둔다.

**라벨을 먼저, 규칙은 나중에**
출력 150개를 읽고 `refusal / answer / partial` 라벨을 먼저 확정해 커밋한 뒤 판정기를 만들었다. 순서가 반대면 "규칙이 틀린 항목"을 볼 때마다 라벨을 규칙 쪽으로 고치고 싶어지고, 그러면 정밀도는 규칙이 자기 자신을 채점한 숫자가 된다.

**다듬기 묶음과 검증 묶음**
150개 중 실행 2개(100개)로 규칙을 다듬고, 나머지 실행 1개(50개)는 규칙을 확정한 뒤 한 번만 쟀다. 머신러닝의 train/test 분리와 같은 생각이다. 규칙도 데이터를 보고 만들면 그 데이터에 과적합된다.
- 결과: 정밀도는 둘 다 1.000, 재현율은 0.893 → 0.692. 놓친 것은 "찾을 수 없습니다", "담고 있지 않습니다", "답변**을** 할 수 없습니다"처럼 다듬기 묶음에 없던 표현이다.
- 검증 묶음을 보고 그 표현을 규칙에 넣으면 숫자는 오르지만, 그 숫자는 더 이상 "처음 보는 출력에서의 성능"이 아니다. 그래서 넣지 않고 다음 실험으로 남겼다.

**지표가 숨기고 있던 것**
거절 정확도는 `거절했나 == 범위 밖 질문인가`다. 검색이 근거를 못 가져온 5문항에서 모델이 "자료에 없다"고 한 것은 받은 자료로는 옳은 행동인데 이 지표로는 오답이다. 예전 판정은 그 거절들을 못 알아봐서 "답했다"로 세었고, 그래서 우연히 정답 처리가 됐다. 기준선 실행에서 새 판정은 범위 밖 4문항을 되찾고 검색 실패 4문항을 잃어 전체가 0.860 → 0.860이다. **평균 하나가 같아도 안에서는 8문항이 뒤집혔다.** 그래서 실험 기록은 평균이 아니라 qtype별 값과 뒤집힌 문항 번호를 적는다.

## 왜 이렇게 했나 (대안과 비교)

- **규칙 vs LLM-judge**: 거절 판정은 `/ask` 요청마다 도는 코드다. LLM을 한 번 더 부르면 요청마다 LLM 호출 한 번만큼 응답이 늦어지고, 판정이 실행마다 달라지고, 판정기 자체를 다시 사람이 보정해야 한다. 규칙은 0ms에 가깝고, 같은 입력에 늘 같은 답을 내고, 왜 그렇게 판정했는지 문장 단위로 설명할 수 있다. 대신 표현이 바뀌면 놓친다(재현율 0.692).
- **구조화 출력(`{"refused": true}`) vs 규칙**: 모델이 스스로 표시하게 하는 편이 더 근본적이다. 하지만 프롬프트를 바꾸면 답변 전체가 달라져 "판정만 바꾼 효과"를 따로 볼 수 없다. 이번에는 변수 하나만 바꾸려고 판정 규칙만 건드렸고, 프롬프트는 다음 실험이다.
- **"거절 문구가 어디든 있으면 거절" vs 문장 전부 검사**: 앞의 것은 "일반 예금은 1억원까지 보호됩니다 [1]. 퇴직연금 한도는 제공된 자료로는 확인할 수 없습니다."(부분 답변)를 지운다. 기준선 문서가 "앞에서 망설이고 실제로 답한 문항"으로 꼽은 012, 024, 039, 042도 위험하다. 그래서 모든 문장이 없음 서술이어야 한다는 조건을 걸었다.
- **PARAPHRASE도 정해진 문구로 바꾼다**: 바꾸지 않으면 거절 이유에 붙은 무관한 인용(기준선 046: 2개)이 근거처럼 화면에 나간다. 대신 "자료에는 정기예금만 있습니다" 같은 설명도 사라진다. 원문은 `llm.text`와 `raw_answer`에 남겨 디버깅과 재채점에 쓴다.
- **`refusal_accuracy`의 뜻을 바꾸고 `_strict`를 따로 둔다**: 예전 보고서와 이어서 볼 수 있게, 예전 방식의 값을 같은 보고서에 함께 남긴다. 새 보고서 하나만 봐도 전후 차이가 보인다.
- **API에는 `refusal_kind`를 내보내지 않는다**: 계획의 제약(필드 추가 없음)이다. `AskResponse`는 `Answer`에서 필드를 하나씩 골라 만들기 때문에 `Answer`에 필드를 더해도 새지 않는다. 테스트로 응답의 키 집합을 확인했다.

## 코드 읽는 순서

1. `docs/eval/refusal-labels.md` — 라벨 기준과 경계 사례. 무엇을 거절로 보는지부터.
2. `src/axbuilder/generation/refusal.py` — 위에서 아래로: `_is_exact`(기존 규칙) → 정규식 주석 → `_sentences` → `_is_absence_statement` → `_is_paraphrase` → `classify_refusal`.
3. `tests/generation/test_refusal.py` — EXACT 목록, 기준선의 실제 거절 4건, NONE이어야 하는 문장들(부분 답변, "…할 수 없습니다"가 정답), fixture 정밀도 단언.
4. `src/axbuilder/generation/answer.py`의 `answer()` — `classify_refusal` 호출과 정규화.
5. `src/axbuilder/eval/run.py`의 `_record`, `_SUMMARY_KEYS`, `format_markdown` — 더한 줄만.
6. `scripts/rescore_refusals.py` — `rescore`(문항별 전후) → `format_rescore`(표).
7. `docs/experiments/2026-11-11-refusal-detection.md` — 수치, 틀린 판정 7개, 한계.

## 면접 예상 질문과 답

**Q1. 왜 LLM-judge가 아니라 규칙으로 거절을 판정했나요?**
거절 판정이 평가에서만이 아니라 서비스의 요청 경로에서 돌기 때문입니다. LLM을 한 번 더 부르면 응답마다 지연과 비용이 늘고, 같은 답에 판정이 달라질 수 있고, 판정용 LLM이 맞는지를 또 검증해야 합니다. 규칙은 결정적이고 왜 그렇게 판정했는지 문장 단위로 설명됩니다. 대신 표현이 조금만 달라져도 놓칩니다. 실제로 규칙을 만들 때 안 쓴 출력 50개에서는 재현율이 0.893에서 0.692로 내려갔습니다. 그래서 "이 모델과 이 프롬프트에서 검증한 규칙"이라고 문서에 적었고, 모델을 바꾸면 라벨 단 출력으로 다시 재야 합니다. 더 근본적인 방법은 모델이 구조화된 출력으로 거절을 직접 표시하게 하는 것이고 다음 실험으로 잡아 두었습니다.

**Q2. 정밀도를 재현율보다 우선한 이유는요?**
두 실수의 피해가 다르기 때문입니다. 판정기가 정상 답을 거절로 잘못 보면 사용자는 답을 통째로 잃고 "확인할 수 없습니다"만 봅니다. 반대로 거절을 놓치면 모델이 쓴 거절 문장이 그대로 나갈 뿐입니다. 내용은 여전히 "자료에 없다"입니다. 그래서 애매하면 답변으로 두었습니다. 예를 들어 거절 이유 안에 숫자가 있으면 그 숫자가 질문의 답일 수 있어서 거절로 보지 않습니다. 그 결과 150개에서 거절로 판정한 34개는 모두 진짜 거절이었고, 진짜 거절 41개 중 7개는 놓쳤습니다. 다만 34개에서 오탐 0개라는 것이 오탐률 0을 뜻하지는 않습니다. 95% 상한으로는 9% 정도까지 열려 있습니다.

**Q3. "같은 출력으로 전후를 비교했다"는 게 무슨 뜻이고 왜 중요한가요?**
로컬 LLM은 같은 질문에도 실행마다 답이 달라집니다. 같은 설정으로 세 번 돌린 실행에서 예전 규칙이 잡은 범위 밖 거절은 2/6, 2/6, 4/6으로 달랐습니다. 판정 규칙을 바꾸고 모델을 다시 돌려 비교하면, 숫자가 달라진 것이 규칙 때문인지 샘플링 때문인지 가를 수 없습니다. 그래서 이미 저장된 모델 출력 150개를 그대로 두고 판정 규칙만 예전 것과 새 것으로 바꿔 채점했습니다. 이러면 차이는 전부 규칙 때문입니다. 저장된 답이 예전 규칙으로 한 번 가공된 텍스트라는 점이 걸려서, 가공 전 원문으로도 판정해 150개 모두 결과가 같다는 것을 확인했습니다.

**Q4. 판정을 고쳤는데 전체 거절 정확도는 왜 그대로인가요?**
지표의 정의가 "범위 밖이면 거절, 아니면 답변이 정답"이기 때문입니다. 검색이 근거를 못 가져온 문항에서 모델이 "자료에 없다"고 한 것은 옳은 행동인데 이 지표에서는 오답입니다. 예전 판정은 그 거절을 못 알아봐서 답변으로 세었고 우연히 정답이 됐습니다. 기준선 실행에서 새 판정은 범위 밖 4문항을 맞게 고치고, 검색 실패 문항 4개를 오답으로 드러냈습니다. 합이 같아 보일 뿐 8문항이 뒤집혔습니다. 여기서 배운 것은 평균만 보면 안 되고 문항 번호로 봐야 한다는 것, 그리고 거절 지표를 "근거를 받고도 거절"과 "근거가 없어서 거절"로 나눠야 한다는 것입니다.

**Q5. 이 규칙이 과적합됐는지는 어떻게 알았나요?**
출력 150개를 실행 단위로 나눠 100개로 규칙을 다듬고 50개는 규칙을 확정한 뒤 한 번만 쟀습니다. 정밀도는 양쪽 모두 1.000이었지만 재현율은 0.893에서 0.692로 내려갔습니다. 놓친 것은 "찾을 수 없습니다"처럼 다듬을 때 못 본 표현이었습니다. 한계도 있습니다. 검증용 50개는 같은 질문, 같은 모델의 다른 실행이라 완전히 새로운 데이터가 아니고, 라벨을 달면서 제가(에이전트가) 이미 읽은 출력입니다. 그래서 새 실행으로 다시 재는 것을 다음 실험 첫 번째로 적었습니다.
