# Task 2 — 문서 모델, 로더, 조항 단위 분할

## 이 작업이 하는 일

- `src/axbuilder/models.py`: 문서 쪽 모델인 `Page(number, text)`, `DocMeta`(doc_id·제목·출처·종류·접근 등급·시행일), `Document(meta, workspace_id, pages)`를 정의합니다.
- `src/axbuilder/ingest/loaders.py`: `load_document(path, meta, workspace_id)`는 `.pdf`를 pdfplumber로 읽어 **페이지마다** 텍스트를 뽑고, `.md`·`.txt`는 한 페이지로 읽습니다. 그 밖의 확장자에는 `UnsupportedFileType`을 냅니다.
- `src/axbuilder/ingest/chunking.py`: 검색 단위로 자르는 함수 세 개가 들어 있습니다.
  - `chunk_by_article(doc)` — 줄 맨 앞의 `제N조`/`제N조의M`부터 다음 조항 머리 앞까지를 한 청크로 만듭니다.
  - `chunk_fixed(doc, size=800, overlap=100)` — 800자 창을 700자씩 밀며 자릅니다. 이웃한 청크는 100자를 공유합니다.
  - `chunk_document(doc)` — 조항 머리가 2개 이상이면 조항 단위로, 아니면 고정 길이로 자릅니다. `doc_type`은 보지 않습니다. Task 2에서는 법령·규정·약관일 때만 조항 단위였는데, Task 3에서 바꿨습니다. 가상 내부 지침처럼 법령이 아니어도 `제N조` 형식인 문서가 있기 때문입니다.

```
파일 ──load_document──▶ Document(pages=[Page(1, "..."), Page(2, "...")])
                              │ 빈 페이지 빼고 "\n"으로 이음, 위치→페이지 번호 표 유지
                              ▼
        chunk_document ──▶ [Chunk("law-1::0000", article="제1조", page=1), ...]
```

## 핵심 개념

**PDF 텍스트 추출의 한계**
PDF는 "이 좌표에 이 글자를 그려라"라는 명령의 모음이라서 문단·표·머리말 같은 구조 정보가 없습니다. pdfplumber(pdfminer.six 기반)는 글자 좌표를 줄 단위로 모아 텍스트를 만듭니다. 그래서 다음과 같은 문제가 생깁니다. 직접 만든 2쪽짜리 한글 PDF로 확인했고, 자세한 내용은 PR 설명에 있습니다.

| 문제 | 실제로 본 것 | 영향 |
|---|---|---|
| 머리말·꼬리말 반복 | 쪽마다 "날짜 + 문서 제목", "URL 1/2"가 본문에 섞임 | 앞 쪽 마지막 조항 청크 끝에 꼬리말과 다음 쪽 머리말이 붙습니다 |
| 단어 중간 줄바꿈 | "예금보험공\n사를", "대\n처하기" | `tokenize`가 `예금보험공사` 대신 `예금·보험·공·사`로 쪼개서 BM25 검색이 맞지 않습니다 |
| 표 | (이번엔 없음) 칸 순서가 줄 단위로 섞임 | 상품설명서 금리표를 묻는 질문에 약해집니다 |
| **스캔본** | 글자가 이미지라 텍스트 층이 없음 → `extract_text()`가 빈 값 | 아래 참고 |

**스캔본 PDF 처리**
글자가 이미지뿐인 PDF에서는 `extract_text()`가 `None`이나 빈 문자열을 돌려줍니다. 이번 작업에서는 이렇게 처리합니다. (1) 페이지는 그대로 남겨 번호를 유지합니다. (2) 문서 전체에 글자가 없으면 경고 로그(`no extractable text … (scanned PDF?)`)를 남깁니다. (3) 분할할 때 빈 페이지를 건너뛰어 **빈 청크를 색인하지 않습니다**(Review Focus 1). 글자를 실제로 살리려면 OCR이 필요합니다. 후보는 조사 문서(`docs/research/04-rag-trends-stack.md`)에 정리한 OpenDataLoader PDF, Docling(기본 OCR에 한글 없음), Upstage Document Parse(API)이고, 다음 마일스톤에서 파서 2종을 비교해 고릅니다.

**조·항·호 구조**
한국 법령과 약관은 `제2조(정의) ① … 1. …`처럼 조(條) > 항(①②) > 호(1. 2.)로 짜여 있습니다. 질문 하나의 근거는 대개 **조 하나** 안에 있고, 답변의 인용도 "예금자보호법 제2조의2"처럼 조 단위입니다. 그래서 조를 청크 경계로 삼으면 인용 단위와 검색 단위가 같아집니다. `제2조의2`는 개정 때 끼워 넣은 조라서 `(의\d+)?`까지 머리로 봅니다.

**고정 길이 분할과 겹침(overlap)**
구조가 없는 문서(상품설명서, 내부 메모)는 글자 수로 자릅니다. 경계에 걸친 문장이 양쪽 청크 어디에서도 온전하지 않은 문제를 줄이려고, 앞 청크 끝의 `overlap`자를 다음 청크 앞에 다시 넣습니다. 창의 시작 위치는 `0, 700, 1400, …`(`size - overlap`씩)이고, 창이 문서 끝에 닿으면 멈춥니다. 멈추지 않으면 마지막 창이 앞 창의 겹침 부분만 담은 중복 청크가 됩니다. 예를 들어 250자 문서를 크기 100자, 겹침 20자로 자르면 3개가 맞고, 4개가 나오면 틀린 것입니다.

## 왜 이렇게 했나 (대안과 비교)

| 결정 | 대안 | 고른 이유 |
|---|---|---|
| 법령·규정·약관은 조항 단위 | 모든 문서를 고정 길이 | 고정 길이로 자르면 한 조항이 둘로 나뉘거나 두 조항이 섞입니다. 그러면 "제2조의2" 질문의 근거가 두 청크에 흩어지고 인용 조항도 모호해집니다. 조항 단위로 자르면 `Chunk.article`을 그대로 인용에 쓸 수 있습니다 |
| 조항 머리가 2개 이상일 때만 조항 단위 | `doc_type`만 보고 결정 | 약관으로 등록했지만 조항이 없는 문서나 스캔본을 조항 단위로 자르면 문서 전체가 한 덩어리가 됩니다. 그럴 때는 고정 길이가 낫습니다 |
| 머리 뒤가 공백·괄호·줄 끝일 때만 머리 | 계획 그대로 `^제\d+조(의\d+)?` | PDF 줄바꿈 때문에 "제3조에 따른", "제3조제1항", "제2조의 규정"이 줄 맨 앞에 올 수 있습니다. 계획의 정규식을 그대로 쓰면 조항 중간이 잘립니다. `제3조 삭제`(공백), `제1조 (목적)`도 머리로 잡습니다 |
| 첫 조항 앞 글을 `article=None` 청크로 남김 | 버림, 제1조에 붙임 | 이 부분에는 법 이름·시행일·법률 번호가 들어 있어서 "언제 시행됐나" 같은 질문의 근거가 됩니다. 제1조에 붙이면 제1조 청크가 오염됩니다 |
| 청크 `page` = 조항 머리(고정 길이는 청크 첫 글자)가 나온 쪽 | 쪽마다 따로 자르기 | 조항이 쪽을 넘어가도 한 청크로 유지합니다. 인용에는 "몇 쪽에서 시작하는지"만 있으면 충분합니다 |
| 고정 길이는 글자 수, 자른 그대로(strip 안 함) | 토큰 수, 문장 경계에서 자르기(LangChain `RecursiveCharacterTextSplitter`) | 특정 토크나이저에 의존하지 않고, 겹침이 정확히 `overlap`자로 보장됩니다. 문장 경계 분할이 더 자연스럽지만 계획 범위 밖이라 Task 9 ablation의 비교 대상으로 남깁니다. 청크 크기와 겹침이 정확도에 영향을 준다는 보고(Chroma 청킹 평가)가 있어서 값은 평가셋으로 정합니다 |
| 텍스트 파일은 UTF-8 → 실패하면 CP949 | UTF-8만 | 공공기관의 한글 텍스트는 CP949인 경우가 많습니다. 그냥 두면 `UnicodeDecodeError`가 나서 업로드가 실패합니다 |
| 유니코드 NFC 정규화 | 정규화 안 함, NFKC | 맥에서 만든 파일 같은 경우 한글이 자모 단위(NFD)로 저장되어 있어서, 화면에서는 같아 보여도 "보호"로 검색하면 맞지 않습니다. NFKC는 항 번호 `①`을 `1`로 바꿔 조·항 구조를 망가뜨립니다 |
| 테스트 PDF를 테스트 안에서 바이트로 생성 | 저장소에 PDF 파일 커밋 | 바이너리 파일 없이 한글, 페이지 번호, 스캔본(텍스트 층 없는 페이지)을 모두 검증합니다. 글꼴 파일 없이 ToUnicode CMap만으로 글자를 되돌립니다 |

**알려진 한계** (다음 작업·마일스톤에서 다룸)
- 머리말·꼬리말을 지우지 않고, 단어 중간 줄바꿈도 복원하지 않습니다(위 표). "여러 쪽에 반복되는 첫·끝 줄 제거"와 "한글-한글 사이 줄바꿈 잇기"는 조항 머리 줄을 망가뜨리지 않게 설계해야 해서 파서를 비교할 때 함께 다룹니다.
- 조항이 아주 길어도 더 자르지 않습니다. 목차 페이지의 `제1조(목적) …… 1` 줄도 조항 머리로 잡혀서 작은 중복 청크가 생깁니다.
- (Task 3에서 해결) Task 2에서는 부칙의 `제1조(시행일)`처럼 같은 조 번호가 다시 나오면 `article`이 본문과 겹쳤습니다. 지금은 부칙 머리 줄 뒤의 조항에 `부칙 제N조` 라벨을 붙여 본문 조항과 구분합니다. 다만 법령은 개정할 때마다 부칙이 생기기 때문에 `부칙 제1조`끼리는 한 문서 안에서도 겹치는 한계가 남아 있습니다([Task 3 학습 노트](task-03-workspace-corpus.md)).
- 장·절 제목(`제2장 예금보험공사`)은 앞 조항 청크 끝에 붙습니다.
- 표는 줄 단위 텍스트로만 나옵니다. 암호화되거나 손상된 PDF는 pdfplumber 예외가 그대로 올라갑니다(API에서 처리, Task 10).

## 면접 예상 질문과 답

**Q1. 왜 고정 길이가 아니라 조항 단위로 잘랐나요?**
은행 상담 질문의 근거는 대부분 약관이나 법령의 조 하나에 들어 있고, 답변도 "제2조의2"처럼 조 단위로 인용해야 합니다. 고정 길이로 자르면 조항 중간이 잘리거나 두 조항이 섞여서 근거가 흩어지고 인용이 모호해집니다. 그래서 조항 단위로 잘랐고, 조항이 없는 상품설명서는 고정 길이로 자릅니다. 어느 쪽이 나은지는 평가셋 ablation으로 수치를 내서 확인합니다.

**Q2. 겹침(overlap)은 왜 두고, 얼마나 두나요?**
경계에 걸친 문장이 두 청크 어느 쪽에서도 온전하지 않으면 검색이 안 되기 때문에, 앞 청크 끝 일부를 다음 청크에 다시 넣었습니다. 대가는 색인이 커지고 같은 내용이 결과에 중복으로 나온다는 점입니다. 기본값은 800자/100자로 두었고, 크기와 겹침이 정확도에 영향을 준다는 보고가 있어서 Task 9 평가셋으로 정하기로 했습니다.

**Q3. 스캔본 PDF가 들어오면 어떻게 되나요?**
텍스트 층이 없어서 추출 결과가 빈 문자열입니다. 빈 청크를 색인하면 검색 결과에 빈 근거가 섞이므로, 분할 단계에서 빈 페이지를 건너뛰어 청크를 0개로 만들고 로더가 "스캔본일 수 있다"는 경고를 남기게 했습니다. 페이지 번호는 유지해서 나중에 OCR을 붙였을 때 인용 쪽 번호가 원문과 맞도록 했습니다. OCR은 한글을 지원하는지 보고 파서 2종을 비교해서 다음 마일스톤에 붙일 계획입니다.

**Q4. 조항 머리 정규식에서 신경 쓴 점은?**
PDF는 화면 폭에서 줄을 바꾸기 때문에 "제3조에 따른" 같은 다른 조항 언급이 줄 맨 앞에 올 수 있습니다. 그래서 머리 바로 뒤가 공백·괄호·줄 끝일 때만 머리로 보도록 해서 이런 경우를 걸렀고, 개정으로 끼워 넣은 `제2조의2`와 삭제 조항 `제3조 삭제`도 잡히게 했습니다. 각 경우는 테스트로 고정했습니다.

**Q5. PDF 테스트는 어떻게 했나요?**
바이너리를 저장소에 넣지 않으려고 테스트 안에서 최소 PDF를 바이트로 만들었습니다. 글꼴 파일 없이 글자 코드를 유니코드 값으로 쓰고 ToUnicode 표로 되돌리게 했습니다. 이렇게 해서 pdfplumber가 한글을 그대로 읽는지, 페이지 번호가 맞는지, 텍스트 없는 페이지(스캔본 상태)에서 청크가 0개인지를 확인했습니다. 이와 별도로 Edge로 만든 실제 한글 PDF에서는 머리말 반복과 단어 중간 줄바꿈 문제를 발견해서 다음 단계 과제로 남겼습니다.
