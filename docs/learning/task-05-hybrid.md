# Task 5 — RRF 하이브리드 검색

> 2026-11 수정: 리뷰 지적 반영 — Qdrant RRF의 순위 기준(0부터), `fsum`을 쓰는 이유, "합의 먼저" 성질의 조건(n = max(candidates, k)), 하이브리드가 나아진 문항.

## 이 작업이 하는 일

- `src/axbuilder/retrieval/hybrid.py`에 세 가지가 들어 있다.
  - `Retriever` 프로토콜: `search(query, k, access_levels) -> list[ScoredChunk]`. `BM25Index`, `DenseIndex`, `HybridRetriever`가 모두 이 모양이다. 그래서 답변 생성(Task 7)·평가(Task 9)는 검색기를 갈아 끼우기만 하면 된다.
  - `rrf_fuse(rankings, k=60, top_n=10)`: 순위 목록 여러 개를 RRF로 합친다. 라이브러리 없이 직접 구현했다.
  - `HybridRetriever(bm25, dense, candidates=30)`: BM25와 dense에서 각각 후보 30개를 받아 `rrf_fuse`로 합치고 상위 k개를 돌려준다.

```
질문 ─┬─ BM25Index.search(k=30, 권한 필터) ──▶ [c7, c2, c9, …]  (점수 0~수십)
      └─ DenseIndex.search(k=30, 권한 필터) ─▶ [c2, c4, c7, …]  (코사인 -1~1)
                                                  │ 점수는 버리고 순위만
                                           rrf_fuse(k=60) ─▶ 상위 k개
```

## 핵심 개념

**RRF 공식과 k의 의미**

```
RRF(d) = Σ_목록 1 / (k + rank_목록(d))      rank는 1부터, d가 없는 목록은 0을 더한다
```

- 계획의 테스트: `[a, b, c]`와 `[b, c, a]`를 합치면 b가 1위다. b는 2위·1위라 `1/62 + 1/61`이고, a는 1위·3위라 `1/61 + 1/63`이다. 한쪽 1위보다 **양쪽 모두 상위**가 이긴다.
- **k는 순위에 따른 몫이 얼마나 빨리 줄어드는지 정한다.** 1위와 10위의 몫을 비교해 보면 다음과 같다.

| k | 1위 몫 | 10위 몫 | 1위 ÷ 10위 |
|---|---|---|---|
| 0 | 1.000 | 0.100 | 10배 |
| 2 | 0.333 | 0.083 | 4배 |
| 60 (이 구현) | 0.0164 | 0.0143 | 1.15배 |

- 위 표는 이 구현의 공식(순위 1부터)에 k를 넣은 값이다. **Qdrant 내장 RRF는 순위를 0부터 센다.** 설치된 qdrant-client 1.20.0의 `hybrid/fusion.py`는 `1 / ((pos + 1) / w + k - 1)`이고 `pos`가 0부터라서, 가중치가 1이면 점수가 `1/(k + rank - 1)`이다. 로컬 모드로 직접 재 보니 양쪽 1위인 점의 점수가 기본값(`FusionQuery(RRF)`)에서 1.0(= 1/2 + 1/2), `Rrf(k=60)`에서 0.033333(= 2/60)이었다. 이 구현의 k=60이면 2/61 = 0.032787이다.
- 그래서 Qdrant 기본값 k=2는 이 공식의 k=1과 같다(1위 0.5, 10위 0.091, 5.5배). 이 구현과 같은 점수를 Qdrant로 내려면 `Rrf(k=61)`을 줘야 한다(로컬 모드에서 0.032787로 같음을 확인).

- k가 작으면 "한 검색기의 1위"가 결과를 좌우한다. k가 크면 순위 차이가 평평해져서 "몇 개의 목록에 나왔는가"가 더 중요해진다. 테스트 `test_rrf_k_controls_how_fast_rank_weight_drops`가 이 차이를 보인다. 한쪽 1위인 a와 양쪽 3위인 b가 있을 때, k=0이면 a가 앞서고(1/1 > 1/3+1/3) k=60이면 b가 앞선다.
- 60은 RRF 논문(Cormack 외, SIGIR 2009)이 실험으로 고른 값이다. Qdrant 내장 RRF는 기본값이 2이고 순위를 0부터 세므로, Qdrant 결합으로 바꾸면 `k=60`이 아니라 `Rrf(k=61)`을 명시해야 같은 점수가 나온다(`docs/research/11`).

**점수 정규화 대신 순위를 합치는 이유**
BM25 점수는 0에서 수십까지 나오고, 질문 길이와 단어 희귀도에 따라 범위가 매번 바뀐다. 코사인은 -1~1이지만 실제로는 0.3~0.6 근처에 몰린다. 수동 확인의 예시 질문을 보면 BM25 1위가 14.93, dense 1위가 0.418이었다. 그냥 더하면 BM25가 결과를 독차지한다.
- min-max 정규화(각 목록을 0~1로)는 목록의 최고·최저점에 끌려간다. 1위가 압도적인 목록과 고만고만한 목록이 같은 0~1로 늘어나고, 이상치 하나가 나머지 점수를 전부 바꾼다. 가중치 α도 정해야 하는데 평가셋 없이 정할 근거가 없다.
- RRF는 순위만 쓰므로 척도가 달라도 상관없고 조정할 값도 k 하나다. `test_rrf_ignores_raw_scores`가 이것을 확인한다. 한 목록의 점수를 1000배로 바꿔도 결과가 같다.
- 대가도 있다. 점수 차이 정보(1위가 2위보다 훨씬 확실한 경우)는 버린다.

**후보 수 `candidates`**
각 검색기에서 몇 개를 받아 합칠지 정한다(기본 30). 최종 k(보통 5)보다 넉넉해야 한다. 한쪽에서는 8위, 다른 쪽에서는 2위인 청크처럼 **양쪽에서 중위권인 청크가 합산 기회를 얻으려면** 두 목록에 모두 들어 있어야 하기 때문이다.
- k가 candidates보다 크면 각 검색기에서 k개씩 받는다. 즉 각 검색기에서 받는 수는 `n = max(candidates, k)`이다. 그렇지 않으면 k=50을 요청해도 결과가 후보 수에 묶인다.
- k=60일 때 숨은 성질이 하나 있다. 양쪽에 다 나온 청크의 점수는 최소 `2/(60+n)`이고, 한쪽에만 나온 청크는 최대 `1/61`이다. 따라서 **각 검색기에서 받는 수 n이 61 이하이면 양쪽 모두에 나온 청크가 한쪽에만 나온 청크보다 항상 앞선다.** 하이브리드는 "두 검색기가 합의한 청크 먼저"가 된다. 기본값(candidates=30)에서는 k가 61 이하일 때 성립한다. n=62이면 2/122 = 1/61로 동점이 되고, 그보다 크면 이 성질이 깨진다.
- 권한 필터는 두 검색기 안에서 top-n 전에 건다. 합친 뒤에 거르면 결과가 k보다 모자란다. 등급 목록이 `[]`이면 두 검색기가 모두 빈 결과를 주므로 하이브리드도 빈 결과다(fail closed).

**BM25가 비는 질문 (Review Focus #2)**
"은?"은 형태소 분석 후 남는 토큰이 없어서 BM25가 빈 목록을 준다. RRF는 빈 목록을 그냥 0으로 더하므로 dense 순위가 그대로 결과가 된다. dense에는 점수 하한이 없어서(Task 4) 항상 가장 가까운 청크를 준다. 은행 코퍼스에서 실제로 확인했다. BM25는 `[]`였고, 하이브리드 결과는 dense 상위 3개와 같았다.

## 왜 이렇게 했나 (대안과 비교)

| 결정 | 대안 | 고른 이유 |
|---|---|---|
| RRF 직접 구현 | Qdrant `FusionQuery(RRF)`, ranx | 공식이 한 줄이고, BM25가 Qdrant 밖(직접 구현)에 있어 어차피 파이썬에서 합쳐야 한다. 면접에서 공식과 k를 직접 설명할 수 있다 |
| 순위 결합(RRF) | 점수 정규화 후 가중합 | 척도가 다른 점수를 맞출 필요가 없고 조정할 값이 k 하나다. 가중합의 α는 평가셋으로 정해야 해서 M-2 실험 항목으로 둔다 |
| `math.fsum`으로 합산 | `+=` 누적 | IEEE 754 덧셈은 교환법칙이 성립해서(`a+b == b+a`) 목록이 2개인 지금은 `+`도 순서와 무관하다. 결합법칙은 성립하지 않아 목록이 3개 이상이면 순서에 따라 마지막 자리가 달라진다(예: 1·2·8위 몫을 `(1/61+1/62)+1/68`로 더하면 …652, `(1/68+1/62)+1/61`이면 …651). fsum은 정확히 반올림한 합이라 검색기를 늘려도 같은 순위 조합이면 정확히 동점이 된다 |
| 동점이면 처음 나온 순서(BM25 먼저) | chunk_id 사전순 | 실행마다 같은 순서를 보장하는 것이 목적이다. 안정 정렬이라 추가 코드가 필요 없다 |
| 한 목록 안의 중복은 높은 순위만 | 매번 더하기 | BM25에 같은 chunk_id 청크가 두 번 색인되면 한 청크가 두 몫을 받게 된다 |

**측정: 은행 코퍼스 945청크, 골든셋 v0 중 답이 있는 44문항** (참고용, 정식 평가는 Task 9)

| 검색기 | Recall@5 | Hit@5 | MRR@10 |
|---|---|---|---|
| BM25 | 0.841 | 38/44 | 0.752 |
| dense | 0.886 | 40/44 | **0.886** |
| hybrid (k=60, candidates=30) | 0.886 | 40/44 | 0.828 |

- 이 표(Task 5 시점)에서는 하이브리드의 Recall@5가 dense와 같고, MRR은 dense보다 **낮았다.** **지금 기준선에서는 Recall@5도 낮다**: dense 0.886, hybrid 0.864로 한 문항 차이다(아래 넷째 항목, [실험 기록](../experiments/2026-11-10-baseline.md), [ADR 0002](../adr/0002-hybrid-rrf.md)). "하이브리드가 항상 낫다"는 가정은 틀릴 수 있다.
- dense와 비교하면 첫 정답 순위(top-10 기준)가 **6문항에서 나빠지고 2문항에서 좋아졌다.** 좋아진 문항은 bank-009(dense 7위 → 하이브리드 4위), bank-034(2위 → 1위)다. 나빠진 문항은 bank-004·010·013·029·032·044다.
- 나빠진 원인은 위의 "합의 먼저" 성질이다. 나빠진 6문항을 보면, 하이브리드 1위는 모두 BM25와 dense 양쪽 top-30에 들어 있던 다른 청크였다. bank-029는 dense가 정답을 1위로 찾았지만 BM25 top-30에는 정답이 없었다. 그래서 양쪽에 다 나온 청크 10개 이상에 밀려 하이브리드 top-10 밖으로 떨어졌다.
- 이 표는 Task 5 시점의 코퍼스로 잰 값이다. 골든셋 PR에서 가상 상품설명서 2개의 문장이 고쳐진 뒤의 main으로 다시 재면(2026-11) bank-017(dense 5위 → 하이브리드 6위)도 top-5 밖으로 밀려 하이브리드가 Recall@5 0.864, Hit@5 39/44가 된다(MRR 0.828, BM25·dense 값은 그대로). 문서 몇 줄에도 흔들리는 차이라는 뜻이다.
- candidates를 바꿔 보면 5·10에서 Recall@5 0.898 / MRR 0.832, 30에서 0.886 / 0.828, 100에서 0.886 / 0.831이었다. 차이가 작아 44문항으로는 결론을 내기 어렵다.
- 그래서 기본값은 계획대로 두고, 가중 RRF(dense 쪽 가중치)와 k·candidates 조합은 M-2 ablation에서 150~200문항으로 정한다.

## 코드 읽는 순서

1. `Retriever` 프로토콜 — 세 검색기가 같은 모양이라 무엇이 좋아지는지
2. `rrf_fuse` — k 검사 → 목록마다 `1/(k+rank)` 모으기(중복은 한 번) → `fsum` → 안정 정렬 → `top_n`
3. `HybridRetriever.search` — `max(candidates, k)`개씩 받기, 권한 필터를 두 검색기에 그대로 전달
4. `tests/retrieval/test_hybrid.py` — 계획의 세 테스트, `test_rrf_ignores_raw_scores`, `test_rrf_k_controls_how_fast_rank_weight_drops`, `RecordingRetriever`로 후보 수·필터 전달 확인, `test_hybrid_access_filter`

## 면접 예상 질문과 답

**Q1. BM25 점수와 코사인 유사도를 그냥 더하면 안 되나요?**
척도가 다릅니다. 이 코퍼스에서 BM25 1위 점수는 14.9였고 코사인 1위는 0.42였습니다. 그대로 더하면 BM25가 결과를 정합니다. 정규화하면 각 목록의 최고·최저점에 따라 값이 출렁이고 가중치도 따로 정해야 합니다. RRF는 순위만 보기 때문에 척도 문제가 없고, 조정할 값은 k 하나입니다.

**Q2. RRF의 k=60은 무슨 의미인가요?**
순위가 내려갈 때 몫이 얼마나 빨리 줄어드는지를 정합니다. k=0이면 1위가 10위의 10배, k=60이면 1.15배입니다. k가 크면 한 검색기의 1위보다 여러 검색기에 함께 나온 청크가 유리해집니다. 60은 원 논문의 실험값입니다. Qdrant 내장 RRF는 기본값이 2이고 순위를 0부터 세서 점수가 `1/(k + 순위 - 1)`입니다. 그래서 Qdrant로 바꾸면 k=61을 줘야 이 구현과 같은 점수가 나옵니다. 라이브러리마다 같은 이름의 파라미터라도 공식이 다를 수 있어서 소스와 실제 값으로 확인했습니다.

**Q3. 후보를 각각 30개씩 받는 이유는요?**
최종 5개만 받으면, 한쪽에서는 2위인데 다른 쪽에서는 8위인 청크가 합산 기회를 잃습니다. 넉넉히 받아야 양쪽에서 중위권인 청크가 올라올 수 있습니다. 다만 k=60이고 각 검색기에서 받는 수(`max(candidates, k)`)가 61개 이하이면, 양쪽에 다 나온 청크가 한쪽에만 나온 청크보다 항상 앞섭니다. 이 성질 때문에 실제로 하이브리드 MRR이 dense보다 낮게 나왔고, 후보 수와 가중치는 평가셋으로 정할 실험 항목으로 남겼습니다.

**Q4. 하이브리드가 dense보다 나빴다면 왜 하이브리드를 쓰나요?**
기준선(44문항, k=5)에서 Recall@5는 dense 0.886, 하이브리드 0.864였고 MRR도 dense가 높았습니다(0.880 대 0.824). 다만 Recall@5 차이는 한 문항(약 0.023)이라 순위는 바뀔 수 있습니다. 문항별로 보면 dense가 1위로 찾은 정답을 하이브리드가 놓친 문항(bank-029)도 있고, 반대로 하이브리드만 찾은 문항(bank-009)도 있습니다. 하이브리드는 조문 번호·금액처럼 글자가 정확히 맞아야 하는 질문과, 임베딩 모델이 모르는 신조어·고유명사에 대한 보험입니다. 지금 평가셋은 자연어 질문 위주라 이런 장점이 덜 드러납니다. 그래서 "항상 하이브리드"로 정하지 않고 기본값을 잠정으로 두었습니다. BM25/dense/hybrid를 모두 지표로 비교하는 구조를 만들었고, 가중 RRF와 리랭커는 M-2에서 더 큰 골든셋으로 실험합니다.

**Q5. "은?" 같은 질문은 어떻게 처리되나요?**
형태소 분석 후 내용어가 없어 BM25는 빈 결과를 줍니다. RRF는 빈 목록을 0으로 더하기만 하므로 dense 순위가 그대로 결과가 됩니다. 오류 없이 동작하는지 단위 테스트(`test_hybrid_works_when_bm25_empty`)와 실제 코퍼스 양쪽에서 확인했습니다. 이런 질문을 답할지 거절할지는 검색이 아니라 답변 단계(Task 7)의 근거 판단이 정합니다.
