# Task 12 — 릴리스 뒤 보안 점검 후속

v0.1.0을 낸 뒤 보안 점검 에이전트가 재현한 지적 10개와, 전체 코드 감사에서 나온 정확성 문제 2개(A·B)를 고친 작업입니다. 그 PR(#19)의 1차 리뷰가 찾은 우회 경로(R1~R5)까지 반영했습니다. 계획 문서에 있는 Task가 아니라 릴리스 후속 작업이라, 번호만 이어서 12를 붙였습니다.

## 핵심 개념

**DNS 리바인딩.** 브라우저의 동일 출처 정책은 "스킴 + 호스트 이름 + 포트"가 같은지만 봅니다. IP는 보지 않습니다. 공격자는 먼저 자기 서버에서 `attacker.example` 페이지를 내려 준 뒤, 그 이름의 DNS 응답을 `127.0.0.1`로 바꿉니다. 그러면 페이지의 스크립트가 `http://attacker.example:8000/workspaces/bank/ask`를 부를 때 요청은 내 PC의 서버로 가지만, 브라우저 입장에서는 같은 출처입니다. `Sec-Fetch-Site`는 `same-origin`이 되고, CORS 없이 응답도 읽을 수 있습니다. 기존 방어(`_RejectCrossSite`)는 이 값을 믿기 때문에 요청이 그대로 통과합니다.
이때도 바뀌지 않는 것이 `Host` 머리글입니다. 브라우저는 주소창의 이름(`attacker.example:8000`)을 그대로 보냅니다. 서버가 "내 이름이 아닌 Host"를 거절하면 이 공격을 막을 수 있습니다. 읽기(GET)까지 막는 이유는 리바인딩의 목적이 응답을 읽는 것이기 때문입니다.

**`Origin` 검사를 더한 이유.** `Sec-Fetch-Site`는 비교적 새 머리글입니다(Chrome 76, Firefox 90, Safari 16.4부터). 그 전 브라우저도 POST에는 `Origin`을 붙입니다. 그래서 `Origin`이 있는데 호스트가 허용 목록에 없으면 거절합니다. `Origin: null`(샌드박스 iframe, `file://`)도 거절됩니다.

**"크기"만으로 끝나지 않는 폭탄.** 지금까지 막은 것은 풀어 낸 바이트(압축 폭탄)와 글자 객체 수(글자 폭탄)였습니다. 이번에 찾은 두 가지는 둘 다 0인데도 자원을 썼습니다.
- 쪽 수 폭탄: `pdfplumber`의 `pdf.pages`는 모든 쪽의 `Page` 객체를 한 번에 만듭니다. 내용이 없어도 쪽마다 객체와 시간이 듭니다.
- 요소 수 폭탄: `ElementTree`는 요소마다 객체를 남깁니다. `<hp:p/>`는 7바이트인데 객체는 약 190바이트입니다.
- 리뷰에서 찾은 것들도 같은 종류입니다. 줄바꿈 하나는 1바이트인데 파서는 이것을 조각 하나로 넘깁니다. 속성 하나는 사전 항목 하나가 되고, 선언만 한 객체 번호 하나는 조회 한 번이 됩니다.

공통된 교훈은 두 가지입니다. 첫째, **"입력 크기"가 아니라 "입력이 파서에게 시키는 일의 수"에 상한을 둬야 합니다.** 둘째, **무엇을 세느냐가 곧 구멍이 됩니다.** 요소만 세면 속성과 글자 조각이 빠지고, 이벤트를 세어도 "이벤트가 오기 전에 이미 만들어진 것"(시작 태그 하나의 속성 사전)이 빠집니다. 이번 리뷰에서는 상한을 하나 둘 때마다 바로 옆의 다른 경로가 나왔습니다. 같은 프로세스 안에서 파서 내부를 하나씩 막는 방식의 한계입니다. 근본적인 해결책은 메모리·시간 상한이 있는 별도 프로세스에서 파싱하는 것입니다(M-3).

**스트리밍 파싱.** `xml.etree.ElementTree.XMLParser(target=...)`에 `start`/`end`/`data` 메서드를 가진 객체를 넘기면, 파서는 트리를 만들지 않고 이벤트만 알려 줍니다. `_HwpxParagraphs`가 그 target입니다. 이 객체는 열려 있는 문단의 스택과 "지금 `hp:t` 안에서 몇 단계 깊이인가"만 기억합니다. 글자가 없는 문단은 닫힐 때 바로 버리므로 빈 문단은 메모리를 쓰지 않습니다.

**유니코드 Cf(형식 문자).** `U+202E`(오른쪽에서 왼쪽으로 덮어쓰기)는 뒤 글자를 거꾸로 보이게 합니다. `U+200B`(폭 없는 공백)는 보이지 않습니다. 제목은 인용과 프롬프트에 그대로 들어가므로, 화면에 보이는 제목과 실제 글자가 달라질 수 있습니다. 한글 완성형(Lo), 자모(Lo), 채움 문자 `U+3164`(Lo), 한자, 원문자(No), 결합 문자(Mn)는 Cf가 아니라서 그대로 받습니다. ZWJ(`U+200D`)로 이은 가족 이모지는 함께 막힙니다.

**색인의 "완성 표시".** `index.json`은 색인을 다 만든 뒤에 쓰는 파일이라, 이 파일이 있으면 "Qdrant 안의 점이 온전하다"는 뜻입니다. 그렇다면 이 파일을 지우는 시점은 "점을 바꾸기 시작하는 순간"이어야 합니다. 예전에는 임베딩보다 먼저 지웠습니다. 임베딩은 가장 오래 걸리고, GPU 메모리 부족으로 가장 자주 실패하는 단계입니다. 그래서 임베딩이 실패하면 점은 하나도 바뀌지 않았는데 표시만 사라져서, 잘 되던 색인까지 409가 됐습니다.

**동점과 결정성.** 본문이 같은 청크("제2조 생략" 등, 실제 코퍼스에 54개)는 벡터가 비트 단위까지 같습니다. 그런데 점수는 정확히 같지 않습니다. Qdrant 로컬 모드(numpy 내적)는 같은 벡터라도 저장 위치에 따라 마지막 자리가 다른 점수를 줍니다. 그 차이는 같은 세션 안에서 약 5e-16, 색인한 세션과 다시 연 세션 사이에서 약 4e-8로 측정됐습니다(dim 1024). 저장 위치는 세션마다 다르기 때문에, 묶음 안에서 누가 조금 더 높게 나오는지가 세션마다 바뀝니다. 그래서 서버를 다시 켜면 같은 질문의 인용이 바뀌었습니다. 처음에는 점수를 `==`로 비교하는 방식으로 고쳤다고 했습니다. 하지만 테스트용 `HashEmbedder`의 벡터가 성분이 몇 개뿐인 희소 벡터라서 점수가 달라지지 않았을 뿐이었습니다. 실제 임베딩처럼 촘촘한 난수 벡터로 테스트하니 문제가 그대로 재현됐습니다. **테스트 대역이 실제 입력의 모양을 닮았는지** 확인해야 한다는 교훈입니다.

## 왜 이렇게 했나 (대안과 비교)

- **쪽 수를 세는 방법.** 카탈로그의 `/Count`를 읽는 것이 가장 싸지만, 파일에 적힌 숫자라서 공격자가 1이라고 적을 수 있습니다. 그래서 pdfminer의 쪽 반복자(`PDFPage.create_pages`)를 상한+1개까지만 반복합니다. 이 반복자는 쪽 사전만 읽고 방문한 객체를 기억하므로 순환 참조가 있어도 멈춥니다.
- **거절할 때 `pdf.close()`를 부르지 않는 이유.** pdfplumber의 `close()`는 `self.pages`의 쪽을 하나씩 닫는데, 이때 모든 쪽 객체가 만들어집니다. `with pdfplumber.open(...)`을 그대로 쓰면, 상한을 넘어 예외가 난 뒤 블록을 빠져나가면서 폭탄이 터집니다. "Page 객체를 하나도 만들지 않았다"를 확인하는 테스트가 이 문제를 잡았습니다. 그래서 쪽이 너무 많을 때는 파일 스트림만 닫습니다.
- **HWPX: `iterparse` 대신 target.** `iterparse` + `elem.clear()`도 쓸 수 있지만, 이 방식은 요소 객체를 일단 만듭니다. `hp:t` 하나에 자식 100만 개를 넣으면 `hp:t`가 닫힐 때까지 모두 메모리에 남습니다. target 방식은 요소 객체를 아예 만들지 않습니다. 대신 기존 추출 규칙(가장 가까운 문단에만 붙이기, `hp:t` 바로 아래 글자만 쓰기)을 이벤트 방식으로 다시 써야 했습니다. 그래서 결과가 같은지 따로 확인했습니다. 실제 표준약관 HWPX 두 개의 추출 결과는 수정 전후가 바이트 단위로 같았습니다(19,538바이트와 29,937바이트). 무작위로 만든 XML 4,000개에서도 이전 구현과 결과가 같았습니다.
- **HWPX 상한은 요소가 아니라 파서 이벤트.** 이벤트는 요소 하나에 1 + 속성 수, 글자 조각 하나에 1로 셉니다. 실제 표준약관 두 개는 각각 5,771개(8천 자: 요소 1,115 + 속성 4,532 + 글자 조각 124)와 7,365개(1만 2천 자)입니다. **상한은 본문이 아니라 표가 정합니다.** 처음에는 본문 위주인 이 두 문서만 보고 100만으로 잡았습니다. 그런데 한컴오피스가 쓰는 표는 칸 하나가 이벤트 55개쯤(요소 10 + 속성 44 + 글자 1)이라서, 3,500행 × 6열 금리표 같은 정상 문서가 거절됐습니다(2차 리뷰). 그래서 1,000만(약 18만 칸)으로 올렸습니다. 12만 칸짜리 표가 3.0초·58MB입니다. 상한을 정할 때는 "가진 표본"이 아니라 "그 형식에서 가장 비싼 정상 모양"을 기준으로 측정해야 한다는 교훈입니다. 상한을 올린 대가로 상한 안에서 드는 비용도 커졌습니다. 줄바꿈으로 쪼갠 글자 조각 1,000만 개는 4.9초·191MB로 통과합니다. 이벤트만으로 막을 수 없는 것에는 상한을 따로 두었습니다.
  - 중첩 깊이 200단: 실제 문서는 12단입니다.
  - 구역 1,000개: 실제 문서는 1개입니다.
  - 서로 다른 이름 1만 개: 파서가 처음 보는 이름을 표에 넣고 지우지 않아서, 이름이 모두 다른 요소 100만 개가 257MB를 썼습니다.
  - 이벤트 없이 이어지는 토큰 256KB: 파서는 시작 태그를 끝까지 읽은 뒤에야 속성 사전을 한꺼번에 만들어 넘깁니다. 그래서 속성 80만 개짜리 태그 하나는 이벤트를 세기도 전에 269MB를 씁니다. 읽은 바이트에 비해 이벤트가 멈춰 있으면 긴 토큰을 삼키는 중이라고 봅니다. 64KB 단위로 검사하므로 실제 경계는 320~384KB입니다.

  공백만 있는 글자 조각은 쌓지 않고 공백 하나로 줄입니다. 결과는 같습니다. 수정 뒤에도 실제 HWPX 두 개의 추출 결과는 바이트 단위로 같았고, 무작위 XML 4,000개에서도 이전 구현과 같았습니다.
- **PDF 객체 수: 훑기 전에 선언 확인.** 쪽이 없으면 pdfminer는 xref의 모든 객체 번호를 조회합니다. xref 스트림은 `/Index [0 N]`(없으면 `/Size`)으로 개수만 선언할 수 있어서, 데이터 없이도 N을 마음대로 키울 수 있습니다. 그래서 `check_object_count`가 쪽을 세기 전에 선언된 수를 상한(100만)과 비교합니다. 건너뛰지 않고 거절하는 이유는 pdfplumber의 `pdf.pages`가 같은 훑기를 다시 하기 때문입니다. 같은 이유로 쪽이 0개면 `pdf.pages`를 부르지 않습니다. 100만은 쪽 상한 5,000쪽 × 쪽당 200개로 잡은 값이고, 실제 대형 PDF로 측정한 값은 아닙니다. 상한에 딱 맞춘 187바이트 PDF는 20~34초가 걸립니다. **무엇을 셀지 한 번 잘못 정했습니다.** 처음에는 xref 구획마다 선언한 수를 더하고, 객체 스트림의 `/N`도 같은 예산에서 뺐습니다. 그런데 객체 스트림 안의 객체는 xref에도 한 번씩 적혀 있어서 두 번 세는 셈이었습니다. 실제 한도가 약 50만이 되어, 쪽당 객체 200개짜리 2,600쪽 PDF가 거절됐습니다. 또 증분 저장한 파일은 구획마다 같은 번호를 다시 적기 때문에, 객체 14개짜리 파일이 74개로 집계됐습니다(2차 리뷰). 지금은 서로 다른 객체 번호를 셉니다. xref 스트림의 구간은 합집합으로, 고전 xref 표의 번호는 집합으로 모읍니다. `/N`은 스트림별 상한으로만 씁니다. 다만 서로 다른 번호만 세면 구획을 늘려 훑는 횟수를 키울 수 있으므로, 구획들이 적은 항목의 합계는 상한의 2배까지만 받습니다. `/Index` 없이 `/Size`만 크게 적은 xref 스트림은 main에서는 읽히던 모양이지만 지금은 거절됩니다.
- **객체 스트림: 선언한 만큼만 파싱.** pdfminer의 `_get_objects`는 `/N`과 상관없이 스트림 끝까지 파싱해서 들고 있습니다. 실제로 쓰는 것은 앞의 3N개뿐이라 거기서 멈추게 했습니다. 같은 파싱이 한 군데 더 있었습니다. `startxref`가 틀리면 pdfminer는 `PDFXRefFallback.load`로 파일을 처음부터 훑어 xref를 복구하는데, 이 메서드가 `_get_objects`를 거치지 않고 객체 스트림을 직접 끝까지 파싱합니다. 이 코드는 메서드 안에 박혀 있어서 일부만 바꿔 끼울 수 없었습니다. 그래서 메서드 전체(40줄)를 옮겨 적고, 스트림을 읽는 한 줄만 "값 2N개까지"로 바꿨습니다. 대가는 pdfminer가 이 메서드를 고쳐도 우리 사본은 옛 동작으로 남는다는 점입니다. 상한 블록 밖에서는 원래 메서드를 씁니다. 리뷰어가 만든 xref 모양 PDF 46개 가운데 44개는 main과 결과가 같았습니다. 나머지 2개는 의도한 차이입니다. `/Size`만 큰 xref 스트림은 거절되고, `/N`이 간접 참조인 객체 스트림은 main에서는 오류였는데 이제는 읽힙니다. **이것으로 못 막는 것**도 있습니다. 선언한 객체 "하나"가 거대한 배열이면 그대로 만들어집니다(8.6KB → 23.1초·781MB). 파싱한 값의 수를 세는 방법도 검토했지만, 태그가 달린 정상 PDF는 객체 스트림 안에 값이 수백만 개 있을 수 있어서 폭탄과 구분할 기준선이 없습니다. 그래서 억지로 상한을 걸지 않고, README에 남은 경로로 적었습니다.
- **Host 허용 목록: 직접 쓴 미들웨어.** Starlette의 `TrustedHostMiddleware`도 있지만, 응답이 400이고 `Origin`은 보지 않습니다. 기존 cross-site 거절과 같은 403으로 맞추고 `Origin`까지 한 곳에서 확인하려고, 40줄짜리 ASGI 미들웨어를 직접 썼습니다. 정규식 전체 일치로 파싱하므로 `localhost@attacker.example`, `localhost.attacker.example` 같은 값은 맞지 않습니다.
- **기본 목록을 대체하는 `AXB_ALLOWED_HOSTS`.** 기본 목록에 더하는 방식이면 `localhost`를 뺄 수 없습니다. Django의 `ALLOWED_HOSTS`와 같은 방식입니다. 와일드카드는 받지 않습니다.
- **pdf_guard: 버전 상한 대신 실패.** `pdfminer.six<2027`처럼 버전 상한을 걸면 보안 수정도 받지 못합니다. 대신 바꿔 끼울 이름 10개가 pdfminer에 실제로 있는지 import할 때 확인하고, 없으면 `PDFGuardUnavailableError`로 멈춥니다. 이름은 그대로인데 pdfminer가 그 함수를 더는 부르지 않게 바뀌는 경우는 이 확인으로 잡을 수 없습니다. 그런 경우에는 폭탄 테스트가 CI에서 실패해서 알려 줍니다.
- **드물게 실패하던 테스트.** `ZipFile.writestr(이름, 내용)`은 항목에 현재 시각을 2초 단위로 적습니다. 테스트는 응답을 만들 때와, 저장된 파일과 비교할 때 `hwpx_bytes()`를 두 번 불렀습니다. 그 사이에 2초 경계를 넘으면 바이트가 달라졌습니다. 시계가 2초씩 가도록 조작한 테스트로 재현했고, 시각을 고정한 `ZipInfo`를 쓰도록 고쳤습니다.

- **재색인 실패(A): `before_replace` 콜백.** `DenseIndex.build`는 이미 "임베딩 → 옛 점 삭제 → 새 점 쓰기" 순서입니다. 그 사이, 즉 임베딩 직후에 부르는 콜백 하나를 더하고, API가 이 콜백에서 `index.json`을 지웁니다. 버린 대안은 세 가지입니다. (1) API가 직접 임베딩하고 `build`에 벡터를 넘기는 방법은 임베딩 코드가 두 곳으로 나뉩니다. (2) 새 컬렉션에 다 만든 뒤 이름을 바꿔 끼우는 방법은 쓰는 도중에 실패해도 옛 색인이 남아서 더 좋습니다. 하지만 Windows 로컬 모드의 `delete_collection`이 파일을 지우지 못하는 문제(Task 10)와 얽혀 변경이 커집니다. (3) 실패하면 `index.json`을 되살리는 방법은, 점이 반쯤 바뀐 경우까지 되살리면 틀린 색인이 "완성"으로 보입니다.
  실패한 뒤에는 메모리 캐시가 비어 있습니다. 같은 Qdrant 폴더는 클라이언트 하나만 열 수 있어서 재색인 전에 닫기 때문입니다. 다음 질문 때 폴더의 색인을 다시 열고 BM25를 다시 만듭니다.
- **동점 순서(B): 허용 오차 안의 점을 기준 점수에 붙여 묶기.** 점수 차가 `TIE_TOLERANCE`(1e-6) 이하면 동점으로 봅니다. 이 값은 흔들림(최대 약 4e-8)보다 충분히 크고, 뜻이 다른 청크 사이의 점수 차(보통 1e-3 이상)보다는 충분히 작습니다. 묶는 방법은 두 가지가 있습니다. 이웃한 점끼리의 차로 묶으면 a≈b, b≈c가 이어지는 연쇄 때문에 묶음이 끝없이 길어질 수 있고, 그 안에서는 점수 순서를 잃습니다. 그래서 묶음에서 가장 높은 점수(기준)와의 차이가 오차 안에 있는 점만 같은 묶음으로 하고, 기준에서 벗어난 첫 점이 다음 묶음의 기준이 되게 했습니다. 따라서 한 묶음의 폭은 1e-6을 넘지 않습니다. 묶음 안에서는 `chunk_id` 오름차순으로 정렬합니다. k에서 잘리는 묶음은 구성원을 모두 봐야 누가 남을지 정할 수 있습니다. 그래서 k+1개를 받아 보고, k번째와 k+1번째가 같은 묶음이면 점수 하한을 걸어 그 묶음의 끝까지 한 번 더 받습니다. 질의는 많아야 두 번입니다. 처음 구현은 두 배씩 늘려 가며 받아서, 전부 동점인 945개에서 6번 질의했습니다.
  **보장 범위**: 같은 벡터끼리의 점수 차(측정한 최대 약 4e-8)는 오차 1e-6보다 훨씬 작아서 늘 한 묶음이 됩니다. 그래서 색인한 세션과 다시 연 세션에서 순서와 k에서 잘린 구성원이 같습니다. 촘촘한 난수 벡터(dim 64·1024) 말뭉치 80개에서 세션 간 차이는 0건이었습니다. 수정 전에는 dim 1024·k=30에서 10개 중 8개였습니다. **보장하지 않는 것**: 서로 다른 청크의 점수가 우연히 "기준 - 1e-6" 경계에서 흔들림 폭 안에 놓이면, 세션에 따라 묶음이 달라질 수 있습니다. 본문은 같아도 임베딩 모델이 배치 구성에 따라 1e-6보다 크게 다른 벡터를 내면 동점이 아닙니다. 실제 모델(GPU)로는 확인하지 못했습니다. 정렬이 문자열 순서라서 `doc::10`이 `doc::2`보다 앞에 오지만, 여기서 필요한 것은 고정된 규칙입니다.
  이 변경은 BM25에는 영향이 없습니다. BM25 평가는 그대로 recall@5 0.841, MRR 0.746입니다. dense·hybrid 수치는 동점 순서와 경계가 바뀌므로 GPU로 다시 측정해야 합니다.

## 면접 예상 질문과 답

**Q1. 서버를 127.0.0.1에만 띄웠는데 왜 Host를 검사하나요?**
127.0.0.1에 띄우면 다른 PC에서는 들어올 수 없지만, 같은 PC의 브라우저는 들어올 수 있습니다. DNS 리바인딩은 공격자 도메인이 127.0.0.1로 풀리게 해서, 브라우저가 로컬 서버를 "공격자 사이트와 같은 출처"로 보게 만듭니다. 이때 요청의 `Host`는 공격자 도메인이므로, 허용한 이름이 아니면 거절합니다. 다만 이것이 인증은 아닙니다. curl은 `Host`를 마음대로 적을 수 있기 때문입니다.

**Q2. 파일 크기 상한이 있는데 왜 쪽 수·요소 수 상한이 또 필요한가요?**
자원을 쓰는 것은 바이트가 아니라 파서가 만드는 객체입니다. 7바이트짜리 `<hp:p/>`가 190바이트 객체가 되고, 30바이트짜리 쪽 사전이 pdfplumber `Page` 객체가 됩니다. 실제로 30KB 파일이 541MB를 썼습니다. 그래서 객체를 만드는 단위(쪽, 요소, 글자)마다 상한을 두었고, 가능하면 객체를 아예 만들지 않는 방식(스트리밍)으로 바꿨습니다.

**Q3. 추출 코드를 다시 썼는데 결과가 같다는 것을 어떻게 확인했나요?**
세 가지로 확인했습니다. 첫째, 기존 HWPX 테스트 11개가 그대로 통과합니다. 둘째, 실제 표준약관 두 개의 추출 텍스트가 수정 전후로 SHA-256까지 같습니다. 셋째, 문단·표·공백 요소를 무작위로 중첩한 XML 4,000개에서 이전 구현과 새 구현의 결과를 비교했습니다. 경계 동작 두 가지(표 뒤에 이어지는 글, `hp:t` 안의 다른 요소)는 테스트로 남겼습니다.

**Q4. 아직 못 막는 것은 무엇인가요?**
PDF를 여는 비용입니다. pdfminer는 쪽을 세기 전에 객체 목록 전체를 읽습니다. 예를 들어 객체 60만 개짜리 47MB PDF는 거절하기까지 12.7초가 걸리고, 메모리를 275MB 씁니다. 순수 파이썬 디코더의 CPU 시간도 그대로입니다. 근본적인 해결책은 파싱을 메모리·시간 상한이 있는 별도 프로세스로 옮기는 것이고, M-3 계획에 들어 있습니다. 또 `Origin` 검사는 포트를 보지 않아서, 구형 브라우저에서 같은 PC의 다른 포트 페이지가 보낸 요청은 막지 못합니다.

**Q5. 외부 라이브러리 내부를 바꿔 끼우는 방어(monkeypatch)는 위험하지 않나요?**
위험합니다. 라이브러리가 이름을 바꾸면 대입은 성공하는데, 아무도 그 값을 쓰지 않아서 방어가 조용히 꺼집니다. 그래서 바꿀 이름이 실제로 있는지 import할 때 확인하고, 없으면 서버가 뜨지 않게 했습니다. 동작 자체는 폭탄 테스트가 CI에서 확인합니다. pdfminer에 상한 옵션이 생기면 그쪽으로 옮기는 것이 맞다고 봅니다.

**Q6. 재색인이 실패하면 서비스는 어떻게 되나요?**
어디서 실패했느냐에 따라 다릅니다. 임베딩 단계에서 실패하면 저장된 점을 건드리기 전이라 이전 색인으로 계속 답하고, 재시작해도 마찬가지입니다. 점을 바꾸는 도중에 실패하거나 서버가 꺼지면 색인이 반쯤 바뀌었을 수 있습니다. 그래서 "색인 없음"(409)으로 보고 다시 색인하라고 알립니다. 이 구분은 완성 표시 파일(`index.json`)을 언제 지우느냐 하나로 정해집니다.

## 남은 위험 (M-2로 넘김)

전체 코드 감사에서 나왔지만 이번에 고치지 않은 것들입니다.

- 프롬프트 길이와 Ollama `num_ctx` 8192 사이에 안전장치가 없습니다. 긴 조항 5개가 들어가면 프롬프트가 잘릴 수 있습니다.
- `[자료 2]`, `[1-3]` 같은 인용 표기 변형은 인용으로 읽지 못합니다.
- txt·md·hwpx 청크의 `page=1`은 의미 없는 값입니다. 이 형식에는 쪽 정보가 없습니다.
- 제목 검사는 유니코드 Cf 범주만 막습니다. 변형 선택자, 한글 채움 문자, 점자 공백, 미지정·사용자 영역 문자는 그대로 통과해 프롬프트와 인용까지 들어갑니다. M-3의 입력 정규화에서 다룰 예정입니다.
- 파서 상한으로 막지 못하는 경로가 남아 있습니다. 해법은 별도 프로세스 격리(M-3)입니다.
  - PDF 객체 하나 안의 큰 배열(8.6KB → 23.1초·781MB)
  - PDF를 여는 비용(47MB → 7.7~12.7초·275MB)
  - ZIP 목록(40만 항목 → 1.8초·295MB)
  - 순수 파이썬 디코더의 CPU 시간
- 재색인이 임베딩 단계에서 실패하면 이전 색인으로 계속 답합니다. 지금은 문서 추가 기능만 있어서 괜찮습니다. 하지만 문서 삭제나 등급 변경 API가 생기면 "지운 문서가 재색인 실패 뒤에도 답에 나온다"는 문제가 되므로, 그때 이 선택을 다시 검토해야 합니다.
- 부칙 청크의 라벨이 중복됩니다.
- `refusal_correct` 지표가 `no_access`·`needs_human` 문항을 제대로 채점하지 않습니다.
- 평가 CLI와 API는 문서를 읽는 입력 경로가 다릅니다. CLI는 코퍼스 폴더에서, API는 업로드 저장소에서 읽습니다.
