# 작업 12 — 릴리스 뒤 보안 점검 후속

v0.1.0을 낸 뒤 보안 점검 에이전트가 재현한 지적 10개를 고친 작업이다. 계획 문서의 Task가 아니라 릴리스 후속 작업이라 번호만 이어서 12로 붙였다.

## 이 작업이 하는 일

| # | 문제 (테스트로 재현) | 고친 방법 |
|---|---|---|
| 1 | `Host: attacker.example:8000` + `Sec-Fetch-Site: same-origin`인 `POST /ask`가 200 | `Host`(있으면 `Origin`도)의 호스트가 허용 목록에 없으면 모든 요청 403. `AXB_ALLOWED_HOSTS` |
| 2 | 내용 없는 쪽 10만 개짜리 8MB PDF가 30.6초·498MB | 쪽 객체를 만들기 전에 쪽을 세어 5,000쪽 초과면 422 → 4.3초·80MB |
| 3 | 빈 `<hp:p/>` 300만 개짜리 30KB HWPX가 8.1초·541MB | 요소 트리를 만들지 않고 글자만 모으고, 요소 100만 개 초과면 422 → 1.3초·44MB |
| 4 | Ollama 클라이언트가 `HTTP_PROXY` 등을 따라 프롬프트가 프록시로 나갈 수 있음 | `httpx.Client(trust_env=False)` |
| 5 | 503 메시지에 `http://user:pass@host`가 그대로 나옴 | URL의 계정 정보를 지운다(`strip_url_credentials`) |
| 6 | 제목에 방향 제어·폭 없는 문자를 넣을 수 있음 | 유니코드 Cf 범주 문자가 있으면 422 |
| 7 | `AXB_DATA_DIR`를 저장소 안 다른 이름으로 두면 원문이 git에 잡힘 | `.gitignore`에 `**/workspaces/*/{raw,documents,index}/` |
| 8 | CI 토큰 권한이 기본값 | `permissions: contents: read` |
| 9 | 다운로드 테스트가 드물게 실패 | ZIP 항목 시각을 고정 |
| 10 | pdfminer가 이름을 바꾸면 PDF 상한이 오류 없이 꺼짐 | 바꿔 끼울 이름이 없으면 `install()`이 실패 |

측정은 같은 PC에서 파일 하나를 `load_document`로 읽는 새 프로세스의 시간과 최대 메모리(peak working set)다. import만 한 상태가 약 40MB다.

## 핵심 개념

**DNS 리바인딩.** 브라우저의 동일 출처 정책은 "스킴 + 호스트 이름 + 포트"가 같은지만 본다. IP는 보지 않는다. 공격자는 `attacker.example` 페이지를 먼저 자기 서버에서 내려 준 뒤, 그 이름의 DNS 응답을 `127.0.0.1`로 바꾼다. 그러면 페이지의 스크립트가 `http://attacker.example:8000/workspaces/bank/ask`를 부를 때 요청은 내 PC의 서버로 가는데, 브라우저에게는 같은 출처다. `Sec-Fetch-Site`는 `same-origin`이고 CORS 없이 응답도 읽는다. 기존 방어(`_RejectCrossSite`)는 이 값을 믿으므로 통과한다.
이때도 바뀌지 않는 것이 `Host` 머리글이다. 브라우저는 주소창의 이름(`attacker.example:8000`)을 그대로 보낸다. 서버가 "내 이름이 아닌 Host"를 거절하면 막힌다. 그래서 읽기(GET)도 막는다. 리바인딩의 목적이 응답을 읽는 것이기 때문이다.

**`Origin` 검사는 왜 더했나.** `Sec-Fetch-Site`는 비교적 새 머리글이다(Chrome 76, Firefox 90, Safari 16.4부터). 그 전 브라우저도 POST에는 `Origin`을 붙인다. `Origin`이 있는데 호스트가 허용 목록에 없으면 거절한다. `Origin: null`(샌드박스 iframe, `file://`)도 거절된다.

**폭탄은 "크기"만이 아니다.** 지금까지 막은 것은 풀어 낸 바이트(압축 폭탄)와 글자 객체 수(글자 폭탄)였다. 이번 두 개는 둘 다 0인데 자원을 썼다.
- 쪽 수 폭탄: `pdfplumber`의 `pdf.pages`는 모든 쪽의 `Page` 객체를 한 번에 만든다. 내용이 없어도 쪽마다 객체와 시간이 든다.
- 요소 수 폭탄: `ElementTree`는 요소마다 객체를 남긴다. `<hp:p/>`는 7바이트인데 객체는 약 190바이트다.

공통된 교훈은 **"입력 크기"가 아니라 "입력이 만들게 하는 객체 수"에 상한을 둬야 한다**는 것이다.

**스트리밍 파싱.** `xml.etree.ElementTree.XMLParser(target=...)`에 `start`/`end`/`data` 메서드를 가진 객체를 넘기면, 파서는 트리를 만들지 않고 이벤트만 알려 준다. `_HwpxParagraphs`가 그 target이다. 열려 있는 문단의 스택과 "지금 `hp:t` 안에서 몇 단계 깊이인가"만 기억한다. 글자가 없는 문단은 닫힐 때 바로 버리므로 빈 문단은 메모리를 쓰지 않는다.

**유니코드 Cf(형식 문자).** `U+202E`(오른쪽에서 왼쪽으로 덮어쓰기)는 뒤 글자를 거꾸로 보이게 한다. `U+200B`(폭 없는 공백)는 보이지 않는다. 제목은 인용과 프롬프트에 그대로 들어가므로, 화면에 보이는 제목과 실제 글자가 달라질 수 있다. 한글 완성형(Lo), 자모(Lo), 채움 문자 `U+3164`(Lo), 한자, 원문자(No), 결합 문자(Mn)는 Cf가 아니라서 그대로 받는다. ZWJ(`U+200D`)로 이은 가족 이모지는 함께 막힌다.

## 왜 이렇게 했나 (대안과 비교)

- **쪽 수를 어떻게 세나.** 카탈로그의 `/Count`를 읽으면 가장 싸지만 파일에 적힌 숫자라 공격자가 1이라고 적을 수 있다. 그래서 pdfminer의 쪽 반복자(`PDFPage.create_pages`)를 상한+1개까지만 돈다. 이 반복자는 쪽 사전만 읽고 방문한 객체를 기억하므로 순환 참조에도 멈춘다.
- **거절할 때 `pdf.close()`를 부르지 않는다.** pdfplumber의 `close()`는 `self.pages`를 돌며 쪽을 닫는데, 이것이 모든 쪽 객체를 만든다. `with pdfplumber.open(...)`을 그대로 쓰면 상한을 넘겨 예외가 난 뒤 블록을 나가면서 폭탄이 터진다. "Page 객체를 하나도 만들지 않았다"를 확인하는 테스트가 이것을 잡았다. 그래서 쪽이 너무 많을 때는 파일 스트림만 닫는다.
- **HWPX: `iterparse` 대신 target.** `iterparse` + `elem.clear()`도 가능하지만 요소 객체를 일단 만든다. `hp:t` 하나에 자식 100만 개를 넣으면 `hp:t`가 닫힐 때까지 모두 메모리에 남는다. target 방식은 요소 객체를 아예 만들지 않는다. 대신 기존 추출 규칙(가장 가까운 문단에만 붙이기, `hp:t` 바로 아래 글자만 쓰기)을 이벤트로 다시 써야 했다. 그래서 동일성을 따로 확인했다: 실제 표준약관 HWPX 두 개의 추출 결과가 수정 전후 바이트 단위로 같고(19,538바이트와 29,937바이트), 무작위로 만든 XML 4,000개에서도 이전 구현과 결과가 같았다.
- **요소 상한 100만 개.** 실제 표준약관 두 개가 1,115개(8천 자)와 1,394개(1만 2천 자)다. 글자 9자에 요소 하나꼴이므로 청크 상한(약 7백만 자)에 닿는 문서도 80만 개쯤이다. 상한에 딱 맞춘 가장 나쁜 파일(한 글자짜리 문단 50만 개)은 1.6초·95MB였다.
- **Host 허용 목록: 직접 쓴 미들웨어.** Starlette의 `TrustedHostMiddleware`도 있지만 응답이 400이고 `Origin`은 보지 않는다. 기존 cross-site 거절과 같은 403으로 맞추고 `Origin`까지 한 곳에서 보려고 40줄짜리 ASGI 미들웨어를 썼다. 정규식 전체 일치로 파싱하므로 `localhost@attacker.example`, `localhost.attacker.example` 같은 값은 맞지 않는다.
- **`AXB_ALLOWED_HOSTS`는 기본 목록을 대신한다.** 더하는 방식이면 `localhost`를 뺄 수 없다. Django의 `ALLOWED_HOSTS`와 같은 방식이다. 와일드카드는 받지 않는다.
- **pdf_guard: 버전 상한 대신 실패.** `pdfminer.six<2027`처럼 묶으면 보안 수정도 못 받는다. 대신 바꿔 끼울 이름 8개가 pdfminer에 실제로 있는지 import 때 확인하고, 없으면 `PDFGuardUnavailableError`로 멈춘다. 이름은 그대로인데 pdfminer가 그 함수를 더는 부르지 않게 바뀌는 경우는 이 확인으로 못 잡는다. 그 경우는 폭탄 테스트가 CI에서 실패해 알려 준다.
- **드물게 실패하던 테스트.** `ZipFile.writestr(이름, 내용)`은 항목에 지금 시각을 2초 단위로 적는다. 테스트는 응답을 만들 때와 저장된 파일과 비교할 때 `hwpx_bytes()`를 두 번 불렀다. 그 사이에 2초 경계를 넘으면 바이트가 달랐다. 시계를 2초씩 가게 조작한 테스트로 재현했고, 시각을 고정한 `ZipInfo`를 쓰게 고쳤다.

## 면접 예상 질문과 답

**Q1. 서버를 127.0.0.1에만 띄웠는데 왜 Host를 검사하나요?**
127.0.0.1에 띄우면 다른 PC에서는 못 오지만, 내 브라우저는 올 수 있습니다. DNS 리바인딩은 공격자 도메인을 127.0.0.1로 풀리게 해서 내 브라우저가 로컬 서버를 "공격자 사이트와 같은 출처"로 보게 만듭니다. 이때 요청의 `Host`는 공격자 도메인이므로, 허용한 이름이 아니면 거절합니다. 다만 인증은 아닙니다. curl은 `Host`를 마음대로 적을 수 있습니다.

**Q2. 파일 크기 상한이 있는데 왜 쪽 수·요소 수 상한이 또 필요한가요?**
자원을 쓰는 것은 바이트가 아니라 파서가 만드는 객체입니다. 7바이트짜리 `<hp:p/>`가 190바이트 객체가 되고, 30바이트짜리 쪽 사전이 pdfplumber `Page` 객체가 됩니다. 30KB 파일이 541MB를 썼습니다. 그래서 객체를 만드는 단위(쪽, 요소, 글자)마다 상한을 두었고, 가능하면 객체를 만들지 않는 방식(스트리밍)으로 바꿨습니다.

**Q3. 추출 코드를 다시 썼는데 결과가 같다는 것을 어떻게 확인했나요?**
세 가지로 확인했습니다. 기존 HWPX 테스트 11개가 그대로 통과합니다. 실제 표준약관 두 개의 추출 텍스트가 수정 전후 SHA-256까지 같습니다. 그리고 문단·표·공백 요소를 무작위로 중첩한 XML 4,000개에서 이전 구현과 새 구현의 결과를 비교했습니다. 경계 동작 두 가지(표 뒤에 이어지는 글, `hp:t` 안의 다른 요소)는 테스트로 남겼습니다.

**Q4. 아직 못 막는 것은 무엇인가요?**
PDF를 여는 비용입니다. pdfminer는 쪽을 세기 전에 객체 목록 전체를 읽습니다. 객체 60만 개짜리 47MB PDF는 거절까지 12.7초·275MB를 씁니다. 순수 파이썬 디코더의 CPU 시간도 그대로입니다. 근본 해결은 파싱을 메모리·시간 상한이 있는 별도 프로세스로 옮기는 것이고 M-3에 있습니다. `Origin`은 포트를 보지 않아서, 구형 브라우저에서 같은 PC의 다른 포트 페이지가 보낸 요청은 막지 못합니다.

**Q5. 외부 라이브러리 내부를 바꿔 끼우는 방어(monkeypatch)는 위험하지 않나요?**
위험합니다. 라이브러리가 이름을 바꾸면 대입은 성공하는데 아무도 그 값을 쓰지 않아 방어가 조용히 꺼집니다. 그래서 바꿀 이름이 실제로 있는지 import 때 확인해 없으면 서버가 뜨지 않게 했고, 폭탄 테스트가 CI에서 동작 자체를 확인합니다. pdfminer에 상한 옵션이 생기면 그쪽으로 옮기는 것이 맞습니다.
