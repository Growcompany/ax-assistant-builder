# Task 19 — 골든셋 원문 전수 대조

계획: [`2026-11-11-m2-slim.md`](../superpowers/plans/2026-11-11-m2-slim.md)의 Task 19. 기록: [대조 기록](../eval/golden-v0-audit.md)(문항별 판정), [주인 확인 목록](../eval/golden-v0-owner-check.md)(11문항), [대조 뒤의 수치](../experiments/2026-11-11-golden-audit.md).

## 이 작업이 하는 일

- 문제: 모든 평가 수치가 기대는 골든셋 50문항이 "에이전트가 문서를 보고 만든 초안, 사람 검수 전"이었다. 정답이나 근거 라벨이 틀렸다면 Recall@5 0.886 같은 숫자는 뜻이 없다.
- 한 일:
  - 골든셋을 만든 것과 다른 실행의 에이전트가 50문항을 원문과 하나씩 대조했다. 본 것은 정답의 사실, 근거 조항 라벨, 대체 근거(같은 내용이 다른 조항에도 있는가), 질문의 모호함, `qtype`, 범위 밖 6문항이 정말 코퍼스에 없는가다.
  - 명백한 오류만 고치기로 했고, 판단이 갈리는 것은 "애매함"으로 남겼다.
  - 주인이 10분에 볼 확인 목록을 만들었다: 애매함 6문항 + "문제 없음" 44문항에서 뽑은 무작위 5문항.
  - BM25 검색 평가를 k = 5와 10으로 다시 돌려 기준선과 견줬다.
- 결과:
  - 문제 없음 44, **수정 0**, 애매함 6(bank-004, 006, 009, 032, 042, 043). `golden.jsonl`은 바뀌지 않았고 파일 해시(`35829957f5be…`)가 기준선과 같다.
  - 그래서 검색 수치도 기준선 그대로다(Recall@5 / MRR: BM25 0.841 / 0.746, dense 0.886 / 0.880, hybrid 0.864 / 0.824).
  - 범위 밖 6문항은 945청크 전체를 핵심어로 찾아 답이 되는 문장이 없음을 확인했다.
  - 수정은 없었지만 발견은 있었다. 대체 근거가 있는 bank-009가 "dense가 놓치고 hybrid가 찾은 문항"이라는 기준선의 서술을 약하게 만든다(아래).
- **이것은 사람 검수가 아니다.** 주인 확인 11문항은 아직 대기 중이다.

## 핵심 개념

**골든셋 검수가 왜 필요한가**
골든셋은 평가의 자다. 자가 틀리면 그것으로 잰 값이 모두 틀린다. 틀리는 방식은 여러 가지다: 정답의 사실이 원문과 다르다, 근거 라벨이 엉뚱한 조항을 가리킨다, 질문이 모호해 답이 둘이다, 범위 밖이라던 질문의 답이 사실은 문서에 있다. 이 골든셋은 LLM이 문서를 보고 만들었으므로 LLM의 오독이 그대로 들어갈 수 있다. 그래서 시스템을 고치기 전에 자부터 확인한다.

**대체 근거와 채점 규칙**
- 검색 채점은 "라벨된 근거 청크가 상위 k에 들어왔는가"다. 근거를 둘 적으면 **둘 다** 찾아야 Recall 1.0이다.
- 그런데 같은 내용이 라벨 밖의 문서에도 있을 수 있다. 이것이 대체 근거다. 검색기가 그쪽을 찾으면 사용자에게는 맞는 답이 나가는데 채점은 오답이다.
- bank-009("예금 보호 1억원이 법에 딱 박혀 있나")의 라벨은 예금자보호법 제32조다. 그런데 상품설명서 2개에 "근거: 제32조 제2항과 시행령 제18조 제7항"이라는 문장이 있다. 세 검색기 모두 상품설명서 청크를 1~3위에 놓았고, 법 조항은 BM25·hybrid에서 4위, dense에서는 5위 밖이었다.
- 지금 스키마에는 "이것을 찾아도 정답" 칸이 없다. `evidence`에 더하면 "모두 찾아야 한다"가 되어 오히려 더 박해진다. 고치려면 허용 근거 칸(예: `alt_evidence`)과 채점 규칙을 먼저 더해야 하고, 그것은 골든셋 수정과 다른 변수라 따로 실험한다.

**"수정 0건"을 어떻게 읽나**
- 뜻하는 것: 같은 종류의 모델이 다른 실행에서 원문과 다시 대조했을 때 명백한 오류를 **찾지 못했다**.
- 뜻하지 않는 것: 오류가 **없다**. 만든 쪽과 대조한 쪽이 같은 계열의 LLM이라 같은 문장을 같은 방식으로 잘못 읽으면 둘 다 "맞다"고 한다. 법령 문장의 적용 범위나 가상 문서 표를 읽는 법 같은 곳이 그렇다.
- "문제 없음"의 범위도 좁다. "정답이 근거 조항의 글과 일치한다"는 뜻이고, 법적으로 완전한 답인지나 실무에서 그렇게 안내하는지는 보장하지 않는다.
- 대조가 보지 못한 것도 적어 두었다: 코퍼스 밖 원문(시행령 등), 2026-11-09 이후의 개정, 다른 말로 쓴 대체 근거(핵심어 검색으로 찾았으므로), 질문이 자연스러운지.

**애매함을 따로 두는 이유**
정답의 사실은 원문과 맞지만 고칠지가 갈리는 문항이 6개 나왔다. 대체 근거 2개(004, 009), 옆 조항이 필요한 것 1개(006), 질문에 조건이 빠진 것 1개(032), 정답에 조건을 더 넣을지 갈리는 것 2개(042, 043)다. 에이전트가 판단으로 고치면 "평가에 유리한 쪽으로 자를 고쳤다"는 의심을 지울 수 없다. 그래서 A(그대로)/B(고침)를 적어 주인이 고르게 했다.

**표본 확인**
에이전트가 "문제 없음"이라고 한 44문항에서 5개를 무작위로 뽑아 주인이 직접 본다. 전부 볼 시간이 없을 때 대조 자체가 믿을 만한지 가늠하는 방법이다. 하나라도 틀리면 같은 유형의 나머지를 다시 대조하기로 했다.

## 왜 이렇게 했나 (대안과 비교)

| 결정 | 대안 | 이유와 한계 |
|---|---|---|
| 에이전트 전수 대조 + 주인 표본 확인(11문항) | 사람이 50문항을 모두 검수 | 계획이 주인의 확인 시간을 10분으로 잡았다. 전수 대조로 기계적인 오류(틀린 조항 번호, 숫자)를 먼저 거르고, 사람의 시간은 판단이 필요한 6문항과 표본 5문항에 쓴다. 한계: 같은 종류의 모델끼리의 대조라 같은 오독을 공유할 수 있다. 문서 어디에도 "사람 검수"라고 쓰지 않았다 |
| 명백한 오류만 고친다 | 애매한 것도 에이전트가 판단해 고친다 | 기준선과의 비교가 깨끗하게 남는다. 고친 것이 0건이라 기준선 수치가 그대로다. 판단은 주인에게 남겼다 |
| 대체 근거 문항을 고치지 않고 계산값만 적는다 | 상품설명서를 근거에 더한다 | 스키마상 더하면 "둘 다 찾아야 정답"이 된다. 허용 근거 칸은 채점 규칙의 변경이라 다른 변수다. 한 번에 변수 하나만 바꾼다 |
| 다시 돌린 평가는 BM25만 | dense·hybrid까지 다시 실행 | 골든셋이 바뀌지 않았으므로 수치는 같다. BM25는 GPU 없이 돌아 "모든 칸이 같다"를 직접 확인했다. dense·hybrid는 2026-11-11에 잰 보고서의 문항별 상위 5개를 읽어 대체 근거의 영향을 봤다 |
| 못 본 것을 문서에 적는다 | 결과만 적는다 | "대조했다"는 말이 실제보다 넓게 읽히지 않게 한다. 법령·고시 5개(826청크)는 근거 조항과 그 앞뒤, 핵심어 검색에 걸린 조항만 읽었다 |

## 면접 예상 질문과 답

**Q1. 평가셋을 직접 확인했습니까?**
전부를 제가 직접 검수한 것은 아닙니다. 골든셋 50문항은 에이전트가 만들었고, 다른 실행의 에이전트가 원문과 전수 대조해 문제 없음 44, 수정 0, 애매함 6으로 판정했습니다. 제가 직접 보는 것은 애매한 6문항과 무작위 표본 5문항, 합쳐 11문항입니다. 그래서 문서에는 "사람 검수"가 아니라 "독립 에이전트의 원문 전수 대조, 주인 확인 11문항"이라고 구분해 적었습니다.

> 주의: 확인 목록 11문항은 2026-11-12 기준으로 아직 대기 중이다. 면접 전에 직접 확인하고, 이 답의 "보는 것은"을 "봤습니다"와 그 결과로 바꾼다.

**Q2. 수정이 0건이면 검수가 의미 없지 않습니까?**
0건이라는 결과에도 정보가 있고, 수정 말고 얻은 것도 있습니다. 먼저 기준선 수치를 그대로 써도 된다는 근거가 하나 생겼습니다. 그리고 BM25가 놓친 문항의 상위 결과를 읽어 "라벨이 박해서 생긴 실패가 아니다"를 확인했고, 대체 근거가 있는 문항 2개와 스키마에 허용 근거 칸이 없다는 문제를 찾았습니다. 다만 0건은 오류가 없다는 증명이 아닙니다. 같은 종류의 모델이 못 찾았다는 뜻이라, 사람 표본 확인을 따로 두었습니다.

**Q3. bank-009가 왜 중요합니까?**
기준선에서 "dense가 놓치고 hybrid가 찾은 문항"의 예로 든 문항이기 때문입니다. 대조해 보니 세 검색기 모두 같은 상품설명서 청크를 1~3위에 놓았고, 차이는 라벨된 법 조항이 4위에 들었느냐뿐이었습니다. 그 상품설명서 문장을 정답으로 인정하면 dense는 1위로 찾은 것이 되고, dense와 hybrid의 Recall@5 차이는 한 문항에서 두 문항으로 벌어집니다(dense 0.886 → 0.909, 계산값). 하이브리드를 기본값으로 둔 근거 하나가 라벨 한 줄에 달려 있었다는 뜻이라, 고치지 않고 정정 방향을 문서에 적어 주인 확인으로 넘겼습니다.

**Q4. 만든 모델과 같은 종류의 모델로 대조하는 것의 한계는 무엇이고, 어떻게 보완했습니까?**
같은 문장을 같은 방식으로 오독하면 둘 다 맞다고 하는 것이 한계입니다. 보완은 세 가지입니다. 대조 방법을 판단이 아니라 기계적인 확인에 가깝게 잡았습니다: 근거 청크 본문을 원문 파일에서 줄 단위로 다시 찾고, 핵심어를 945청크 전체에서 검색했습니다. 판단이 갈리는 문항은 고치지 않고 사람에게 넘겼습니다. 그리고 "문제 없음" 문항에서 무작위 표본을 뽑아 사람이 대조 자체를 점검하게 했습니다. 그래도 이것은 사람 검수를 대신하지 못하고, 그 점을 README의 한계에 적었습니다.

**Q5. 대체 근거 문제는 어떻게 풀 계획입니까?**
골든셋 스키마에 허용 근거 칸을 더하고 채점 규칙을 함께 바꾸는 것입니다. 예를 들면 "필수 근거를 모두 찾았거나 허용 근거를 찾았으면 정답"입니다(아직 정하지 않은 제안입니다). 이것은 채점 규칙의 변경이라 골든셋 수정과 섞지 않고 따로 실험해 전후를 문항 단위로 보고합니다. 지금은 bank-009 한 문항만 바꿨을 때의 계산값만 적어 두었습니다.
