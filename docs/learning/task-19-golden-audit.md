# Task 19 — 골든셋 원문 전수 대조

계획은 [`2026-11-11-m2-slim.md`](../superpowers/plans/2026-11-11-m2-slim.md)의 Task 19입니다. 기록은 [대조 기록](../eval/golden-v0-audit.md)(문항별 판정), [작성자 확인 목록](../eval/golden-v0-owner-check.md)(11문항), [대조 뒤의 수치](../experiments/2026-11-11-golden-audit.md)에 있습니다.

## 이 작업이 하는 일

- 문제: 모든 평가 수치의 바탕인 골든셋 50문항은 "에이전트가 문서를 보고 만든 초안, 사람 검수 전" 상태였습니다. 정답이나 근거 라벨이 틀렸다면 Recall@5 0.886 같은 숫자는 의미가 없습니다.
- 한 일:
  - 골든셋을 만든 실행과는 다른 실행의 에이전트가 50문항을 원문과 하나씩 대조했습니다. 확인한 항목은 정답의 사실, 근거 조항 라벨, 대체 근거(같은 내용이 다른 조항에도 있는지), 질문의 모호함, `qtype`, 그리고 범위 밖 6문항의 답이 정말 코퍼스에 없는지입니다.
  - 명백한 오류만 고치기로 하고, 고칠지 말지 의견이 나뉠 수 있는 문항은 "애매함"으로 남겼습니다.
  - 작성자가 10분 안에 볼 수 있는 확인 목록을 만들었습니다. 애매함 6문항과, "문제 없음" 44문항에서 무작위로 뽑은 5문항입니다.
  - BM25 검색 평가를 k = 5와 10으로 다시 실행해 기준선과 비교했습니다.
- 결과:
  - 문제 없음 44, **수정 0**, 애매함 6(bank-004, 006, 009, 032, 042, 043)이었습니다. `golden.jsonl`은 바뀌지 않았고, 파일 해시(`35829957f5be…`)도 기준선과 같습니다.
  - 그래서 검색 수치도 기준선과 같습니다(Recall@5 / MRR: BM25 0.841 / 0.746, dense 0.886 / 0.880, hybrid 0.864 / 0.824).
  - 범위 밖 6문항은 945청크 전체를 핵심어로 검색해, 답이 되는 문장이 없다는 것을 확인했습니다.
  - 수정은 없었지만 발견한 것은 있습니다. 대체 근거가 있는 bank-009 때문에, 이 문항을 "dense가 놓치고 hybrid가 찾은 문항"으로 든 기준선의 설명이 약해집니다(아래 참고).
- **이것은 사람 검수가 아닙니다.** 이 작업을 마칠 때 작성자 확인 11문항은 아직 대기 중이었습니다. 그 뒤 2026-11-12에 작성자가 이 판단도 에이전트에게 맡겨서, 사람 검수는 끝내 하지 않았습니다.

## 핵심 개념

**골든셋 검수가 왜 필요한가**
골든셋은 평가에 쓰는 자입니다. 자가 틀리면 그 자로 측정한 값이 모두 틀립니다. 골든셋이 틀리는 방식은 여러 가지입니다. 정답의 사실이 원문과 다를 수 있고, 근거 라벨이 엉뚱한 조항을 가리킬 수 있고, 질문이 모호해 답이 둘일 수 있고, 범위 밖이라던 질문의 답이 사실은 문서에 있을 수도 있습니다. 이 골든셋은 LLM이 문서를 보고 만들었기 때문에 LLM의 오독이 그대로 들어갈 수 있습니다. 그래서 시스템을 고치기 전에 자부터 확인합니다.

**대체 근거와 채점 규칙**
- 검색 채점 기준은 라벨된 근거 청크가 상위 k에 들어왔는지입니다. 근거를 두 개 적으면 **둘 다** 찾아야 Recall이 1.0입니다.
- 그런데 같은 내용이 라벨에 없는 문서에도 있을 수 있습니다. 이것을 대체 근거라고 부릅니다. 검색기가 대체 근거를 찾으면 사용자는 맞는 답을 받는데도 채점에서는 오답이 됩니다.
- bank-009("예금 보호 1억원이 법에 딱 박혀 있나")의 라벨은 예금자보호법 제32조입니다. 그런데 상품설명서 2개에 "근거: 제32조 제2항과 시행령 제18조 제7항"이라는 문장이 있습니다. 세 검색기 모두 상품설명서 청크를 1~3위에 놓았고, 법 조항은 BM25·hybrid에서 4위, dense에서는 5위 밖이었습니다.
- 지금 스키마에는 "이것을 찾아도 정답"이라고 적을 칸이 없습니다. `evidence`에 더하면 "모두 찾아야 한다"는 조건이 되어 채점이 오히려 더 엄격해집니다. 고치려면 허용 근거 칸(예: `alt_evidence`)과 채점 규칙을 먼저 더해야 합니다. 이것은 골든셋 수정과는 다른 변수라서 따로 실험합니다.

**"수정 0건"을 어떻게 읽나**
- 뜻하는 것: 같은 종류의 모델이 다른 실행에서 원문과 다시 대조했을 때 명백한 오류를 **찾지 못했다**는 것입니다.
- 뜻하지 않는 것: 오류가 **없다**는 뜻은 아닙니다. 만든 쪽과 대조한 쪽이 같은 계열의 LLM이라, 같은 문장을 같은 방식으로 잘못 읽으면 둘 다 맞다고 판단합니다. 법령 문장의 적용 범위나 가상 문서의 표를 읽는 방법 같은 곳이 그런 예입니다.
- "문제 없음"이 말하는 범위도 좁습니다. 정답이 근거 조항의 글과 일치한다는 뜻일 뿐, 법적으로 완전한 답인지나 실무에서 그렇게 안내하는지는 보장하지 않습니다.
- 대조에서 보지 못한 것도 적어 두었습니다. 코퍼스 밖 원문(시행령 등), 2026-11-09 이후의 개정, 다른 표현으로 쓴 대체 근거(핵심어 검색으로 찾았기 때문), 질문이 자연스러운지 여부입니다.

**애매함을 따로 두는 이유**
정답의 사실은 원문과 맞지만, 고칠지 말지 의견이 나뉠 수 있는 문항이 6개 나왔습니다. 대체 근거가 있는 문항 2개(004, 009), 옆 조항이 필요한 문항 1개(006), 질문에 조건이 빠진 문항 1개(032), 정답에 조건을 더 넣을지 판단이 필요한 문항 2개(042, 043)입니다. 에이전트가 자기 판단으로 고치면 "평가에 유리한 쪽으로 자를 고쳤다"는 의심을 지울 수 없습니다. 그래서 문항마다 A(그대로)와 B(고침)를 적어 작성자가 고르게 했습니다.

**표본 확인**
에이전트가 "문제 없음"이라고 판정한 44문항에서 5개를 무작위로 뽑아 작성자가 직접 보도록 했습니다. 전부 볼 시간이 없을 때 대조 자체를 믿을 수 있는지 가늠하는 방법입니다. 하나라도 틀리면 같은 유형의 나머지 문항을 다시 대조하기로 했습니다.

## 왜 이렇게 했나 (대안과 비교)

| 결정 | 대안 | 이유와 한계 |
|---|---|---|
| 에이전트 전수 대조 + 작성자 표본 확인(11문항) | 사람이 50문항을 모두 검수 | 계획에서 작성자의 확인 시간을 10분으로 잡았습니다. 전수 대조로 기계적인 오류(틀린 조항 번호, 숫자)를 먼저 거르고, 사람의 시간은 판단이 필요한 6문항과 표본 5문항에만 쓰기로 했습니다. 한계는 같은 종류의 모델끼리 대조해서 같은 오독을 공유할 수 있다는 점입니다. 그래서 문서 어디에도 "사람 검수"라고 쓰지 않았습니다 |
| 명백한 오류만 고치기 | 애매한 문항도 에이전트가 판단해 고치기 | 기준선과 깨끗하게 비교할 수 있습니다. 고친 것이 0건이라 기준선 수치가 그대로입니다. 판단은 작성자에게 남겼습니다 |
| 대체 근거 문항은 고치지 않고 계산값만 적기 | 상품설명서를 근거에 더하기 | 지금 스키마에서 근거를 더하면 "둘 다 찾아야 정답"이 됩니다. 허용 근거 칸을 만드는 것은 채점 규칙을 바꾸는 일이라 다른 변수입니다. 한 번에 변수 하나만 바꿉니다 |
| 평가는 BM25만 다시 실행 | dense·hybrid까지 다시 실행 | 골든셋이 바뀌지 않았으므로 수치는 같습니다. BM25는 GPU 없이 실행할 수 있어서 모든 칸이 같다는 것을 직접 확인했습니다. dense·hybrid는 2026-11-11에 측정한 보고서에서 문항별 상위 5개를 읽어 대체 근거의 영향을 확인했습니다 |
| 보지 못한 것도 문서에 적기 | 결과만 적기 | "대조했다"는 말이 실제보다 넓게 읽히지 않게 하려는 것입니다. 법령·고시 5개(826청크)는 근거 조항과 그 앞뒤, 핵심어 검색에 걸린 조항만 읽었습니다 |

## 면접 예상 질문과 답

**Q1. 평가셋을 직접 확인했습니까?**
아니요, 제가 직접 검수하지는 않았습니다. 골든셋 50문항은 에이전트가 만들었고, 다른 실행의 에이전트가 원문과 전수 대조해 문제 없음 44, 수정 0, 애매함 6으로 판정했습니다. 애매한 6문항과 무작위 표본 5문항, 모두 11문항은 처음에 제가 직접 보려고 따로 뽑았지만, 2026-11-12에 그 판단도 에이전트에게 맡겼습니다. 그래서 문서에는 "사람 검수"라고 쓰지 않고, 에이전트의 원문 전수 대조와 에이전트에게 맡긴 판단이라고 구분해 적었습니다.

> 2026-11-12 갱신: 작성자가 이 11문항의 판단을 에이전트에게 맡겼습니다. 체크와 선택은 에이전트가 했고 사람 검수가 아닙니다([확인 목록](../eval/golden-v0-owner-check.md)의 "확인 결과 요약").

**Q2. 수정이 0건이면 검수가 의미 없지 않습니까?**
0건이라는 결과에도 정보가 있고, 수정 말고 얻은 것도 있습니다. 먼저 기준선 수치를 그대로 써도 된다는 근거가 하나 생겼습니다. 그리고 대조한 에이전트가 BM25가 놓친 문항의 상위 결과를 읽어 "라벨이 박해서 생긴 실패가 아니다"를 확인했고, 대체 근거가 있는 문항 2개와 스키마에 허용 근거 칸이 없다는 문제를 찾아냈습니다. 다만 0건은 오류가 없다는 증명이 아닙니다. 같은 종류의 모델이 찾지 못했다는 뜻일 뿐이라서, 사람이 보는 표본 확인을 따로 두었습니다.

**Q3. bank-009가 왜 중요합니까?**
기준선에서 "dense가 놓치고 hybrid가 찾은 문항"의 예로 든 문항이기 때문입니다. 대조 결과를 보면 세 검색기 모두 같은 상품설명서 청크를 1~3위에 놓았고, 차이는 라벨된 법 조항이 4위에 들었느냐뿐이었습니다. 그 상품설명서 문장을 정답으로 인정하면 dense는 1위로 찾은 것이 되고, dense와 hybrid의 Recall@5 차이는 한 문항에서 두 문항으로 벌어집니다(dense 0.886 → 0.909, 계산값). 하이브리드를 기본값으로 둔 근거 하나가 라벨 한 줄에 달려 있었다는 뜻입니다. 그래서 대조한 에이전트는 이 문항을 고치지 않고, 정정 방향을 문서에 적어 확인 목록으로 넘겼습니다. 2026-11-12에 판단을 맡은 에이전트는 이 문항을 그대로 두었습니다.

**Q4. 만든 모델과 같은 종류의 모델로 대조하는 것의 한계는 무엇이고, 어떻게 보완했습니까?**
한계는 같은 문장을 같은 방식으로 잘못 읽으면 둘 다 맞다고 판단한다는 점입니다. 보완책은 세 가지입니다. 첫째, 대조 방법을 판단보다 기계적인 확인에 가깝게 잡았습니다. 근거 청크 본문을 원문 파일에서 줄 단위로 다시 찾고, 핵심어를 945청크 전체에서 검색했습니다. 둘째, 의견이 나뉠 수 있는 문항은 고치지 않고 확인 목록으로 따로 뺐습니다. 셋째, "문제 없음" 문항에서 무작위 표본을 뽑아 대조 자체를 점검할 수 있게 했습니다. 다만 이 확인 목록도 2026-11-12에 에이전트에게 맡겨서 사람이 보지는 않았습니다. 그래서 이것이 사람 검수를 대신하지 못한다는 점을 README의 한계에 적었습니다.

**Q5. 대체 근거 문제는 어떻게 풀 계획입니까?**
골든셋 스키마에 허용 근거 칸을 더하고 채점 규칙도 함께 바꿀 계획입니다. 예를 들면 "필수 근거를 모두 찾았거나 허용 근거를 찾았으면 정답"으로 보는 방식인데, 아직 정하지 않은 제안입니다. 이것은 채점 규칙을 바꾸는 일이라 골든셋 수정과 섞지 않고, 따로 실험해 전후를 문항 단위로 보고하려고 합니다. 지금은 bank-009 한 문항만 바꿨을 때의 계산값만 적어 두었습니다.
