# Task 10 — API 서버

## 이 작업이 하는 일

- `src/axbuilder/api/app.py`의 `create_app(settings, llm=None, embedder=None)`이 FastAPI 앱을 만든다. 지금까지 만든 부품(워크스페이스, 로더·분할, BM25·dense·RRF, `answer()`)을 HTTP로 연결한다.
- `src/axbuilder/api/main.py`는 `app = create_app(Settings.from_env())` 한 줄이다. `uvicorn axbuilder.api.main:app`으로 실행한다. 테스트는 이 파일을 import하지 않는다(실제 모델을 쓰므로).

| 메서드 | 경로 | 성공 | 실패 |
|---|---|---|---|
| GET | `/health` | 200 `{"status": "ok"}` | |
| POST | `/workspaces` | 201 (만든 워크스페이스) | 409 중복, 422 잘못된 id·여러 줄 이름 |
| POST | `/workspaces/{id}/documents` | 201 `{"doc_id"}` | 404, 409 같은 doc_id, 413 50MB 초과, 415 형식, 422 메타·빈 파일·깨진 파일·압축 폭탄·너무 긴 문서 |
| POST | `/workspaces/{id}/index` | 200 `{"chunks": n}` | 404 |
| POST | `/workspaces/{id}/ask` | 200 `{"answer", "citations", "refused", "latency_ms"}` | 404, 400 모르는 역할, 409 색인 없음, 422 빈 질문, 503 LLM·임베딩 모델 못 씀 |

모든 POST는 브라우저가 다른 사이트에서 보냈으면(`Sec-Fetch-Site: cross-site`) 403이다. 본문은 업로드 경로만 51MB, 나머지(JSON)는 64KB까지 받는다(넘으면 413).

```
업로드 ─▶ 확장자(415) ─▶ 1MB씩 복사하며 크기(413) ─▶ 빈 파일(422) ─▶ 서명(415) ─▶ 실제 파싱(422) ─▶ documents/{doc_id}.{ext}
색인   ─▶ 문서 전부 읽기 ─▶ BM25 + Qdrant(index/qdrant) ─▶ 메모리 캐시
질문   ─▶ 역할 확인(400) ─▶ answer(): 권한 등급으로 검색 ─▶ LLM ─▶ 인용 [i] = citations[i-1]
```

## 핵심 개념

**REST와 상태 코드**
자원(워크스페이스, 문서)을 경로로, 동작을 메서드로 나타낸다. 상태 코드는 클라이언트가 "무엇을 고쳐야 하는지" 알려 주는 약속이다. 4xx는 클라이언트가 무언가를 바꿔야 한다는 뜻이다. 400·413·415·422는 요청 자체를 고쳐야 하고, 404·409는 자원의 상태가 바뀌어야(워크스페이스를 만들거나 `/index`를 부른 뒤) 같은 요청이 성공한다. 429처럼 "잠시 기다렸다 다시 하라"는 4xx도 있다(이 저장소의 Claude 클라이언트도 408·409·429를 일시 오류로 본다). 5xx는 서버 쪽 문제다. 503은 "지금 못 하지만 잠시 뒤 될 수 있음"이다. 그래서 Ollama가 꺼진 것은 503이고, 메시지에 해결 방법(`ollama serve`)을 담는다. 계획 표에 없던 409(색인 없음)를 더했다. 요청은 맞지만 자원의 상태(색인 전)가 안 맞는 경우라서다.

**의존성 주입**
`create_app`은 LLM과 임베더를 인자로 받는다. 테스트는 `FakeLLM`과 `HashEmbedder`를 넣는다. 그래서 API 테스트 77개가 네트워크·GPU·모델 없이 약 10초에 돈다. 받은 것이 없으면 설정대로 만든다. 임베딩 모델은 처음 색인하거나 질문할 때 불러온다. 덕분에 서버가 바로 뜨고 `/health`는 GPU 없이도 답한다.

**업로드 검증 (믿지 않는 입력 5가지)**
1. *파일 이름*: 클라이언트가 보낸 이름에서는 확장자만 쓴다. 저장 이름은 검증한 `doc_id`로 만든다(`documents/law-1.txt`). `../../evil.txt`를 보내도 폴더 밖에 쓸 수 없다. `doc_id`는 소문자·숫자를 `-`로 이은 것만 받고, Windows 장치 이름(`con`)도 막는다.
2. *크기*: 실제로 받은 바이트를 센다. `Content-Length`만 보면 안 되는 이유는 두 가지다. chunked 전송에는 이 머리글이 없고, 머리글은 multipart 본문 전체의 크기라 파일 하나의 크기를 알려 주지 않는다. 검사는 두 겹이다. ① 요청 본문을 받으면서 세는 ASGI 미들웨어(업로드 51MB = 파일 50MB + 양식 여유 1MB, 나머지 경로 64KB). FastAPI는 multipart 본문을 엔드포인트보다 먼저 끝까지 읽어 임시 파일에 쌓기 때문에, 이것이 없으면 거대한 본문이 디스크를 채울 수 있다. ② 엔드포인트가 파일을 1MB씩 복사하며 50MB를 넘으면 413. (머리글보다 긴 본문을 보내는 테스트는 TestClient에서만 재현된다. 실제 uvicorn은 `Content-Length`만큼만 본문으로 읽는다.)
3. *형식*: 확장자만 믿지 않고 내용의 서명을 본다. PDF는 앞 1024바이트 안에 `%PDF-`(규격은 첫 줄이지만 Adobe Reader가 1024바이트까지 봐 주는 관례를 따름), HWPX(ZIP)는 `PK\x03\x04`, 텍스트는 NUL 바이트가 없어야 한다.
4. *내용*: 받기 전에 `load_document`와 `chunk_document`로 실제로 읽어 본다. 깨진 파일과 텍스트가 없는 파일(스캔본 PDF)은 422다. 파서마다 예외가 달라 모두 잡고, 상세는 서버 로그에만 남긴다. 청크가 1만 개를 넘는 문서도 422다(색인·재시작 비용을 묶는다).
5. *메타데이터*: `access_level`은 업로드에서 필수다. 기본값(public)을 두면 빠뜨린 내부 문서가 모두에게 보인다(fail-open). `title`·`source`와 워크스페이스 이름은 한 줄(제어 문자 금지)과 길이 상한을 둔다. 프롬프트에 그대로 들어가서, 줄바꿈으로 `[질문]` 같은 구분 줄을 위조할 수 있기 때문이다.

**압축 폭탄: 작은 파일이 파싱하며 거대해지는 경우 (보안 리뷰)**
업로드 크기 50MB 상한은 *받는* 크기만 막는다. 파서가 *풀어 내는* 크기는 따로 막아야 한다.
- HWPX: 구역 XML에 DTD 내부 엔티티(`<!ENTITY a "...">` + `&a;` 반복)를 넣으면 XML 바이트 상한을 우회한다. 4.6KB 업로드가 텍스트 66MB, 색인 180초가 됐다. expat의 billion laughs 방어는 100배까지 허용한다. 한컴 HWPX에는 DTD가 없으므로 `TreeBuilder.doctype()`에서 예외를 던져 DTD가 보이면 엔티티 정의 전에 멈춘다.
- PDF: pdfminer가 FlateDecode를 `zlib.decompress(data)`로 한 번에 풀어, 1MB PDF가 1GB로 풀렸다(최대 메모리 2.1GB). pdfminer에 상한 옵션이 없어 `pdf_guard`가 pdfminer의 해제 함수(Flate·LZW·RunLength)를 상한 있는 것으로 바꿔 끼운다. 문서 하나에서 풀어 낸 합계가 256MB를 넘으면 1MB 단위로 풀다가 바로 멈춘다(같은 파일이 0.7초, 최대 메모리 약 300MB에 422). 동시에 도는 파싱은 2개로 묶는다.
- 남은 위험: 순수 파이썬 디코더(CCITT)의 CPU 시간, 풀린 내용으로 만드는 객체 수는 막지 못한다. 완전히 막으려면 메모리·시간 상한을 건 별도 프로세스에서 파싱해야 한다(M-3).

**역할은 인증이 아니다**
M-1에서는 `/ask`의 역할을 요청이 정한다. 누구나 `준법감시`를 보내면 internal 문서가 든 답을 받는다. 설계상 M-1은 인증이 없고 서버를 127.0.0.1에만 띄운다. 실제 배포에서는 인증 토큰의 클레임으로 역할을 정하고, 검색 단계의 권한 필터는 그대로 둔다(M-3). 같은 이유로 브라우저가 다른 사이트에서 보낸 POST(악성 페이지가 로컬 서버에 문서를 심는 경우)는 `Sec-Fetch-Site`로 막는다. 이 머리글은 브라우저가 붙이고 페이지 스크립트가 바꿀 수 없다.

**오류 응답에 내부 정보를 넣지 않는다**
처리하지 못한 예외는 "서버 내부 오류" 한 줄의 500으로 바꾼다. 스택 트레이스는 서버 로그에만 남긴다. LLM 오류 메시지는 해결 방법을 담고 있어 그대로 보여 주되 로컬 경로는 `<path>`로 지운다. Claude SDK의 인증 오류에는 `C:\Users\<이름>\.config\anthropic\...` 같은 경로가 들어가기 때문이다. 경로 정규식은 공백에서 경로가 끝난다고 봐서 `C:\Users\John Doe\...`는 `Doe`가 남는다. 그래서 서버의 홈 폴더와 사용자 이름을 먼저 글자 그대로 지운다.

**색인 캐시와 Qdrant 로컬 모드의 단일 클라이언트 제약**
Qdrant 로컬 모드는 폴더에 잠금 파일을 둬서 한 폴더를 클라이언트 하나만 열 수 있다. 그래서 워크스페이스별로 `_LoadedIndex`(Qdrant 클라이언트 + BM25 + 하이브리드)를 메모리에 하나만 두고, 재색인할 때 **이전 클라이언트를 닫은 뒤** 새로 연다. 서버를 끌 때는 lifespan이 모두 닫는다. 워크스페이스마다 잠금을 하나 두어 색인·검색·문서 등록이 겹치지 않게 했다. 검색기는 검색할 때마다 잠금 안에서 캐시를 다시 꺼낸다. 미리 꺼내 두면 재색인이 닫은 클라이언트를 쓸 수 있기 때문이다. 느린 LLM 생성은 잠금 밖에서 한다.

구현하다 Windows 전용 버그를 찾았다. qdrant-client(1.20) 로컬 모드의 `delete_collection`은 컬렉션의 SQLite 파일을 닫지 않고 폴더를 지우려 한다. Windows는 열린 파일을 지울 수 없어 삭제가 **조용히** 실패한다(`ignore_errors=True`). 같은 이름으로 다시 만들면 옛 점을 그대로 읽어서, 재색인해도 지운 문서의 청크가 남고 임베딩 차원이 바뀌면 오류가 났다. Linux(CI)에서는 열린 파일도 지워져서 드러나지 않는다. `DenseIndex.build`가 컬렉션을 지우기 전에 점을 모두 지우게 고치고 회귀 테스트를 넣었다.

**서버 재시작 후**
BM25는 메모리에만 있어 재시작하면 사라진다. 그 워크스페이스에 처음 질문이 오면 `index/index.json`(임베더 이름·차원·청크 수)을 확인하고 `index/qdrant`를 연다. 그 안의 청크(payload에 Chunk 전체가 있다)로 BM25를 다시 만든다. 임베딩은 다시 계산하지 않는다. 청크 순서를 (doc_id, 번호)로 맞춰 재시작 전후 검색 결과가 같다(테스트로 확인). 임베더가 바뀌었거나 청크 수가 다르면 409로 다시 색인하라고 알린다. `index.json`은 색인을 다 만든 **뒤에** 쓰고, 재색인을 시작할 때 먼저 지운다. 도중에 서버가 꺼지면 "색인 없음"이 된다. 문서를 올린 뒤에는 `/index`를 다시 불러야 질문에 반영된다.

**Claude 시간 제한 결정 (`ClaudeClient`)**
SDK 기본값은 요청당 600초, 재시도 2번이고 시간 초과도 재시도한다. 질문 하나가 최악 30분(600초 × 3)을 넘게 묶인다. `/ask`는 사람이 기다리는 요청이라 **한 번 120초(연결 5초), 재시도 1번**으로 정했다. 최악은 약 4분(120초 × 2 + 재시도 전 대기 0.375~0.5초)이다. 이 값은 `ClaudeClient` 전체에 걸려서 클라우드 평가(`run_eval --with-llm`)에도 쓰인다. 평가는 첫 `LLMUnavailableError`에서 멈추므로, 생각이 긴 답 하나가 유료 50문항 실행을 중간에 끝낼 수 있다. 첫 클라우드 평가(M-2) 전에 호출자별 timeout이나 스트리밍을 정한다.
- 120초: `OllamaClient`와 같은 값이다. 근거 청크 5개로 짧게 답하는 요청은 이 안에 든다. SDK는 비스트리밍 생성 속도를 시간당 12만 8천 토큰으로 어림하는데, 이 기준이면 `max_tokens=16000`을 다 쓰는 답은 약 450초, 120초 안에는 약 4천 토큰이다. 생각 토큰이 많은 아주 긴 답은 시간 초과(503)가 날 수 있고, 그때는 스트리밍으로 바꾼다.
- 재시도 1번: 529(과부하)·5xx·연결 끊김은 금방 실패하고 다시 하면 되는 경우가 많다. 반대로 시간 초과를 다시 하면 기다림과 비용이 두 배다. 둘 사이에서 1번을 골랐다. 429는 서버가 준 `retry-after`만큼 기다리므로 최악 시간이 그만큼 늘 수 있다.
- anthropic 2.x는 httpx2 기반이라 `httpx.Timeout`이 아니라 `anthropic.Timeout`을 써야 한다. 실제 Claude 호출 없이 클라이언트 설정값만 테스트한다.

## 왜 이렇게 했나 (대안과 비교)

| 선택 | 대안 | 이유 |
|---|---|---|
| 저장 이름 = doc_id | 클라이언트 파일 이름을 정리해 쓰기 | 정리 규칙은 빠뜨리기 쉽다(`..`, 역슬래시, 장치 이름, 유니코드). 서버가 정한 이름이면 공격면이 없다 |
| 본문 상한 미들웨어(경로별) + 엔드포인트 검사 | 엔드포인트 검사만 / `Content-Length`만 | multipart는 엔드포인트 전에 다 읽힌다. chunked 전송에는 `Content-Length`가 없다. JSON 경로까지 51MB를 받으면 검증 전에 메모리에 올라간다 |
| PDF 해제 함수를 상한 있는 것으로 바꿔 끼우기 | 별도 프로세스에서 파싱(메모리·시간 상한) | 재현된 폭탄(Flate)을 표준 라이브러리만으로 바로 막는다. 프로세스 격리는 Windows에서 Job Object가 필요하고 업로드마다 프로세스 시작 비용이 든다. CPU 시간 공격까지 막으려면 M-3에서 격리로 간다 |
| HWPX에서 DTD 거부 | expat 증폭 상한 조정 / defusedxml | 한컴 HWPX에는 DTD가 없어 거부해도 잃는 것이 없다. 표준 라이브러리만으로 되고, 엔티티 정의 전에 멈춘다 |
| 올릴 때 파싱해 보고 422 | 색인할 때 실패 | 문제를 일으킨 요청에서 바로 알려야 고치기 쉽다. 색인 때 실패하면 어느 문서가 원인인지 찾아야 한다 |
| 재시작 후 Qdrant에서 청크를 꺼내 BM25 재구성 | 재시작마다 `/index` 다시 / 청크를 별도 파일로 저장 | 임베딩(가장 비싼 단계)을 다시 하지 않는다. 별도 파일은 Qdrant와 어긋날 수 있다. 색인 안의 청크가 곧 기준이다 |
| 워크스페이스별 잠금, 검색 때만 잡기 | 잠금 없음 / 요청 전체 잠금 | Qdrant 로컬 모드는 동시 접근에 안전하지 않다. LLM 생성까지 잠그면 한 질문이 재색인을 몇 분 막는다 |
| 임베딩 모델 지연 로딩 | 시작할 때 로딩 | 서버가 바로 뜬다. 대신 첫 색인·첫 질문이 모델 로딩 시간(수 초)만큼 느리다 |

## 면접 예상 질문과 답

**Q1. 파일 업로드에서 무엇을 막았나요?**
파일 이름은 확장자만 쓰고 저장 이름은 검증한 doc_id로 만들어 경로 조작을 막았습니다. 크기는 실제로 받은 바이트로 셉니다. chunked 전송에는 `Content-Length`가 없고, FastAPI가 multipart를 엔드포인트보다 먼저 읽기 때문에 본문 상한 미들웨어를 따로 두었습니다. 형식은 확장자와 함께 PDF `%PDF-`, HWPX `PK` 서명을 봅니다. 내용은 받기 전에 실제로 파싱해서 깨진 파일과 스캔본은 500이 아니라 422로 돌려줍니다. 보안 리뷰에서 받는 크기보다 *풀어 내는* 크기가 문제라는 것을 배웠습니다. HWPX의 DTD 엔티티와 PDF의 Flate 압축으로 수 KB~1MB 파일이 수십 MB~1GB로 풀렸습니다. DTD는 거부하고, PDF는 문서당 해제 합계를 256MB로 묶었습니다. 마지막으로 `access_level`을 필수로 해서, 빠뜨린 내부 문서가 public으로 새지 않게 했습니다.

**Q2. 왜 503이고, 왜 409인가요?**
LLM 서버가 꺼졌거나 시간이 초과된 것은 요청이 아니라 서버 쪽 일시 상태라서 503입니다. 클라이언트는 다시 시도하면 되고, 메시지에 `ollama serve` 같은 해결 방법이 들어 있습니다. 색인 전에 질문하면 요청 자체는 올바르지만 자원 상태가 맞지 않아서 409로 "먼저 /index를 부르라"고 알립니다. 404는 워크스페이스가 없거나 id 형식이 틀린 경우입니다. 형식이 틀린 id는 그런 워크스페이스가 있을 수 없으니 404로 통일했습니다.

**Q3. 서버를 다시 켜면 색인을 다시 해야 하나요?**
아닙니다. dense 색인은 Qdrant 파일로 남아 있고, 처음 질문이 올 때 그 파일을 엽니다. BM25는 메모리에만 있어서 Qdrant payload에 저장한 청크로 다시 만듭니다. 임베딩은 다시 계산하지 않습니다. 임베딩 모델이 바뀌어 차원이 다르면 409로 재색인을 요구합니다. 실제 모델로 재시작해 본 결과 첫 질문이 모델 로딩과 Ollama 응답을 합쳐 약 24초 걸렸습니다.

**Q4. Qdrant 로컬 모드를 쓰면서 겪은 문제는요?**
한 폴더를 클라이언트 하나만 열 수 있어서, 재색인할 때 이전 클라이언트를 닫고 다시 엽니다. 그리고 Windows에서만 생기는 버그를 찾았습니다. 컬렉션을 지울 때 SQLite 파일이 열려 있어 삭제가 조용히 실패하고, 다시 만들면 옛 점이 살아났습니다. Linux CI에서는 드러나지 않아서, 로컬 Windows에서 실패하는 회귀 테스트로 고정하고 점을 먼저 지우게 고쳤습니다. 여러 프로세스가 쓰려면 Qdrant 서버 모드로 가야 합니다(M-5 서빙 단계).

**Q5. Claude 타임아웃을 어떻게 정했나요?**
SDK 기본값이면 요청 하나가 최악 30분을 넘게 묶입니다. 사용자가 기다리는 API라 한 번 120초, 재시도 1번으로 최악 약 4분에 끝나게 했습니다. 과부하(529)나 연결 끊김은 금방 실패해서 한 번 다시 하는 게 이득이고, 시간 초과를 여러 번 다시 하면 기다림과 비용만 늘어서 1번으로 제한했습니다. 아주 긴 답이 필요해지면 스트리밍으로 바꾸는 것이 맞습니다.
