# Task 25 — 긴 조항 나누기

계획: `docs/superpowers/plans/2026-11-12-m2-rest.md`의 Task 25. 이 노트는 코드, 값을 고른 측정, 단위 테스트까지를 다룬다. 나누기 전후의 검색·답변 비교와 기본값 결정은 Task 26의 실험 기록(`docs/experiments/2026-11-12-article-split.md`)과 ADR 0007에 따로 쓴다. **기본값은 바꾸지 않았다**(나누지 않음).

## 이 작업이 하는 일

리랭커 실험에서 긴 조항의 뒤쪽 항이 리랭커 입력 512토큰에서 잘려 답을 못 보는 문항이 4개 나왔다(bank-005·012·042·044, [실험 기록의 "잘림"](../experiments/2026-11-11-reranker.md)). 그래서 긴 본문 조항을 항 경계에서 여러 청크로 나누는 선택 기능을 넣었다.

| 무엇 | 내용 |
|---|---|
| `chunk_document(doc, max_chars=None)`, `chunk_by_article(doc, max_chars=None)` | `max_chars`보다 긴 본문 조항을 항(①) → 호(1.) → 목(가.) → 줄 → 글자 수 순서로 나누고, 이웃 조각을 `max_chars` 안에서 욕심내어 묶는다. 둘째 조각부터 `제11조(대리인 거래)` 같은 조항 머리 줄을 앞에 붙인다(머리 길이도 `max_chars`에 센다). `article`·`page`·`doc_id`는 원래 조항 그대로. `None`이면 예전과 바이트까지 같다 |
| 나누지 않는 것 | 부칙, 첫 조항 앞 머리말, 조항이 없는 문서의 고정 길이 청크(800자) |
| `Settings.max_chunk_chars` | `AXB_MAX_CHUNK_CHARS`, 200~20,000, 기본 `None`. 업로드 검사와 색인이 이 값으로 나눈다 |
| `index.json` | `"chunking": {"max_chars": N 또는 null}`. 지금 설정과 다르면 색인 상태가 `stale`이고 질문은 409(다시 색인). 이 필드가 없는 예전 파일은 `null`(나누지 않음)로 읽는다 |
| 평가 CLI | `--max-chunk-chars N`. 보고서 `config`에 `chunking`, 파일 이름 끝에 `-mN`. 옵션이 없으면 보고서·이름이 예전과 같다 |
| `axb serve` | 분할을 켰으면 시작할 때 `청크 분할: …` 한 줄 |

**고른 값(측정): 800자.** 토크나이저만 CPU로 불러(모델 가중치·GPU 없이) 골든셋에서 가장 긴 질문(73자)을 붙여 셌다.

| max_chars | 전체 청크 | 나눈 조각 | 조각 중 512토큰 초과 (KURE-nano / bge-v2-m3) |
|---|---|---|---|
| 없음 | 945 | 0 | (본문 조항 532개 중 74 / 69개가 넘는다) |
| 700 | 1,112 | 263 | 0% / 0% |
| 750 | 1,097 | 242 | 0% / 0% |
| **800** | **1,079** | **213** | **1.9% / 1.4%** (최대 550 / 529토큰) |
| 850 | 1,063 | 192 | 11.5% / 6.2% |
| 900 | 1,049 | 168 | 23.8% / 13.1% |

- 글자 → 토큰 비율(본문 조항, 200자 이상): KURE-nano 중앙값 0.563, 95분위 0.610 / bge-v2-m3 0.535, 0.602. 질문(73자)과 특수 토큰이 45토큰이라 본문에 남는 자리는 약 467토큰이다. 467 ÷ 0.61 ≈ 765자가 "거의 모든 조각이 들어가는" 길이이고, 묶은 조각은 대부분 그보다 짧아(800에서 중앙값 600자) 800자에서도 98% 이상이 들어간다.
- 계획의 기준(조각의 95% 이상)을 만족하는 값 가운데 가장 크다. 900은 KURE-nano에서 76%만 들어간다. 750은 0%지만 청크가 18개 더 많다. 상품설명서의 고정 길이 청크(800자)와 크기도 같다.
- 800에서 945 → 1,079청크. 79개 본문 조항이 나뉘었고(본문 532 → 666), 부칙 385·머리말과 상품설명서 28은 그대로다.
- 네 문항의 정답 조항은 2~5조각으로 나뉘고, 답이 든 조각은 그 문항의 질문과 합쳐 151~463토큰이라 두 토크나이저 모두 512 안에 든다(나누기 전에는 634~1,620토큰).

## 핵심 개념

**리랭커의 입력 한도.** 크로스 인코더는 `[질문][SEP][청크]`가 512토큰을 넘으면 뒤를 자른다. 조항 단위 청크는 길이가 들쭉날쭉해서(중앙값 307자, 최대 3,572자) 긴 조항의 뒤쪽 항은 모델이 아예 보지 못한다. 청크를 나누면 그 항이 자기 조각 안에서 앞쪽에 온다.

**재귀 분할 + 욕심 묶기.** "가장 굵은 경계로 먼저 자르고, 그래도 긴 덩어리만 더 가는 경계로 자른 뒤, 이웃 덩어리를 한도 안에서 다시 이어 붙인다." LangChain의 `RecursiveCharacterTextSplitter`와 같은 생각인데, 경계를 글자(`\n\n`, `.`)가 아니라 법령의 구조(항·호·목)로 잡았다. 묶기 때문에 짧은 항 여러 개가 한 조각에 들어가고 조각이 지나치게 잘게 쪼개지지 않는다. 예: 가계대출약관 제7조(2,740자)는 ① / ② / ③ / ④ / ⑤~⑦로 5개가 되고, 제3조(1,587자)는 ①~④ / ⑤~⑧ / ⑨로 3개가 된다.

**조항 머리 붙이기.** 둘째 조각 "⑨ 제1항 및 제2항 제2호에 의한 이자 등의 율과 관련하여…"만 보면 무슨 조항인지 알 수 없다. 앞에 `제3조(이자등과 지연배상금)`을 붙이면 BM25·임베딩·리랭커가 모두 제목 낱말을 보고, LLM도 자료에서 조항 이름을 읽는다. 붙인 머리도 길이에 넣어 어떤 조각도 `max_chars`를 넘지 않는다(테스트로 고정).

**색인과 설정의 짝.** 색인은 "어떤 청크를 넣었나"의 결과다. 분할 설정이 바뀌면 같은 문서에서 다른 청크가 나오므로, 예전 색인으로 검색하면 지금 설정과 다른 단위로 답한다. 그래서 임베딩 모델 이름처럼 분할 설정도 `index.json`에 남기고, 다르면 `stale` + 409로 다시 색인하게 했다.

## 왜 이렇게 했나 (대안과 비교)

| 결정 | 대안 | 고른 이유 |
|---|---|---|
| 항 → 호 → 목 → 줄 → 글자 순서 | 고정 길이(800자 + 겹침)로 다시 자르기 | 고정 길이는 항 가운데에서 끊어 문장이 두 조각에 걸치고, 어느 항인지 맥락도 잃는다. 항은 법령에서 뜻이 한 단위로 끝나는 자리다. 실제로 800자에서는 79개 조항을 항에서, 그중 22곳을 호에서, 2곳을 목에서 더 나눴고 줄·글자 수로 자른 곳은 없었다 |
| 이웃 조각을 한도 안에서 묶기 | 항마다 한 청크 | 이 코퍼스의 항은 짧은 것이 많다(한 줄짜리 "⑦ … 무효로 한다."). 항마다 나누면 청크가 크게 늘고, 짧은 청크는 BM25에서 과하게 높게 나온다 |
| 둘째 조각부터 머리 줄 | 머리 없이 / 모든 조각에 문서 제목까지 | 첫 조각은 원문이 이미 머리로 시작한다. 문서 제목은 청크 필드(`title`)에 있고 프롬프트에도 들어간다 |
| `page`는 조항이 시작한 쪽 | 조각이 시작한 쪽 | 근거 라벨(`article`·`page`)이 나누기 전과 같아야 골든셋을 같은 규칙으로 채점한다. 지금 코퍼스는 쪽이 없는 형식(txt·hwpx·md)뿐이다 |
| **부칙은 나누지 않음** | 부칙도 같은 규칙 | 800자보다 긴 부칙은 12개이고 11개가 "다른 법률의 개정"(다른 법을 고치는 지시문), 1개는 1997년 시행일 조항이다. 나누면 부칙 청크가 385 → 427(+42)이 되는데, 그 조각들은 "은행법", "금융위원회" 같은 낱말이 많아 질문과 상관없이 후보 자리를 차지한다. 골든셋은 부칙을 근거로 쓰지 않는다(라벨이 개정마다 겹친다. guide-counseling의 짧은 부칙 제2조 하나만 예외). **대가:** 이 12개는 리랭커 입력에서 계속 잘린다(최대 7,269토큰 중 앞 512). BM25 후보 30개(44문항)에서 잘린 부칙 쌍은 1쌍뿐이었다 |
| 하한 200자, 머리는 95자까지 | 하한 없음 | 조항 머리(이 코퍼스 최대 47자)를 붙이고도 본문 자리가 남아야 한다. 머리로 보는 모양은 조 번호 4자리·가지 번호 3자리·괄호 앞 공백 3칸·제목 80자까지라 머리는 95자를 넘지 않고, 머리 뒤 공백은 몇 칸이든 한 글자로 센다. 그래서 덩어리 한도(200 − 96)는 늘 1 이상이다. 하한은 `chunking.MIN_MAX_CHARS` 하나이고 설정의 하한과 같다(테스트로 묶었다) |
| 설정이 다른 색인은 409 | 조용히 그대로 쓰기 / 자동으로 다시 색인 | 그대로 쓰면 "설정을 바꿨는데 결과가 그대로"인 혼란과, 평가와 서비스가 다른 단위로 도는 문제가 생긴다. 자동 재색인은 임베딩을 다시 돌려 시간이 오래 걸리고 GPU를 쓴다. 기존 임베더 불일치(409)와 같은 규칙으로 맞췄다 |
| 평가 CLI는 `--max-chunk-chars`만 본다 | `AXB_MAX_CHUNK_CHARS`도 읽기 | `--reranker`와 같은 원칙: 평가 조건은 명령줄에서 정하고 보고서 이름과 `config`에 남긴다. 셸에 남은 환경변수가 결과를 바꾸지 않게 |

## 남은 위험

- **PR #24 리뷰에서 무한 루프가 나와 고쳤다.** 머리 뒤 공백이 193칸이거나(200자 기준) 머리 자체가 길면 덩어리 한도가 0 이하가 되어 글자 수로 자르는 반복이 앞으로 나가지 못했다. 분할을 켠 서버에 그런 .txt를 올리면 업로드 검사가 파싱 자리를 쥔 채 멈추는 경로였다. 머리 길이에 상한을 두고, 머리 뒤 공백을 한 글자로 세고, `_cut`이 매번 한 글자 이상 나가게 했다. 실제 코퍼스 결과는 기본(945청크)과 200~20,000자 사이 12개 값에서 수정 전과 바이트까지 같다.
- 나눈 조각도 조항 라벨로 채점하므로 답이 없는 조각이 맞은 것으로 셀 수 있다(답 문구 기준 지표를 함께 본다).
- 부칙 12개는 리랭커 입력에서 계속 잘린다(위 표).

## 코드 읽는 순서

1. `src/axbuilder/ingest/chunking.py`: `SPLIT_LEVELS`·`ARTICLE_HEAD`·`MIN_MAX_CHARS` → `chunk_by_article`의 마지막 두 줄 → `_split_article`(머리, 덩어리 한도, 묶기) → `_units`(경계 단계별 재귀) → `_cut`(글자 수, 공백 우선)
2. `tests/ingest/test_article_split.py`: 손으로 계산한 기대값(①②는 함께 258자, ③은 따로), 머리만 있는 조각이 생기지 않는 경우(공정위 약관은 머리 줄 다음 줄에 ①), "모든 조각 ≤ max_chars, 글자를 잃지 않음" 성질 테스트, 어떤 입력에도 끝나는지(리뷰의 세 입력, 공백·제어 문자만 있는 본문, 아주 긴 머리를 스레드 시간 제한으로), 무작위 입력 2,000개의 성질 테스트, 원문이 있을 때만 도는 945청크·800자 1,079청크 지문 비교
3. `src/axbuilder/settings.py`의 `max_chunk_chars` → `src/axbuilder/api/app.py`의 `_parse`, `build_index`(`chunking` 기록), `_chunking_matches`, `_index_status`, `loaded_index` → `tests/api/test_index_chunking.py`
4. `src/axbuilder/eval/run.py`의 `--max-chunk-chars` → `tests/eval/test_run_chunking.py`

## 면접 예상 질문과 답

**Q1. 왜 항 단위로 나눴나요? 고정 길이로 자르면 더 간단하지 않나요?**
고정 길이는 글자 수만 보고 끊어서 한 문장이 두 청크에 걸치고, 뒤 청크에는 어느 조항의 몇 항인지가 사라집니다. 법령의 항은 요건과 효과가 한 단위로 끝나는 자리라 거기서 끊으면 조각마다 뜻이 완결됩니다. 다만 항이 한도보다 길 수 있어서 호, 목, 줄, 마지막으로 글자 수까지 단계적으로 내려가고, 짧은 항은 이웃과 한도 안에서 묶습니다. 이 코퍼스에서 800자로 나눴을 때는 항·호·목 경계만 쓰였고 글자 수로 자른 곳은 없었습니다.

**Q2. max_chars 800은 어떻게 골랐나요?**
목적이 "리랭커 입력 512토큰 안에 답이 든 항이 들어가는 것"이라서 토큰으로 쟀습니다. 두 리랭커의 토크나이저만 CPU로 불러 가장 긴 골든셋 질문을 붙여 셌고, 후보 500~1,000자를 비교했습니다. 본문은 글자당 약 0.56토큰이고 질문이 45토큰을 써서, 800자에서 조각의 98% 이상이 512 안에 들고 900자에서는 76%로 떨어집니다. 계획의 기준(95%)을 넘는 값 중 가장 커서 청크가 가장 적게 늘어나는 800을 골랐습니다. 측정 전 값은 리랭커 실험의 잘린 쌍 수(115, 166)를 그대로 재현해 세는 방법이 맞는지 확인했습니다.

**Q3. 나눈 조각에 조항 머리를 왜 붙이나요?**
둘째 조각부터는 "⑨ 제1항 및 제2항 제2호에 의한…"처럼 시작해서 혼자서는 어느 조항인지 모릅니다. 머리를 붙이면 검색기와 리랭커가 조항 제목 낱말을 보고, LLM이 인용할 때도 맥락이 남습니다. 대신 머리가 길이를 먹으므로 머리까지 넣어 한도를 계산해 모든 조각이 max_chars를 넘지 않게 했고, 그것을 성질 테스트로 고정했습니다.

**Q4. 분할 설정을 바꾸면 왜 다시 색인해야 하나요?**
색인에는 청크마다 계산한 임베딩과 BM25 통계가 들어 있습니다. 분할이 바뀌면 같은 문서에서 다른 청크가 나오니, 예전 색인으로 답하면 지금 설정과 다른 단위의 결과를 냅니다. 그래서 `index.json`에 분할 설정을 남기고, 서버 설정과 다르면 화면에는 "다시 색인 필요"로, 질문에는 409로 알립니다. 필드가 없는 예전 색인은 그때 나누지 않았으므로 "나누지 않음"으로 읽어 기본 설정에서는 그대로 씁니다. 모르는 모양이면 준비됨이라고 하지 않습니다.

**Q5. 청크가 늘면 생기는 부작용은요?**
같은 조항의 조각들이 상위 k를 나눠 차지할 수 있습니다. 나누기 전에는 상위 5개가 다섯 개의 서로 다른 조항이었는데, BM25로 재 보니 44문항 중 6문항에서 한 조항의 조각이 2개 이상 들어와 220칸 중 8칸을 썼습니다. 그만큼 다른 근거가 밀려납니다. 또 채점은 조항 라벨로 하므로 답이 없는 조각이 들어와도 맞은 것으로 셉니다(지표가 후해질 수 있다). BM25만으로는 Recall@5가 0.841 → 0.818로 한 문항(bank-003) 내려가고 한 문항(bank-004)은 순위가 올랐습니다. 리랭커·dense와의 실제 효과는 Task 26에서 문항 단위와 맥니마 검정으로 확인합니다. 필요하면 같은 조항 조각을 하나로 합치거나 이웃 조각을 함께 넣는 방법을 다음 후보로 둡니다.

**Q6. 텍스트를 나누는 반복문에서 무엇을 보장해야 하나요?**
두 가지입니다. 첫째, **진행 보장**: 한 번 돌 때마다 자르는 위치가 적어도 한 글자 앞으로 가야 합니다. 이 프로젝트에서 실제로 놓쳤습니다. 조각 한도를 `max_chars − 머리 길이 − 머리 뒤 공백`으로 계산했는데, 공백이 193칸인 입력에서 한도가 0이 되어 같은 자리에서 영원히 돌았습니다. 서버에서는 업로드 하나가 파싱 자리를 붙잡아 다른 업로드까지 막는 문제가 됩니다. 고칠 때는 한도의 하한을 구조로 보장하고(머리 95자 상한, 공백은 한 글자로 계산, `max_chars` ≥ 200), 자르는 함수(`_cut`) 맨 앞에도 `budget < 1`이면 예외를 내는 가드를 두어 두 겹으로 막았습니다. 둘째, **불변식을 성질로 테스트하기**: 손으로 고른 예시는 제가 생각한 입력만 확인합니다. 그래서 "끝난다, 모든 조각이 한도 이하다, 공백 말고는 글자를 잃지 않는다"를 시드를 고정한 무작위 입력 2,000개(공백·줄바꿈·항 기호·긴 머리를 아무 데나 넣은 것)로 확인합니다. 그중 513개가 고치기 전 코드를 멈추게 하는 입력이었습니다. 끝나지 않는 버그는 테스트도 끝나지 않게 만드므로, 스레드에서 돌리고 시간 제한으로 실패하게 했습니다(Windows에는 `signal.alarm`이 없다). 마지막으로 실제 코퍼스 결과가 고치기 전과 바이트까지 같은지 지문으로 비교해, 고친 것이 실험 수치를 바꾸지 않았음을 확인했습니다.
