# Task 21 — 리랭커 (코드 부분)

계획은 `docs/superpowers/plans/2026-11-11-m2-slim.md`의 Task 21입니다. 이 노트는 코드와 단위 테스트까지를 다룹니다. 실험 결과와 기본으로 켤지에 대한 결정은 실험 기록(`docs/experiments/2026-11-11-reranker.md`)과 ADR 0006에 따로 적었습니다. 아래 "실험 결과 요약"은 그 두 문서를 줄인 것입니다.

## 이 작업이 하는 일

검색기(BM25, dense, hybrid)가 고른 후보 30개 정도를 **크로스 인코더**로 다시 채점해 순위를 새로 매기는 단계를 만들었습니다.

| 항목 | 내용 |
|---|---|
| `retrieval/rerank.py` | `Reranker` 프로토콜, `CrossEncoderReranker`(sentence-transformers), `RerankRetriever`(검색기를 감싸는 검색기)를 담았습니다 |
| `eval.run` 옵션 | `--reranker {none,kure-nano,bge-v2-m3}`(기본 none), `--candidates N`(리랭커에 넘기는 후보 수, 기본 30)을 더했습니다 |
| 보고서 | 리랭커를 쓰면 `config`에 `reranker`, `candidates`, `rerank_truncated`, `rerank_pairs`가 붙고, 파일 이름이 `…-hybrid+kure-nano-c30.json` 꼴이 됩니다 |
| 건드리지 않은 것 | API와 기본 검색기는 그대로입니다. `--reranker none`으로 만든 보고서는 이전과 같습니다 |

## 핵심 개념

**바이 인코더와 크로스 인코더.** dense 검색(바이 인코더)은 질문과 청크를 **따로** 벡터로 만든 뒤 내적으로 비교합니다. 청크 벡터를 미리 만들어 둘 수 있어 빠르지만, 질문과 청크의 낱말이 서로를 보지 못합니다. 크로스 인코더는 `[질문] [SEP] [청크]`를 **한 입력으로** 읽고 관련도 점수 하나를 냅니다. 낱말끼리 직접 비교하므로 더 정확하지만, 미리 계산해 둘 수 없고 쌍마다 모델을 한 번씩 실행해야 합니다. 945청크 전부에 적용하면 질문 하나에 945번입니다. 그래서 싸게 넓게 고르고(검색), 비싸게 좁게 다시 보는(리랭크) 두 단계로 씁니다.

**후보 수(candidates).** 리랭커는 받은 후보 안에서만 순서를 바꿉니다. 정답이 후보 30개 안에 없으면 리랭커가 아무리 좋아도 찾지 못합니다. 후보를 늘리면 정답이 들어올 가능성은 커지지만, 지연이 후보 수에 비례해 늘고 헷갈리는 오답도 같이 들어옵니다. 그래서 실험 축에 30과 50을 두었습니다.

**감싸는 구조(decorator).** `RerankRetriever`는 `Retriever` 프로토콜(`search(질문, k, access_levels)`)을 그대로 만족합니다. 그래서 `answer()`와 `run_eval()`은 리랭커가 있는지 모르는 채로 그대로 씁니다. base가 무엇이든(BM25, dense, hybrid) 같은 방식으로 붙일 수 있습니다.

**권한 필터의 위치.** `access_levels`는 base 검색기에만 넘깁니다. base는 색인 안에서 등급을 거른 뒤 후보를 넘깁니다. 리랭커는 그 후보의 본문만 받으므로 권한 밖 청크를 볼 방법이 없습니다. "검색 → 리랭크 → 권한 필터" 순서였다면 권한 밖 문서가 모델에 들어가 로그나 오류 메시지로 샐 수 있고, 결과 수도 k보다 모자라게 됩니다.

**입력 길이와 잘림.** 크로스 인코더는 `max_length`(기본 512토큰)를 넘는 입력의 뒷부분을 잘라 버립니다. 은행 코퍼스에는 11,452자짜리 청크가 있어서, 정답 문장이 뒤쪽에 있으면 모델은 그 문장을 보지 못한 채 점수를 냅니다. 이런 일이 조용히 일어나지 않도록 `truncated`에 잘린 쌍의 수를 셉니다. 세는 방법은 이렇습니다. 모델에 들어가는 모양 그대로(특수 토큰을 포함한 질문+본문 쌍) **자르지 않고** 토큰화해 길이를 구하고, 한도를 넘는 쌍을 셉니다. 분모가 있어야 의미가 있으므로 채점한 쌍의 수 `scored`도 함께 셉니다.

**늦게 불러오기(lazy load).** `sentence_transformers`와 `torch`는 선택 설치(`.[ml]`)입니다. 모듈 맨 위에서 import하면 기본 설치나 CI에서는 `rerank.py`를 import하기만 해도 오류가 납니다. 그래서 첫 `score()` 호출 때 import하고 모델을 올립니다. 불러오지 못하면 `RerankerUnavailableError`에 모델 이름, 원인, 설치 명령을 담아 알립니다.

**안정 정렬.** 파이썬의 `sorted`는 키가 같은 항목끼리 원래 순서를 지킵니다. 그래서 리랭커 점수가 같으면 base 순위가 그대로 남습니다. 같은 입력에서 늘 같은 결과가 나와야 어느 문항이 뒤집혔는지 비교할 수 있습니다.

## 서버에서 켜는 법 (Task 22)

실험에서만 쓰던 리랭커를 서버의 선택 기능으로 넣었습니다. 환경변수 `AXB_RERANKER`(`none`·`kure-nano`·`bge-v2-m3`, 기본 `none`)와 `AXB_RERANK_CANDIDATES`(1~200, 기본 30)를 주고 서버를 띄우면 됩니다. 예를 들면 `AXB_RERANKER=kure-nano axb serve`입니다. 서버가 시작할 때 `리랭커: nlpai-lab/KURE-Reranker-nano (후보 30개, 처음 질문 때 불러옵니다)` 한 줄이 나오고, 꺼져 있으면 `리랭커: 꺼짐`이 나옵니다.

화면, `/ask`, `/v1/*`, `axb mcp`가 모두 같은 서비스 계층(`_Service.answer_with_usage`)을 지나므로 한 곳에서만 감싸면 됩니다. `_Service._retriever()`가 워크스페이스 검색기(`_WorkspaceRetriever`)를 `RerankRetriever`로 감쌉니다. 리랭커 인스턴스는 **서버 전체에 하나**만 둡니다. 워크스페이스마다 모델을 올리면 GPU 메모리가 워크스페이스 수만큼 들기 때문입니다. 인스턴스는 임베더처럼 처음 질문이 올 때 만듭니다. 감싸는 위치를 워크스페이스 잠금의 **바깥**으로 잡았기 때문에, 잠금은 base 검색 동안만 잡히고 0.4초쯤 걸리는 리랭크는 잠금 밖에서 실행됩니다. 대신 모델이 하나뿐이라 `_SerialReranker`가 채점을 한 번에 한 요청씩만 처리합니다. 동시에 들어온 첫 질문 두 개가 모델을 두 번 올리지 않게 하려는 것입니다.

색인은 건드리지 않습니다. `index.json`에 리랭커를 적지 않으므로 켜고 꺼도 다시 색인할 필요가 없고, 응답 필드도 그대로입니다. `none`이면 `_retriever()`가 예전과 같은 검색기를 그대로 반환합니다.

## 조용히 넘어가지 않고 503을 돌려주는 이유 (Task 22)

리랭커를 불러오지 못했을 때(패키지 없음, 내려받기 실패, 모델을 올리다가 난 GPU 메모리 부족) 고를 수 있는 길은 둘입니다. 리랭커 없이 그냥 답하거나, 실패를 알리는 것입니다. 그냥 답하면 서비스는 멈추지 않지만 **설정한 사람이 모르는 사이에 품질이 달라집니다**. 실험에서 KURE-nano(후보 30개)는 Recall@5를 hybrid 0.864 → 0.943, dense 0.886 → 0.966으로 0.08쯤 올렸습니다(44문항에서 유의하지는 않습니다). 그러니 리랭커가 빠지면 답이 눈에 띄지 않게 나빠지고, 응답만 봐서는 구별할 수 없습니다. 켰다고 믿고 있는데 실제로는 꺼져 있는 상태는, 평가 숫자와 실제 서비스가 어긋나는 고장 가운데 가장 찾기 어려운 종류입니다. 그래서 임베더 실패와 같은 방식으로 503을 줍니다.

503은 이렇게 **불러올 때의 실패**에만 줍니다. 불러온 뒤 채점하다가 난 오류(채점 중 GPU 메모리 부족 포함)는 `RerankerUnavailableError`가 아니라서 500입니다.

이 PC의 관리 API(화면)에는 원인, `pip install -e ".[ml]"`, 그리고 "리랭커 없이 쓰려면 `AXB_RERANKER=none`으로 다시 띄우라"는 안내를 줍니다. 리랭커를 끄는 것은 관리자가 **알고 내리는 결정**이어야 하기 때문입니다. API 키로 부르는 `/v1/*`에는 고정 문구(`문서 검색을 사용할 수 없습니다. 이 어시스턴트의 관리자에게 문의하세요`)만 주고, 모델 이름과 원인은 서버 로그에 남깁니다. 밖의 사용자에게 백엔드 상세를 알리지 않는다는 기존 규칙을 따른 것입니다. 다음 질문 때 다시 불러오기를 시도하므로, 원인을 고치면 서버를 다시 띄우지 않아도 됩니다.

## 실험 결과 요약 (2026-11-12)

숫자는 [실험 기록](../experiments/2026-11-11-reranker.md)과 [ADR 0006](../adr/0006-reranker.md)에서 옮겼습니다. 골든셋 v0의 44문항을 역할 `준법감시`로 측정한 값입니다.

**조합 표** (k = 5, 후보 30개, Recall@5 / MRR)

| base | 리랭커 없음 | + KURE-nano | + bge-v2-m3 |
|---|---|---|---|
| BM25 | 0.841 / 0.746 | 0.898 / 0.868 | 0.909 / 0.861 |
| dense | 0.886 / 0.880 | 0.966 / 0.921 | 0.955 / 0.889 |
| hybrid | 0.864 / 0.824 | 0.943 / 0.887 | 0.932 / 0.883 |

- 질문당 평균 지연은 dense 48 ms에서 403 ms(KURE-nano) / 797 ms(bge-v2-m3)로 늘었습니다. LLM 없이 검색만 측정한 값입니다.
- 기준선의 대표 실패 사례인 bank-029는 hybrid에서 풀렸습니다(10위 밖 → KURE-nano 2위). BM25 단독에서는 정답이 68위라 후보에 들지 못해 풀리지 않았습니다. 정답이 후보 안에 있어야 한다는 위 개념 그대로입니다.
- 나빠진 문항도 있습니다. dense + KURE-nano는 bank-042를 새로 놓쳤고, bank-012는 리랭커를 붙인 12개 조합 모두에서 정답이 1위 → 2위로 내려갔습니다. 리랭커에 넣은 쌍의 8.7~18.0%가 512토큰에서 잘렸습니다. 답이 잘린 뒤쪽에 있던 네 문항(005, 012, 042, 044)은 모두 적어도 한 리랭커에서 순위가 내려가거나 5위 밖으로 밀렸습니다.

**맥니마 검정.** 문항을 맞힘/놓침으로 나눠 같은 문항끼리 비교하는 정확 맥니마 검정을 했습니다. base → 리랭커 12개 비교의 p값은 0.063~0.453이고, 0.05 아래는 하나도 없습니다. 권장 설정인 hybrid → hybrid + KURE-nano(후보 30)는 새로 맞힌 문항이 4개, 새로 놓친 문항이 0개인데도 p = 0.125입니다. 뒤집힌 문항이 3~8개뿐이라 검정력이 낮습니다. 또 조합 12개를 같은 44문항에 적용해 좋은 값을 골라 읽었으므로 낙관 편향이 있습니다.

**답변 평가** (50문항, `qwen3.5:4b-q4_K_M`, 조건마다 한 번 실행)

| 조건 | 인용 정밀도 | 근거 기준 거절 정확도 | 근거가 있는데 거절 | 근거가 없는데 답함 |
|---|---|---|---|---|
| hybrid, 리랭커 없음 | 0.670 | 0.860 | 2 | 5 |
| hybrid + KURE-nano | 0.827 | 0.940 | 2 | 1 |
| dense + KURE-nano | 0.791 | 0.900 | 4 | 1 |

- 조건마다 한 번씩만 실행한 값입니다. 기준선에서는 같은 설정의 인용 정밀도가 0.662, 0.677, 0.707로 흔들렸습니다.
- 거절 관련 칸은 좁힌 거절 규칙으로 다시 채점한 값이고, 모델은 다시 실행하지 않았습니다. 처음 규칙으로 채점한 값은 0.687 / 0.880 / 2 / 4와 0.798 / 0.900 / 5 / 0이었습니다. 달라진 세 문항은 판정기가 새로 놓친 거절입니다. dense + KURE-nano의 "근거가 있는데 거절"은 출력 원문으로 세면 5개입니다.
- 8GB GPU에 임베딩 모델, 리랭커, Ollama를 함께 올리면 VRAM 사용량이 7.9GB까지 찹니다. 리랭커 없는 실행도 같았습니다. 실패는 없었지만 리랭커를 올린 두 실행에서는 색인 시간이 21.9초에서 130.7~132.9초로 늘었습니다. 질문당 지연도 0.9~1.4초 늘었습니다.

**결정(ADR 0006).** 리랭커는 선택 기능으로 넣고 기본값은 꺼 둡니다. 권장 설정은 KURE-Reranker-nano, 후보 30개입니다. 기본 검색기(hybrid)는 바꾸지 않았고, 잠정 결정으로 남아 있습니다.

## 왜 이렇게 했나 (대안과 비교)

| 결정 | 대안 | 이유 |
|---|---|---|
| 검색기를 감싸는 `RerankRetriever` | `answer()`나 `HybridRetriever` 안에 리랭크 단계를 넣기 | 기존 코드를 고치지 않고 붙였다 뗄 수 있습니다. 리랭커 없는 기본 경로는 영향을 받지 않습니다(Review Focus 5) |
| `--candidates`는 "리랭커에 넘기는 수" | hybrid 내부의 RRF 후보 수를 바꾸는 옵션 | 계획이 그런 뜻으로 적혀 있습니다. hybrid는 `search(k)`에서 이미 `max(자기 candidates, k)`개씩 받아 합치므로, 리랭커가 50개를 요청하면 BM25·dense에서 50개씩 받습니다. 보고서의 `retriever_params.candidates`에도 실제 값이 남도록 맞췄습니다 |
| 리랭커 없이 `--candidates`를 주면 오류 | 조용히 무시 | 무시하면 hybrid 후보 수를 바꿨다고 오해한 채 실험 결과를 읽게 됩니다 |
| `none`일 때 새 필드를 넣지 않음 | `reranker: null`을 항상 기록 | 리랭커 없는 보고서가 v0.2.0과 같아야 기준선과 그대로 비교할 수 있습니다. 필드가 없으면 리랭커가 없다는 뜻입니다 |
| 점수를 변환하지 않음 | 시그모이드로 0~1 확률로 바꾸기 | 순서만 쓰기 때문입니다. 단조 변환은 순서를 바꾸지 않습니다. 클래스 2개를 내는 모델만 (관련 로짓 − 무관 로짓)으로 값 하나를 만듭니다 |
| 잘림을 토큰 길이로 직접 계산 | 글자 수로 어림 | 한국어는 글자당 토큰 수가 토크나이저마다 다르고, 두 후보 모델도 서로 다릅니다. 어림으로는 틀린 숫자를 보고하게 됩니다. 대신 토큰화를 한 번 더 하는 시간이 들고, 이 시간은 지연에 포함됩니다 |
| 장치를 지정하지 않음 | 임베더처럼 `"cuda"` 고정 | sentence-transformers가 GPU가 있으면 GPU를, 없으면 CPU를 고릅니다. `torch`를 직접 import하지 않아도 되고, GPU 없는 PC에서도 느리지만 실행됩니다 |
| 평가 전에 한 번 미리 호출(예열) | 그냥 시작 | 모델을 올리는 몇 초가 첫 문항의 지연에 섞이면 평균·최대 지연이 틀어집니다. 적재 시간은 `model_load_seconds`에, 후보 수만큼의 첫 배치는 `warmup_seconds`에 들어갑니다. 잘림 수도 평가 문항에서 생긴 것만 셉니다 |

## 코드 읽는 순서

1. `src/axbuilder/retrieval/rerank.py`의 `RerankRetriever.search` — 15줄 안에 전체 흐름(후보 받기 → 채점 → 검증 → 안정 정렬 → k개)이 들어 있습니다.
2. 같은 파일의 `CrossEncoderReranker` — `_load`(늦게 불러오기와 오류 문구), `_count_truncated`, `score`, `_relevance`(출력 모양 처리) 순서로 봅니다.
3. `src/axbuilder/eval/run.py`의 `main` — `--reranker` 분기에서 리랭커 예열 → `build_retriever(..., min_candidates)` → `RerankRetriever`로 감싸기 → 보고서 필드 기록 순서로 진행됩니다.
4. `tests/retrieval/test_rerank.py` — 계획의 명세 테스트(순서, 동점, 권한, 후보 수)와, 가짜 `CrossEncoder`로 잘림·오류를 확인하는 테스트가 있습니다.
5. `tests/eval/test_run.py` 끝의 리랭커 절 — `none`이면 보고서가 그대로인지, 리랭커가 있으면 무엇이 기록되는지 확인합니다.

## 면접 예상 질문과 답

**Q. 임베딩 검색이 있는데 리랭커를 왜 또 붙이나요?**
임베딩 검색은 질문과 문서를 따로 벡터로 만들어 비교하기 때문에 빠르지만, 세밀한 낱말 대응을 놓칩니다. 크로스 인코더는 질문과 문서를 함께 읽어서 더 정확합니다. 다만 쌍마다 모델을 실행해야 해서 전체 문서에는 쓸 수 없습니다. 그래서 검색으로 후보 30개를 고르고, 리랭커로 그 안의 순서만 바로잡게 했습니다. 실제로 좋아지는지는 가정하지 않고, 같은 골든셋으로 base 3종 × 리랭커 3종을 측정해서 정하게 했습니다.

**Q. 리랭커를 붙이면 권한 필터가 뚫릴 위험은 없나요?**
권한 등급은 base 검색기가 색인 안에서 거르고, 리랭커는 그 결과의 본문만 받습니다. 테스트에서는 가짜 base와 가짜 리랭커를 써서 권한 밖 청크에 가장 높은 점수를 주도록 해 놓고, 그래도 리랭커가 받은 본문 목록에 그 청크가 없다는 것을 단언합니다. 볼 수 있는 등급이 하나도 없는 역할이면 리랭커는 아예 호출되지 않습니다.

**Q. 긴 문서가 512토큰에서 잘리면 어떻게 되나요? 어떻게 알 수 있죠?**
뒷부분이 버려져서 모델이 보지 못합니다. 정답 문장이 뒤쪽에 있으면 점수가 낮게 나옵니다. 오류가 나지 않으니 직접 세지 않으면 알 수 없습니다. 그래서 질문+본문 쌍을 자르지 않고 토큰화해 한도를 넘는 쌍을 세고, 보고서에 `rerank_truncated`와 분모 `rerank_pairs`를 남기게 했습니다. 이 비율이 높으면 `max_length`를 늘리거나 청크를 더 잘게 나누는 실험을 따로 해야 한다는 신호입니다.

**Q. 리랭커의 비용은 무엇이고 어떻게 측정했나요?**
질문마다 후보 수만큼 모델을 실행하는 시간, GPU 메모리, 설치 크기(0.6GB와 2.3GB)가 비용입니다. 평가 실행기는 문항별 지연을 `retriever.search` 전체 시간으로 측정하므로, base 검색과 리랭크 시간이 함께 들어갑니다. 모델을 올리는 시간은 예열 단계로 빼서 따로 기록했습니다. 정확도 이득과 이 비용을 함께 보고 ADR로 결정했습니다.

**Q. hybrid에 리랭커를 붙일 때 후보 수는 어떻게 맞췄나요?**
`--candidates`는 리랭커에 넘기는 후보 수입니다. hybrid는 `search(k)`에서 `max(내부 후보 수, k)`개씩 BM25와 dense에서 받아 RRF로 합친 뒤 k개를 반환합니다. 리랭커가 50개를 요청하면 내부에서도 50개씩 받으므로 후보가 모자라지 않습니다. 30개 이하를 요청하면 내부는 기본값 30을 유지합니다. 주의할 점은 후보를 50으로 늘리면 리랭커 입력뿐 아니라 RRF에 들어가는 목록 길이도 함께 늘어난다는 것입니다. 그래서 보고서의 `retriever_params.candidates`에 그 값을 남겨 두었습니다.

**Q. 리랭커로 오른 수치는 통계적으로 유의한가요?**
유의하지 않았습니다. 문항을 맞힘/놓침으로 나눠 정확 맥니마 검정을 했더니 base → 리랭커 12개 비교의 p값이 0.063~0.453이었고, 0.05 아래는 하나도 없었습니다. 권장 설정인 hybrid + KURE-nano는 새로 맞힌 문항이 4개, 새로 놓친 문항이 0개인데도 p = 0.125입니다. 44문항에서는 뒤집힌 문항이 3~8개뿐이라 검정력이 낮습니다. 그래서 "Recall@5가 0.864에서 0.943이 됐고 방향은 12개 조합 모두 같았지만 유의하지 않다"고 적었고, 여러 조합 중 좋은 값을 고른 낙관 편향도 함께 적었습니다. 그 뒤 골든셋 v1의 127문항으로 다시 측정했을 때는 세 검색기 모두 보정 전 p < 0.05가 나왔습니다(Task 26).

**Q. 수치가 올랐는데 왜 기본으로 켜지 않았나요?**
이유는 세 가지입니다. 첫째, 44문항에서 유의하지 않은 차이로 기본 동작을 바꾸기에는 근거가 약했습니다. 둘째, 8GB GPU에서 임베딩 모델, 리랭커, 로컬 LLM을 함께 실행하면 VRAM이 7.9GB까지 찹니다. 색인 시간도 22초에서 131~133초로 늘었고, 질문당 지연이 0.9~1.4초 늘었습니다. 셋째, 켜면 모델 0.6GB를 더 내려받아야 합니다. 그래서 설정 한 줄(`AXB_RERANKER=kure-nano`)로 켜는 선택 기능으로 넣었습니다. 리랭커가 해롭다는 증거가 있어서 끈 것은 아닙니다. GPU 메모리에 여유가 있거나 LLM이 다른 장비에 있으면 켜는 쪽을 권한다고 ADR 0006에 적었습니다.
