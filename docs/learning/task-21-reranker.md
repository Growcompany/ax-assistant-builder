# Task 21 — 리랭커 (코드 부분)

계획: `docs/superpowers/plans/2026-11-11-m2-slim.md`의 Task 21. 이 노트는 코드와 단위 테스트까지를 다룬다. 실험 결과와 "기본으로 켤지"의 결정은 실험 기록(`docs/experiments/2026-11-11-reranker.md`)과 ADR 0006에 따로 쓴다. 아래 "실험 결과 요약"은 그 두 문서를 줄인 것이다.

## 이 작업이 하는 일

검색기(BM25, dense, hybrid)가 고른 후보 30개쯤을 **크로스 인코더**로 다시 채점해서 줄을 다시 세우는 단계를 만들었다.

| 무엇 | 내용 |
|---|---|
| `retrieval/rerank.py` | `Reranker` 프로토콜, `CrossEncoderReranker`(sentence-transformers), `RerankRetriever`(검색기를 감싸는 검색기) |
| `eval.run` 옵션 | `--reranker {none,kure-nano,bge-v2-m3}`(기본 none), `--candidates N`(리랭커에 넘기는 후보 수, 기본 30) |
| 보고서 | 리랭커를 쓰면 `config`에 `reranker`, `candidates`, `rerank_truncated`, `rerank_pairs`가 붙고 파일 이름이 `…-hybrid+kure-nano-c30.json`이 된다 |
| 건드리지 않은 것 | API와 기본 검색기. `--reranker none`의 보고서는 이전과 같다 |

## 핵심 개념

**바이 인코더와 크로스 인코더.** dense 검색(바이 인코더)은 질문과 청크를 **따로** 벡터로 만든 뒤 내적으로 비교한다. 청크 벡터를 미리 만들어 둘 수 있어 빠르지만, 질문과 청크의 낱말이 서로를 보지 못한다. 크로스 인코더는 `[질문] [SEP] [청크]`를 **한 입력으로** 읽고 관련도 점수 하나를 낸다. 낱말끼리 직접 비교하므로 더 정확하지만, 미리 계산해 둘 수 없고 쌍마다 모델을 한 번 돌려야 한다. 945청크 전부에 돌리면 질문 하나에 945번이다. 그래서 "싸게 넓게 고르고(검색), 비싸게 좁게 다시 본다(리랭크)"의 두 단계로 쓴다.

**후보 수(candidates).** 리랭커는 받은 후보 안에서만 순서를 바꾼다. 정답이 후보 30개 안에 없으면 리랭커가 아무리 좋아도 못 찾는다. 후보를 늘리면 정답이 들어올 가능성은 커지지만 지연이 후보 수에 비례해 늘고, 헷갈리는 오답도 같이 들어온다. 실험 축에 30과 50을 둔 이유다.

**감싸는 구조(decorator).** `RerankRetriever`는 `Retriever` 프로토콜(`search(질문, k, access_levels)`)을 그대로 만족한다. 그래서 `answer()`와 `run_eval()`은 리랭커가 있는지 모른 채 그대로 쓴다. base가 무엇이든(BM25, dense, hybrid) 같은 방식으로 붙는다.

**권한 필터의 위치.** `access_levels`는 base 검색기에만 넘긴다. base는 색인 안에서 등급을 거른 뒤 후보를 준다. 리랭커는 그 후보의 본문만 받으므로 권한 밖 청크를 볼 방법이 없다. "검색 → 리랭크 → 권한 필터" 순서였다면 권한 밖 문서가 모델에 들어가고(로그·오류 메시지로 샐 수 있다) 결과 수도 k보다 모자라게 된다.

**입력 길이와 잘림.** 크로스 인코더는 `max_length`(기본 512토큰)를 넘는 입력의 뒤를 잘라 버린다. 은행 코퍼스에는 11,452자짜리 청크가 있어서, 정답 문장이 뒤쪽에 있으면 모델은 그 문장을 보지 못한 채 점수를 낸다. 이런 일이 조용히 일어나지 않게 `truncated`에 잘린 쌍의 수를 센다. 세는 방법: 모델에 들어가는 모양 그대로(특수 토큰을 포함한 질문+본문 쌍) **자르지 않고** 토큰화해 길이를 재고, 한도를 넘는 쌍을 센다. 분모가 있어야 뜻이 있으므로 채점한 쌍의 수 `scored`도 함께 센다.

**늦게 불러오기(lazy load).** `sentence_transformers`와 `torch`는 선택 설치(`.[ml]`)다. 모듈 맨 위에서 import하면 기본 설치와 CI에서 `rerank.py`를 import하는 것만으로 오류가 난다. 그래서 첫 `score()` 호출 때 import하고 모델을 올린다. 못 불러오면 `RerankerUnavailableError`에 모델 이름, 원인, 설치 명령을 담는다.

**안정 정렬.** 파이썬의 `sorted`는 키가 같은 항목의 원래 순서를 지킨다. 리랭커 점수가 같으면 base 순위가 그대로 남는다. 같은 입력이면 늘 같은 결과가 나와야 "어느 문항이 뒤집혔는지"를 비교할 수 있다.

## 서버에서 켜는 법 (Task 22)

실험에서만 쓰던 리랭커를 서버의 선택 기능으로 넣었다. 환경변수 `AXB_RERANKER`(`none`·`kure-nano`·`bge-v2-m3`, 기본 `none`)와 `AXB_RERANK_CANDIDATES`(1~200, 기본 30)를 주고 서버를 띄우면 된다. 예: `AXB_RERANKER=kure-nano axb serve`. 시작할 때 `리랭커: nlpai-lab/KURE-Reranker-nano (후보 30개, 처음 질문 때 불러옵니다)` 한 줄이 나온다(꺼져 있으면 `리랭커: 꺼짐`). 화면, `/ask`, `/v1/*`, `axb mcp`가 모두 같은 서비스 계층(`_Service.answer_with_usage`)을 지나므로 한 곳에서 감싼다: `_Service._retriever()`가 워크스페이스 검색기(`_WorkspaceRetriever`)를 `RerankRetriever`로 싼다. 리랭커 인스턴스는 **서버 전체에 하나**이고(워크스페이스마다 모델을 올리면 GPU 메모리가 워크스페이스 수만큼 든다) 임베더처럼 처음 질문 때 만든다. 감싸는 위치를 워크스페이스 잠금의 **바깥**으로 잡아서, 잠금은 base 검색 동안만 잡히고 0.4초쯤 걸리는 리랭크는 잠금 밖에서 돈다. 대신 모델이 하나라 `_SerialReranker`가 채점을 한 번에 한 요청씩만 하게 한다(동시에 온 첫 질문 둘이 모델을 두 번 올리지 않게). 색인은 건드리지 않는다: `index.json`에 리랭커를 적지 않으므로 켜고 꺼도 다시 색인할 필요가 없고, 응답 필드도 그대로다. `none`이면 `_retriever()`가 예전과 같은 검색기를 그대로 돌려준다.

## 왜 조용히 넘어가지 않고 503인가 (Task 22)

리랭커를 불러오지 못했을 때(패키지 없음, 내려받기 실패, GPU 메모리 부족) 고를 수 있는 길은 둘이다. 리랭커 없이 그냥 답하거나, 실패를 알리거나. 그냥 답하면 서비스는 멈추지 않지만 **설정한 사람이 모르는 사이에 품질이 달라진다**. 실험에서 KURE-nano(후보 30개)는 Recall@5를 hybrid 0.864 → 0.943, dense 0.886 → 0.966으로 0.08쯤 올렸으므로(44문항에서 유의하지는 않다), 리랭커가 빠지면 답이 눈에 띄지 않게 나빠지고 응답만 봐서는 구별할 수 없다. "켰다고 믿고 있는데 실제로는 꺼져 있는" 상태는 평가 숫자와 실제 서비스가 어긋나는 가장 찾기 어려운 종류의 고장이다. 그래서 임베더 실패와 같은 방식으로 503을 준다. 이 PC의 관리 API(화면)에는 원인, `pip install -e ".[ml]"`, 그리고 "리랭커 없이 쓰려면 `AXB_RERANKER=none`으로 다시 띄우라"는 안내를 준다. 끄는 것은 관리자가 **알고 내리는 결정**이어야 한다. API 키로 부르는 `/v1/*`에는 고정 문구(`문서 검색을 사용할 수 없습니다. 이 어시스턴트의 관리자에게 문의하세요`)만 주고 모델 이름·원인은 서버 로그에 남긴다(밖의 사용자에게 백엔드 상세를 주지 않는 기존 규칙). 다음 질문 때 다시 불러오기를 시도하므로 원인을 고치면 서버를 다시 띄우지 않아도 된다.

## 실험 결과 요약 (2026-11-12)

숫자는 [실험 기록](../experiments/2026-11-11-reranker.md)과 [ADR 0006](../adr/0006-reranker.md)에서 옮겼다. 골든셋 v0 44문항, 역할 `준법감시`다.

**조합 표** (k = 5, 후보 30개, Recall@5 / MRR)

| base | 리랭커 없음 | + KURE-nano | + bge-v2-m3 |
|---|---|---|---|
| BM25 | 0.841 / 0.746 | 0.898 / 0.868 | 0.909 / 0.861 |
| dense | 0.886 / 0.880 | 0.966 / 0.921 | 0.955 / 0.889 |
| hybrid | 0.864 / 0.824 | 0.943 / 0.887 | 0.932 / 0.883 |

- 지연은 질문당 평균 dense 48 ms → 403 ms(KURE-nano) / 797 ms(bge-v2-m3)다. LLM 없이 검색만 잰 값이다.
- 기준선의 대표 실패 bank-029는 hybrid에서 풀렸다(10위 밖 → KURE-nano 2위). BM25 단독에서는 정답이 68위라 후보에 없어서 풀리지 않았다. "정답이 후보 안에 있어야 한다"는 위 개념 그대로다.
- 나빠진 문항도 있다. dense + KURE-nano는 bank-042를 새로 놓쳤고, bank-012는 리랭커를 붙인 12개 조합 모두에서 정답이 1위 → 2위가 됐다. 넣은 쌍의 8.7~18.0%가 512토큰에서 잘렸고, 답이 잘린 뒤쪽에 있던 네 문항(005, 012, 042, 044)은 모두 적어도 한 리랭커에서 순위가 내려가거나 5위 밖으로 밀렸다.

**맥니마 검정.** 문항을 맞힘/놓침으로 나눠 같은 문항끼리 견주는 정확 맥니마 검정을 했다. base → 리랭커 12개 비교의 p값은 0.063~0.453이고 0.05 아래가 하나도 없다. 권장 설정인 hybrid → hybrid + KURE-nano(후보 30)는 새로 맞힘 4, 새로 놓침 0인데 p = 0.125다. 뒤집힌 문항이 3~8개뿐이라 검정력이 낮다. 또 조합 12개를 같은 44문항에 돌려 좋은 값을 읽었으므로 낙관 편향이 있다.

**답변 평가** (50문항, `qwen3.5:4b-q4_K_M`, 조건마다 한 번 실행)

| 조건 | 인용 정밀도 | 근거 기준 거절 정확도 | 근거가 있는데 거절 | 근거가 없는데 답함 |
|---|---|---|---|---|
| hybrid, 리랭커 없음 | 0.687 | 0.880 | 2 | 4 |
| hybrid + KURE-nano | 0.827 | 0.940 | 2 | 1 |
| dense + KURE-nano | 0.798 | 0.900 | 5 | 0 |

- 한 번씩만 돌린 값이다. 기준선에서 같은 설정의 인용 정밀도가 0.662, 0.677, 0.707로 흔들렸다.
- 8GB GPU에 임베딩 모델, 리랭커, Ollama를 함께 올리면 VRAM 사용량이 7.9GB에 붙는다(리랭커 없는 실행도 같았다). 실패는 없었지만 리랭커를 올린 두 실행에서 색인 시간이 21.9초 → 130.7~132.9초, 질문당 지연이 0.9~1.4초 늘었다.

**결정(ADR 0006).** 리랭커는 선택 기능으로 넣고 기본은 끈다. 권장은 KURE-Reranker-nano, 후보 30개다. 기본 검색기(hybrid)는 바꾸지 않았고 잠정으로 남는다.

## 왜 이렇게 했나 (대안과 비교)

| 결정 | 대안 | 이유 |
|---|---|---|
| 검색기를 감싸는 `RerankRetriever` | `answer()`나 `HybridRetriever` 안에 리랭크 단계를 넣기 | 기존 코드를 고치지 않고 붙였다 뗄 수 있다. 리랭커 없는 기본 경로가 영향을 받지 않는다(Review Focus 5) |
| `--candidates`는 "리랭커에 넘기는 수" | hybrid 내부의 RRF 후보 수를 바꾸는 옵션 | 계획의 뜻이 그렇다. hybrid는 `search(k)`에서 이미 `max(자기 candidates, k)`개씩 받아 합치므로, 리랭커가 50개를 청하면 BM25·dense에서 50개씩 받는다. 보고서의 `retriever_params.candidates`에도 실제 값이 남게 맞췄다 |
| 리랭커 없이 `--candidates`를 주면 오류 | 조용히 무시 | 무시하면 "hybrid 후보 수를 바꿨다"고 오해한 채 실험 결과를 읽게 된다 |
| `none`일 때 새 필드를 넣지 않음 | `reranker: null`을 항상 기록 | 리랭커 없는 보고서가 v0.2.0과 같아야 기준선과 그대로 비교된다. 필드가 없으면 리랭커가 없다는 뜻이다 |
| 점수를 변환하지 않음 | 시그모이드로 0~1 확률로 바꾸기 | 순서만 쓴다. 단조 변환은 순서를 바꾸지 않는다. 클래스 2개를 내는 모델만 (관련 로짓 − 무관 로짓)으로 값 하나를 만든다 |
| 잘림을 토큰 길이로 직접 잼 | 글자 수로 어림 | 한국어는 글자당 토큰 수가 토크나이저마다 다르다(두 후보 모델도 다르다). 어림은 틀린 숫자를 보고하게 된다. 대가는 토큰화를 한 번 더 하는 시간(지연에 포함된다) |
| 장치를 지정하지 않음 | 임베더처럼 `"cuda"` 고정 | sentence-transformers가 GPU가 있으면 GPU, 없으면 CPU를 고른다. `torch`를 직접 import하지 않아도 되고 GPU 없는 PC에서도 느리지만 돈다 |
| 평가 전에 한 번 미리 호출(예열) | 그냥 시작 | 모델을 올리는 몇 초가 첫 문항의 지연에 섞이면 평균·최대 지연이 틀린다. 적재 시간은 `model_load_seconds`에, 후보 수만큼의 첫 배치는 `warmup_seconds`에 들어간다. 잘림 수도 평가 문항에서 생긴 것만 센다 |

## 코드 읽는 순서

1. `src/axbuilder/retrieval/rerank.py`의 `RerankRetriever.search` — 15줄 안에 전체 흐름이 있다(후보 받기 → 채점 → 검증 → 안정 정렬 → k개).
2. 같은 파일의 `CrossEncoderReranker` — `_load`(늦게 불러오기와 오류 문구), `_count_truncated`, `score`, `_relevance`(출력 모양 처리).
3. `src/axbuilder/eval/run.py`의 `main` — `--reranker` 분기: 리랭커 예열 → `build_retriever(..., min_candidates)` → `RerankRetriever`로 감싸기 → 보고서 필드.
4. `tests/retrieval/test_rerank.py` — 계획의 명세 테스트(순서, 동점, 권한, 후보 수)와 가짜 `CrossEncoder`로 본 잘림·오류.
5. `tests/eval/test_run.py` 끝의 리랭커 절 — `none`이면 보고서가 그대로인지, 리랭커가 있으면 무엇이 기록되는지.

## 면접 예상 질문과 답

**Q. 임베딩 검색이 있는데 리랭커를 왜 또 붙이나요?**
임베딩 검색은 질문과 문서를 따로 벡터로 만들어 비교하므로 빠르지만 세밀한 낱말 대응을 놓친다. 크로스 인코더는 질문과 문서를 함께 읽어 더 정확하다. 다만 쌍마다 모델을 돌려야 해서 전체 문서에는 못 쓴다. 그래서 검색으로 후보 30개를 고르고 리랭커로 그 안의 순서만 바로잡는다. 실제로 좋아지는지는 가정하지 않고 같은 골든셋으로 base 3종 × 리랭커 3종을 재서 정하게 했다.

**Q. 리랭커를 붙이면 권한 필터가 뚫릴 위험은 없나요?**
권한 등급은 base 검색기가 색인 안에서 거른다. 리랭커는 그 결과의 본문만 받는다. 테스트에서 가짜 base와 가짜 리랭커를 써서, 권한 밖 청크에 가장 높은 점수를 주도록 해 놓고도 리랭커가 받은 본문 목록에 그 청크가 없음을 단언한다. 볼 수 있는 등급이 없는 역할이면 리랭커는 불리지도 않는다.

**Q. 긴 문서가 512토큰에서 잘리면 어떻게 되나요? 어떻게 알 수 있죠?**
뒤쪽이 버려져 모델이 못 본다. 정답 문장이 뒤에 있으면 점수가 낮게 나온다. 오류가 나지 않으므로 직접 세지 않으면 모른다. 그래서 질문+본문 쌍을 자르지 않고 토큰화해 한도를 넘는 쌍을 세고, 보고서에 `rerank_truncated`와 분모 `rerank_pairs`를 남긴다. 비율이 높으면 `max_length`를 늘리거나 청크를 더 잘게 나누는 실험을 따로 해야 한다는 신호다.

**Q. 리랭커의 비용은 무엇이고 어떻게 쟀나요?**
질문마다 후보 수만큼 모델을 돌리는 시간, GPU 메모리, 설치 크기(0.6GB와 2.3GB)다. 평가 실행기는 문항별 지연을 `retriever.search` 전체로 재므로 base 검색과 리랭크 시간이 함께 들어간다. 모델을 올리는 시간은 예열로 빼서 따로 기록한다. 정확도 이득과 이 비용을 함께 보고 ADR로 결정한다.

**Q. hybrid에 리랭커를 붙일 때 후보 수는 어떻게 맞췄나요?**
`--candidates`는 리랭커에 넘기는 수다. hybrid는 `search(k)`에서 `max(내부 후보 수, k)`개씩 BM25와 dense에서 받아 RRF로 합친 뒤 k개를 돌려준다. 리랭커가 50개를 청하면 내부에서도 50개씩 받으므로 모자라지 않는다. 30 이하를 청하면 내부는 기본 30을 유지한다. 주의할 점은, 후보를 50으로 늘리면 리랭커 입력만이 아니라 RRF에 들어가는 목록 길이도 함께 늘어난다는 것이다. 보고서의 `retriever_params.candidates`에 그 값을 남겨 두었다.

**Q. 리랭커로 오른 수치는 통계적으로 유의한가요?**
유의하지 않다. 문항을 맞힘/놓침으로 나눠 정확 맥니마 검정을 했더니 base → 리랭커 12개 비교의 p값이 0.063~0.453이었고 0.05 아래가 없었다. 권장 설정인 hybrid + KURE-nano는 새로 맞힌 문항이 4개, 새로 놓친 문항이 0개인데도 p = 0.125다. 44문항에서는 뒤집힌 문항이 3~8개뿐이라 검정력이 낮다. 그래서 "Recall@5가 0.864에서 0.943이 됐고 방향은 12개 조합 모두 같았지만 유의하지 않다"고 적었고, 여러 조합 중 좋은 값을 고른 낙관 편향도 함께 적었다.

**Q. 수치가 올랐는데 왜 기본으로 켜지 않았나요?**
이유는 셋이다. 첫째, 44문항에서 유의하지 않은 차이로 기본 동작을 바꾸기에는 근거가 약하다. 둘째, 8GB GPU에서 임베딩 모델, 리랭커, 로컬 LLM이 함께 돌면 VRAM이 7.9GB에 붙고 색인 시간이 22초에서 131~133초로, 질문당 지연이 0.9~1.4초 늘었다. 셋째, 켜면 모델 0.6GB를 더 내려받는다. 그래서 설정 한 줄(`AXB_RERANKER=kure-nano`)로 켜는 선택 기능으로 넣었다. 리랭커가 해롭다는 증거가 있어서 끈 것은 아니고, GPU 메모리에 여유가 있거나 LLM이 다른 장비에 있으면 켜는 쪽을 권한다고 ADR 0006에 적었다.
