# 2026-11-10 기준선(baseline): BM25 · dense · hybrid 검색과 hybrid + 로컬 LLM 답변

M-1의 첫 수치다. 골든셋 v0(50문항)으로 검색기 3개를 같은 조건에서 비교하고, hybrid에 로컬 LLM을 붙여 답변 지표를 한 번 잰다. 모든 수치는 아래 "재현 방법"의 명령을 실제로 실행한 출력과 보고서 JSON에서 옮겼다.

## 요약

- **검색은 dense가 가장 좋았다.** Recall@5 / MRR: BM25 0.841 / 0.746, dense 0.886 / 0.880, hybrid 0.864 / 0.824 (근거가 있는 44문항).
- **hybrid(RRF)가 dense보다 낮았다.** Recall@5 차이는 한 문항이다. 문항 단위로 보면, BM25가 놓친 청크는 dense에서 1위여도 RRF 합산에서 밀린다(실패 사례 3).
- **문서 단위 근거가 지표를 부풀린다.** 조항 근거만 있는 25문항의 Recall@5는 0.78~0.82이고, 문서 단위 근거가 들어간 19문항은 0.92~0.97이다.
- **hybrid + qwen3.5:4b**: 인용 정밀도 0.662, 거절 정확도 0.860. 다만 범위 밖 6문항 중 4개는 모델이 "제공된 자료로는 … 확인할 수 없습니다"처럼 **문구를 바꿔 거절**했다. Task 7의 거절 판정(정해진 문구로 시작해야 거절)이 이것을 답변으로 세어서 out_of_scope 거절 정확도가 0.333으로 나왔다. 사람이 읽어 보면 6문항 모두 답을 피했다(아래 "답변 결과").

- **지표마다 분모가 다르다.** 거절 정확도는 n(전체 50), Recall·MRR은 "근거 n"(범위 밖을 뺀 44), 인용 정밀도는 "인용 n"(인용이 하나라도 있는 39문항: 거절했거나 인용 없이 답한 문항은 빠진다)이 분모다. 예를 들어 out_of_scope 행의 인용 정밀도 0.000은 6문항이 모두 틀리게 인용했다는 뜻이 아니라, 인용을 단 **1문항(046)** 의 값이다.
- "근거 n"·"인용 n" 열은 리뷰 뒤 `format_markdown`에 추가했다. 이 표는 같은 보고서 JSON(`20261110-0119-hybrid-2.json`)을 수정한 코드로 다시 출력해 옮겼고, 지표 값은 처음 출력과 같다.
- 검색 지표(Recall·MRR)는 범위 밖 6문항을 빼고 계산하므로 위 검색 표의 hybrid k = 5와 같다.
- 입력 토큰은 질문당 평균 2,000(최대 3,824), 출력 토큰은 평균 79(최대 240)였다.

**거절 지표를 사람이 다시 읽은 결과 (지표가 아니라 판독)**

거절 정확도의 오답 7개는 두 종류다.

| 묶음 | 문항 | 모델이 한 일 | 지표의 판정 |
|---|---|---|---|
| 범위 밖 (6) | 048, 049 | 정해진 문구 그대로 거절 | 맞음 |
| | 045, 046, 047, 050 | "제공된 자료로는 … 확인할 수 없습니다"처럼 문구를 바꿔 거절. 046은 무관한 인용 2개를 달았다 | **틀림** (답한 것으로 셈) |
| 검색이 근거를 못 가져옴 (5) | 005, 006, 010, 017, 029 | 모두 문구를 바꿔 답을 피했다. 005(3개)·017(1개)은 "자료에 없다"고 설명하며 무관한 인용을 달았다 | 맞음 (답한 것으로 세어 "과잉 거절 아님") |
| 근거를 가져옴 (39) | 020, 022, 025 | 답이 든 청크가 1~2위에 있는데 정해진 문구로 거절(과잉 거절) | **틀림** |

- 정리하면 모델은 **근거가 없을 때 지어내지 않고 피했다**(범위 밖 6/6, 검색 실패 5/5). 문제는 (1) 정해진 거절 문구를 지키지 않아 화면에 인용이 붙은 거절이 나가는 것(**3문항**: 범위 밖 046, 검색 실패 005·017)과 (2) 근거가 있는데 거절하는 것(3/39)이다.
- 지표가 사람의 판독과 어긋나는 이유는 거절 판정이 "정규화한 답이 거절 문구로 시작하는가"라는 글자 규칙이기 때문이다. 이 규칙을 느슨하게 하면 "제공된 자료로는 … 다만 [1]에 따르면 …"처럼 앞에서 망설이고 실제로 답한 문항(012, 024, 039, 042)이 거절로 바뀐다. 그래서 M-2에서 판정 규칙과 프롬프트(구조화된 출력)를 함께 바꾸고 이 표로 다시 비교한다.

**답변에서 본 다른 실패**

- 인용 번호 밀림: bank-028은 [1](민원 처리 지침 제13조)의 문장을 그대로 옮기고 [2]를 달았다(두 번 실행 모두). bank-024는 [1](상담 지침 제8조)의 내용에 [4](주택담보대출 설명서)를 달았다. 내용은 맞지만 인용 정밀도는 0이다.
- 다른 상품의 표를 읽음: bank-034(자유적금 36개월 기본금리)에 정기예금 표의 2.65%를 답하고 정기예금 청크를 인용했다(정답 3.10%). 자유적금 금리표가 든 청크(`prod-free-savings::0001`)는 상위 5개에 없었는데, 같은 문서의 다른 청크 3개가 들어와 Recall@5는 1.0이었다. 인용 정밀도가 이 오답을 잡았다.
- 인용으로 잡을 수 없는 오답: bank-030은 맞는 조항(제7조)을 인용했지만 "75세 고객"을 "만 80세 … 초고령 고객"이라고 바꿔 말했다. 인용 정밀도는 위치만 보므로 이런 내용 오류는 M-2의 답변 채점(LLM-judge + 사람)으로 잡아야 한다.

**실행 간 차이**: 같은 설정으로 앞서 한 번 더 돌린 실행(`20261110-0110-hybrid.json`, 커밋 `f7ffd153520c`에서 실행. 실행 도중 보고서 경로 표시 코드를 고쳐 기록에는 `-dirty`가 붙었다)은 인용 정밀도 0.707, 거절 정확도 0.860이었다. 검색 결과는 같고 LLM 샘플링만 다르므로, 50문항 기준 인용 정밀도는 실행마다 0.05 정도 흔들릴 수 있다. 모델끼리 비교할 때는 여러 번 돌린 평균을 써야 한다.

## 문서 단위 근거가 지표를 얼마나 부풀리나

상품설명서 3개는 조항이 없어 근거를 문서 단위(`doc_id`만)로 달았다. 문서 단위 근거는 그 문서의 청크 6개 중 아무거나 맞아도 정답이다. 조항 근거는 예를 들어 은행법 청크 256개 중 1개만 정답이다.

- k = 5에서 문서 단위 근거가 들어간 19문항의 Recall은 BM25 0.921, dense 0.974, hybrid 0.947이고, 조항 근거만 있는 25문항은 0.780, 0.820, 0.800이다. **0.14~0.15 차이**가 난다.
- 전체 수치(0.84~0.89)는 이 두 묶음의 가중 평균이다. "검색이 조항을 정확히 찾는 능력"은 조항 단위 행으로 읽어야 한다.
- table 8문항은 모두 문서 단위라서 table 행의 1.000은 "표의 그 칸이 있는 청크를 찾았다"가 아니라 "그 상품설명서의 어떤 청크든 가져왔다"는 뜻이다. 실제로 bank-034는 자유적금 청크 3개를 가져와 Recall@5가 1.0이었지만 금리표가 든 청크는 그중에 없었고, 모델은 함께 들어온 정기예금 표를 읽고 틀린 금리를 답했다.
- 답변 지표에서도 같은 차이가 보인다: 인용 정밀도는 문서 단위 근거 묶음 0.853, 조항 단위 묶음 0.540이다.

- 실제 상위 5개(hybrid): 정기예금 설명서(일부 해지), 주택담보대출 설명서, 고령 고객 지침 제12조(모바일뱅킹 지원), 자유적금 설명서, 예금거래기본약관 제20조(약관의 변경). BM25에서 정답 조항은 104위, dense k = 10 안에도 없었다.
- 원인 추정: 질문의 "이체 취소"와 조문의 "거래지시 철회"가 형태소로도 의미로도 멀다. 조문은 318자로 짧고 "모바일", "이체" 같은 말이 없다. LLM은 "제공된 자료로는 확인하기 어렵습니다"라고 답을 피했다(지어내지는 않음).

**2. bank-010 — 답이 긴 조문의 한 호에 묻혀 있음 (세 검색기 모두 실패)**
- 질문: "보이스피싱이 무서워서 인터넷·모바일로는 아예 돈이 못 빠져나가게 계좌를 만들 수 있나요?"
- 기대 근거: 전자금융감독규정 제34조(전자금융거래 시 준수사항) 제2호 — "비대면 전자금융거래를 허용하지 않는 계좌 개설 … 서비스를 이용자가 요청하는 경우 … 제공할 수 있도록 시스템을 갖출 것".
- 실제 상위 5개(hybrid): 고령 고객 지침 제12조·제7조, 전자금융감독규정 제6조(추심이체 출금 동의), 전자금융거래법 제6조의3(계좌정보의 사용 및 관리), 정기예금 설명서. BM25 순위 31위(후보 30개 바로 밖), dense는 7위(k = 10에서만 찾음).
- 원인 추정: 제34조는 암호화 통신·실명확인·무결성 검증 같은 보안 의무 목록이고 답은 그중 한 호다. 조 단위 청크에서 이 호의 비중이 작아 임베딩이 흐려진다. 질문의 "보이스피싱", "인터넷·모바일"은 조문의 "비대면 전자금융거래"와 겹치지 않고, 오히려 금융사기 예방을 다루는 가상 내부 지침을 끌어온다.

**3. bank-029 — dense가 1위로 찾았는데 hybrid가 놓침 (RRF의 한계)**
- 질문: "아드님이 70세 어머님 대신 예금을 찾으러 오셨는데, 어떤 서류를 받아야 하나요?"
- 기대 근거: 고령 고객 응대 지침 제11조(대리인 거래) — 위임장, 인감증명서(또는 본인서명사실확인서), 대리인 실명확인증표.
- 실제 결과: dense는 제11조를 **1위**(코사인 0.550)로 찾았다. BM25에서는 68위라 hybrid 후보 30개에 들지 못했다. 그래서 RRF 점수가 dense 쪽 1/(60+1) ≈ 0.0164뿐이고, 두 목록에 모두 나온 청크들(5위 점수 0.0288)보다 낮아 hybrid 상위 5개는 물론 10개에도 들지 못했다. hybrid 상위 5개: 예금거래기본약관 제10조(지급·해지청구), 자유적금 설명서, 고령 고객 지침 제7조·제12조·제2조.
- 원인 추정: BM25 쪽은 "대신" ↔ "대리인", "아드님·어머님" ↔ "고령 고객"이 겹치지 않는다. RRF는 두 검색기를 같은 무게로 더하므로, 한쪽이 크게 틀리면 다른 쪽의 1위도 버린다.
- 이것은 우연이 아니라 구조다. 후보 30개, RRF k = 60에서 한 목록에만 나온 청크는 1위여도 최대 1/61 ≈ 0.0164이고, 두 목록에 모두 나온 청크는 둘 다 30위여도 최소 2/90 ≈ 0.0222다. 그래서 두 목록에 함께 나온 청크가 k개 이상이면(이 문항처럼) 한 검색기에서만 찾은 청크는 1위여도 상위 k개에 들 수 없다.
- bank-017도 같은 방향이다(정답이 dense 5위·BM25 10위라 1/65 + 1/70 ≈ 0.02967, hybrid 5위 0.02986에 근소하게 밀림). 문항별로 더하면 dense만 찾은 근거가 3문항분(017, 029, 041·042의 절반씩), hybrid만 찾은 근거가 2문항분(009, 043·044의 절반씩)이라 Recall@5 차이가 한 문항이 된다.

## 해석할 때 주의할 점

- **문항 수가 작다.** 근거가 있는 문항은 44개라서 한 문항이 Recall에서 약 0.023이다. dense와 hybrid의 Recall@5 차이(0.886 대 0.864)는 한 문항이다. 순위는 바뀔 수 있다. M-2에서 골든셋을 150~200문항으로 늘린 뒤 다시 비교한다.
- **부칙 청크 잡음.** 청크 945개 중 385개(41%)가 부칙(시행일, 경과조치, "다른 법률의 개정")이다. 대부분 짧고(중앙값 92자) 법령 이름을 그대로 담고 있어서, 질문에 법령 이름이 나오면 dense가 부칙 청크를 끌어온다(예: bank-009에서 dense 5위가 예금자보호법 부칙 제18조 "다른 법률의 개정"). k = 5에서 상위 결과 220칸 중 부칙 청크가 BM25 2칸, dense 9칸(7문항), hybrid 3칸이었다. 골든셋 근거 중 부칙은 1개(가상 지침의 부칙 제2조)뿐이라 부칙 청크가 상위에 오면 거의 늘 자리만 차지한다. 또 짧은 청크가 많으면 BM25의 평균 길이(avgdl)가 내려가 긴 본문 조항(예: 금융소비자보호법 제28조, 1,140자)이 길이 보정에서 손해를 볼 수 있다(추정, 미검증).
- **라벨은 한 곳만 정답으로 본다.** bank-009("1억원이 예금자보호법에 박혀 있나")의 근거는 예금자보호법 제32조인데, 상품설명서 두 개가 "근거: 예금자보호법 제32조 제2항"을 인용하며 1억원을 설명한다. 세 검색기 모두 상품설명서를 1~3위에 놓았다. 사용자에게는 도움이 되는 결과일 수 있지만 지표에서는 틀린 것이다. 이런 문항은 Recall·MRR·인용 정밀도를 실제보다 낮게 만든다.
- **거절 정확도는 글자 규칙이다.** 위 "거절 지표를 사람이 다시 읽은 결과"처럼 문구를 바꾼 거절을 답변으로 센다. 모델끼리 비교할 때 "정해진 문구를 지키는 모델"이 유리하다.
- **골든셋이 문서를 보고 만들어졌다.** 질문의 일부(50문항 중 12개)는 원문 문장을 바꿔 쓴 것이라 단어 겹침에 유리하다(BM25 쪽). 반대로 구어체 질문은 법령 용어와 겹치지 않아 BM25가 크게 놓친다(실패 사례 1, 3).
- **역할은 `준법감시` 하나만 쟀다.** `상담원`(public만)이라면 내부 지침 근거가 있는 문항(lookup 7, multi_doc 3)은 검색 결과에 근거가 나올 수 없다. 권한 필터 평가는 M-3에서 따로 한다.
- **인용 정밀도는 하한값이다.** 라벨 밖 청크를 인용하면 그 청크가 실제로 답을 뒷받침해도 0점이다. 반대로 맞는 청크를 인용하고 내용을 틀리게 옮긴 답(bank-030)은 잡지 못한다.
- **LLM 수치는 한 번 실행 값이다.** 같은 설정의 두 실행에서 인용 정밀도가 0.662와 0.707로 달랐다(릴리스 후 세 번째 실행은 0.677, 맨 아래 절). 시간도 한 번씩 잰 값이다.

## 다음에 바꿔 볼 것 (M-2 후보)

1. **리랭커**: hybrid 후보 30개(또는 dense 후보)를 cross-encoder 리랭커로 다시 정렬한다. 실패 사례 3처럼 "한 검색기만 찾은 정답"을 살릴 수 있는지 본다. 늘어나는 지연을 함께 기록한다.
2. **융합 방식**: RRF에서 dense 가중치를 높이거나(가중 RRF) 후보 수를 30 → 50·100으로 바꿔 hybrid가 dense를 넘는지 확인한다. dense 단독도 계속 비교군으로 둔다.
3. **부칙 처리**: (a) 부칙을 색인에서 빼기, (b) 별도 컬렉션으로 두고 질문에 "시행", "경과" 같은 말이 있을 때만 찾기, (c) 최신 부칙만 남기기. 부칙 근거 문항(bank-026)이 깨지지 않는지 함께 본다.
4. **청크 크기**: 긴 조항을 항(①②)이나 호 단위로 나누고 article을 물려준다. 본문 조항은 최대 3,572자(전자금융거래법 제2조)다. 가장 긴 청크 11,452자는 본문이 아니라 다른 법률 개정 지시문이 붙은 금소법 부칙 제13조라서, 그쪽은 부칙 처리(3번)에서 다룬다. 실패 사례 2처럼 조항 안 한 호에만 답이 있는 경우를 겨냥한다. 여러 청크가 같은 라벨을 갖게 되므로 채점 규칙(Task 8 학습 노트)도 함께 정한다.
5. **골든셋 확대와 라벨 개선**: 150~200문항, 구어체 질문 비율 유지, 상품설명서 근거를 섹션 단위로 좁히기, "같은 내용을 담은 다른 위치"를 허용 근거로 추가하기.
6. **거절 판정과 프롬프트**: 답변을 `{"answer", "citations", "refused"}` 같은 구조화된 출력으로 받거나, 거절 판정을 문구 변형까지 받도록 바꾸고 위 판독 표와 맞는지 확인한다. LLM 지표는 3회 이상 돌려 평균과 범위를 적는다.
7. **질문 바꿔 쓰기(query rewriting)**: "이체 취소" → "거래지시 철회"처럼 구어체를 법령 용어로 바꾸는 단계가 BM25 실패를 줄이는지 본다(LLM 호출 비용·지연과 함께).
