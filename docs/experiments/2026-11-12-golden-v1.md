# 2026-11-12 골든셋 v1로 다시 재기: 검색기 3종 × 리랭커 × 긴 조항 나누기, k = 5·10

[계획](../superpowers/plans/2026-11-12-m2-rest.md) Task 26의 검색 실험이다. 골든셋을 v0(근거가 있는 44문항)에서 v1(127문항)로 늘린 뒤 검색기(BM25, dense, hybrid) × 리랭커(없음, KURE-Reranker-nano 후보 30) × 분할(기본, 800자)을 k = 5와 10에서 다시 쟀다. LLM은 부르지 않았다. 답변 평가는 [답변 기록](2026-11-12-answers-v1.md), 분할 전후는 [분할 기록](2026-11-12-article-split.md)에 따로 적었다. 결정은 [ADR 0002](../adr/0002-hybrid-rrf.md)·[ADR 0006](../adr/0006-reranker.md)의 "갱신 (2026-11-12, 골든셋 v1)"과 [ADR 0007](../adr/0007-article-split.md)에 있다.

측정은 구현 세션의 에이전트가 GPU로 돌렸다. 이 기록의 수치는 평가 담당 에이전트가 저장된 보고서 JSON 33개(검색 24, 답변 9)의 문항별 기록에서 다시 계산했다. 보고서의 요약값, 실행 로그의 표와는 모두 맞았고, 구현 세션의 에이전트가 따로 낸 수치와 다른 곳은 아래 "구현 세션의 에이전트의 수치와 대조"에 적었다.

## 요약

- **리랭커는 세 검색기 모두에서 문항 단위로 유의하게 올랐다**(k = 5, 답 문구 기준, 기본 분할, 보정 전 p. 리랭커 세 비교만 Holm 보정하면 셋 다 남고, 계획의 11개 비교를 묶으면 BM25만 남는다 — 아래 "여러 비교"). 새로 맞힘 / 새로 놓침: BM25 15 / 2 (p = 0.002), dense 10 / 2 (p = 0.039), hybrid 12 / 2 (p = 0.013). v0 44문항에서는 방향이 같았지만 p = 0.063~0.453이었다.
- **유의해진 것은 표본이 커져서다(검정력).** 같은 보고서에서 v0 44문항 부분만 떼면 세 검색기 모두 5 / 1, p = 0.219로 여전히 유의하지 않다. 새 83문항이 불일치 문항을 더했다.
- **남는 결론은 채점 규칙과 비교 묶음에 따라 다르다.** 라벨 기준으로는 dense의 리랭커 효과가 유의하지 않다(8 / 2, p = 0.109). Holm 보정을 하면, 리랭커 비교 3개만 한 묶음으로 볼 때는 답 문구 기준 셋 다 남고, 이 기록의 주요 비교 11개(리랭커 3, 분할 6, dense 대 hybrid 2)를 한 묶음으로 볼 때는 BM25의 리랭커 효과만 남는다(보정 p = 0.026).
- **dense와 hybrid는 갈리지 않았다.** 리랭커 없이 답 문구 기준 Recall@5 / MRR이 dense 0.886 / 0.810, hybrid 0.870 / 0.752이고, 문항 단위로는 hybrid 쪽 8 / 10 (p = 0.81)이다. 리랭커를 붙이면 k = 5에서 두 검색기가 맞힌 문항이 똑같다(127문항 중 117).
- **BM25가 강할 질의**: 조항 번호로 묻는 18문항(`article_ref`)은 dense가 Recall@5·MRR 모두 1.000이다(hybrid 1.000 / 0.903, BM25 0.944 / 0.861). 정식 상품명으로 묻는 12문항(`product_name`)은 답 문구 기준 Recall@5가 BM25 1.000, hybrid 0.917, dense 0.833이다(라벨 기준은 셋 다 1.000). hybrid와 dense의 차이는 한 문항(bank-074)이다.
- **긴 조항 나누기(800자)는 검색 지표를 거의 바꾸지 않았다.** 리랭커와 함께면 세 검색기 모두 1 / 0(bank-042), 리랭커 없이 1~3 / 2~3이다. → [분할 기록](2026-11-12-article-split.md)
- **라벨 기준은 문서 단위 근거 문항(50)에서 후하다.** 리랭커 없는 세 검색기에서 라벨 기준이 답 문구 기준보다 MRR은 0.20~0.24, Recall@5는 0.09~0.10 높다. 조항 단위 근거 문항(77)은 기본 분할에서 두 기준이 같다.
- **비용**: 질문당 검색 지연 평균 hybrid 42 ms → hybrid + KURE 400 ms. VRAM 최대(바탕 약 0.67GB 포함) 4,688 → 5,272 MiB.

## 재현 방법

```bash
export PYTHONPATH=src AXB_DATA_DIR=<원문이 있는 data 폴더>
# 검색기(bm25 | dense | hybrid)와 k(5 | 10)마다 네 번
.venv/Scripts/python -m axbuilder.eval.run --workspace bank --retriever hybrid --k 5 --reports-dir <저장소 밖 폴더>
.venv/Scripts/python -m axbuilder.eval.run --workspace bank --retriever hybrid --k 5 --reranker kure-nano --candidates 30 --reports-dir <…>
.venv/Scripts/python -m axbuilder.eval.run --workspace bank --retriever hybrid --k 5 --max-chunk-chars 800 --reports-dir <…>
.venv/Scripts/python -m axbuilder.eval.run --workspace bank --retriever hybrid --k 5 --reranker kure-nano --candidates 30 --max-chunk-chars 800 --reports-dir <…>
```

- 보고서: k = 5가 `20261112-1426-bm25.json` ~ `20261112-1436-hybrid+kure-nano-c30-m800.json` 12개, k = 10이 `20261112-1438-bm25.json` ~ `20261112-1448-hybrid+kure-nano-c30-m800.json` 12개. 저장소 밖(세션 임시 폴더)에 두었고 커밋하지 않았다.
- 24개 보고서의 `config`에서 커밋, 골든셋·코퍼스 지문, 역할이 모두 같고 청크 수가 분할에 따라 945 / 1,079임을 확인했다. 보고서의 청크 ID는 같은 코드로 CPU에서 다시 만든 청크 목록과 모두 맞았다.
- 검색은 결정적이다. 같은 역할로 돈 답변 실행 8회의 상위 5개는 같은 조건의 검색 실행과 127문항 모두 같았다.

## 두 채점: 라벨 기준과 답 문구 기준

- **라벨 기준**(`matches`): 청크의 문서·조항 라벨이 근거와 같으면 맞음. M-1부터 쓴 지표다.
- **답 문구 기준**(`matches_strict`): 라벨이 맞고, 청크 본문에 근거의 답 문구(anchor)가 들어 있음. Task 24에서 더했다.
- 이 기록의 문항 단위 검정은 답 문구 기준을 본문으로 하고 라벨 기준을 함께 적는다.

라벨 기준이 얼마나 후했나 (k = 5, 기본 분할, 리랭커 없음. 칸은 라벨 → 답 문구):

| 부분 | n | BM25 R@5 | BM25 MRR | dense R@5 | dense MRR | hybrid R@5 | hybrid MRR |
|---|---|---|---|---|---|---|---|
| v0 부분 전체 | 44 | 0.841 → 0.795 | 0.742 → 0.623 | 0.886 → 0.864 | 0.880 → 0.843 | 0.864 → 0.841 | 0.824 → 0.719 |
| v0 · 문서 단위 근거 포함 | 19 | 0.921 → 0.816 | 0.860 → 0.583 | 0.974 → 0.921 | 0.974 → 0.889 | 0.947 → 0.895 | 0.974 → 0.732 |
| 새 부분 전체 | 83 | 0.873 → 0.843 | 0.767 → 0.687 | 0.940 → 0.898 | 0.894 → 0.793 | 0.934 → 0.886 | 0.859 → 0.769 |
| 새 · 문서 단위 근거 포함 | 31 | 0.984 → 0.903 | 0.925 → 0.711 | 1.000 → 0.887 | 0.962 → 0.692 | 1.000 → 0.871 | 0.968 → 0.728 |
| 조항 단위 근거만 (v0 25 + 새 52) | 77 | 0.799 (같음) | 0.666 (같음) | 0.877 (같음) | 0.838 (같음) | 0.864 (같음) | 0.767 (같음) |

- 차이는 모두 문서 단위 근거(상품설명서)에서 나온다. 상품설명서는 조항이 없어 라벨 기준으로는 그 문서 6청크 중 아무거나 맞고, 답 문구 기준으로는 답이 든 1~2청크만 맞는다.
- 그러니 v0로 보고한 수치([기준선](2026-11-10-baseline.md), [리랭커 기록](2026-11-11-reranker.md))는 문서 단위 문항에서 후했다. v0 부분의 hybrid MRR은 라벨 0.824, 답 문구 0.719다. dense는 덜 깎인다(0.880 → 0.843).
- 리랭커를 붙이면 두 기준의 차이가 Recall@5 0.02, MRR 0.04 정도로 준다. 문서 단위 근거 행의 답 문구 MRR이 0.662~0.767에서 0.863~0.873으로 오른다(답이 든 표 행 청크가 위로 온다).

- 태그 행에는 새 문항만 들어 있다(v0에는 태그가 없다). 한 문항의 무게가 article_ref 0.056, product_name 0.083, internal_only 0.125다.
- `product_name`은 라벨 기준으로 여섯 조합 모두 Recall@5 1.000이다(상품설명서 6청크 중 아무거나 맞음). 답 문구 기준으로 갈리는 문항은 둘이다: bank-080은 BM25만 찾고(리랭커를 붙이면 BM25도 놓친다), bank-074는 dense만 놓친다.
- `internal_only` 8문항은 근거가 내부 지침(15~18청크짜리 문서)이라 모든 조합이 1.000이다. 역할 `상담원`에서의 동작은 [답변 기록](2026-11-12-answers-v1.md)의 "권한 확인"에 있다.

## 리랭커: 문항 단위 (k = 5)

"맞힘"은 Recall@5 = 1.0(근거를 모두 찾음)이다. multi_doc에서 근거 하나만 찾으면 맞힘이 아니다. p는 정확 맥니마(양측)다.

| 검색기 | 분할 | 답 문구: 새로 맞힘 / 새로 놓침 | p | 라벨: 새로 맞힘 / 새로 놓침 | p |
|---|---|---|---|---|---|
| BM25 | 기본 | 15 / 2 | 0.0023 | 12 / 0 | 0.0005 |
| dense | 기본 | 10 / 2 | 0.039 | 8 / 2 | 0.109 |
| hybrid | 기본 | 12 / 2 | 0.013 | 9 / 1 | 0.021 |
| BM25 | 800 | 17 / 2 | 0.0007 | 14 / 0 | 0.0001 |
| dense | 800 | 10 / 1 | 0.012 | 8 / 1 | 0.039 |
| hybrid | 800 | 13 / 2 | 0.0074 | 10 / 1 | 0.012 |

뒤집힌 문항(답 문구 기준, 기본 분할):

| 검색기 | 새로 맞힘 | 새로 놓침 |
|---|---|---|
| BM25 | 017, 032, 034, 037, 044, 060, 082, 085, 096, 116, 120, 121, 122, 125, 132 | 040, 080 |
| dense | 009, 010, 041, 043, 044, 074, 091, 095, 096, 122 | 042, 133 |
| hybrid | 010, 017, 029, 034, 041, 083, 086, 096, 116, 121, 122, 125 | 040, 119 |

- v0 기준선의 대표 실패 bank-029(dense 1위, BM25 68위라 RRF에서 밀림)는 hybrid에서 여전히 리랭커로 풀린다.
- 두 기준이 다른 문항은 모두 상품설명서 근거다. BM25의 032·034·116은 라벨로는 원래 맞힌 문항이고, 답 문구로는 리랭커가 답이 든 표 행 청크를 5위 안에 올려 새로 맞혔다. 040·080은 답 문구 기준으로만 새로 놓쳤다(설명서 청크는 남았지만 답이 든 청크가 빠졌다).
- dense가 새로 놓친 042(가계대출약관 제7조, 2,740자)는 [리랭커 기록](2026-11-11-reranker.md)과 같은 실패다. 800자 분할에서는 풀린다.

### 44문항에서 비유의, 127문항에서 유의: v0 부분과 새 부분

| v0 44문항, 답 문구 | 5 / 1, p = 0.219 | 5 / 1, p = 0.219 | 5 / 1, p = 0.219 |

- v0 부분의 라벨 기준 hybrid 4 / 0, p = 0.125는 [리랭커 기록](2026-11-11-reranker.md)의 값과 같다. 이번 실행에서도 v0 부분만으로는 유의하지 않다.
- 효과의 방향과 크기(불일치 문항 중 리랭커 쪽 비율, hybrid 5/6 → 12/14)는 비슷하다. 불일치 문항이 6개에서 14개로 늘자 같은 비율로도 p가 0.05 아래로 내려갔다. 효과가 새로 생긴 것이 아니라 알아볼 수 있게 된 것이다.

## dense 대 hybrid

| 조건 (k = 5) | dense R@5 / MRR (답 문구) | hybrid R@5 / MRR (답 문구) | hybrid 쪽 새로 맞힘 / 새로 놓침, p (답 문구) | 라벨 |
|---|---|---|---|---|
| 리랭커 없음, 기본 | 0.886 / 0.810 | 0.870 / 0.752 | 8 / 10, p = 0.81 | 6 / 8, p = 0.79 |
| 리랭커 없음, 800 | 0.886 / 0.801 | 0.870 / 0.737 | 8 / 10, p = 0.81 | 6 / 8, p = 0.79 |
| KURE, 기본 | 0.948 / 0.880 | 0.941 / 0.866 | 0 / 0 | 0 / 0 |
| KURE, 800 | 0.949 / 0.885 | 0.945 / 0.873 | 0 / 0 | 0 / 0 |

- 리랭커 없이 뒤집힌 문항(기본 분할, 답 문구): hybrid만 맞힘 009, 040, 043, 044, 074, 091, 095, 119 / dense만 맞힘 017, 029, 034, 042, 083, 086, 116, 121, 125, 133.
- KURE를 붙이면 맞힌 문항 집합이 같다. 평균의 차이는 multi_doc의 절반 맞힘과 순위에서 나온다.
- k = 10: 리랭커 없이 hybrid 쪽 2 / 4 (p = 0.69), KURE와 함께 0 / 1 (bank-042, dense만 맞힘).

[ADR 0002](../adr/0002-hybrid-rrf.md)의 질문("BM25가 강한 질의에서 hybrid가 dense보다 나은가")에 대한 데이터 (k = 5, 기본 분할, 리랭커 없음, 답 문구 기준 R@5 / MRR):

| 태그 | n | BM25 | dense | hybrid |
|---|---|---|---|---|
| article_ref | 18 | 0.944 / 0.861 | **1.000 / 1.000** | 1.000 / 0.903 |
| product_name | 12 | **1.000 / 0.794** | 0.833 / 0.694 | 0.917 / 0.750 |

- **조항 번호 질의에서는 BM25 보강이 필요 없었다.** dense가 18문항 모두 1위로 찾았다. hybrid는 BM25 순위가 섞이며 060("34조", 4위), 061·064(2위)의 순위가 내려갔다. BM25는 060을 놓쳤다("제"를 뺀 질의).
- **상품명 질의에서는 hybrid가 dense보다 한 문항(bank-074) 낫다.** BM25가 가장 좋다. k = 10에서도 답 문구 Recall이 BM25·hybrid 1.000, dense 0.917(bank-080)이다. 12문항에서 한 문항 차이라 검정할 만한 표본이 아니다.

## 여러 비교: Holm 보정

이 기록은 k = 5 답 문구 기준으로만 문항 단위 비교 16개(리랭커 6, 분할 6, dense 대 hybrid 4)를 했고, k = 10과 라벨 기준까지 세면 그 네 배다. 비교가 많으면 우연히 p < 0.05가 나올 가능성도 커진다. 그래서 어느 묶음을 한 가족으로 보느냐에 따라 Holm 보정 뒤 남는 것을 적는다(k = 5).

| 묶음 | 비교 수 | 보정 뒤 p < 0.05로 남는 것 |
|---|---|---|
| 리랭커 효과, 기본 분할, 답 문구 | 3 | BM25 (보정 p = 0.007), hybrid (0.026), dense (0.039) |
| 리랭커 효과, 기본 분할, 라벨 | 3 | BM25 (0.0015), hybrid (0.043). dense는 보정 전 0.109 |
| 계획의 세 질문: 리랭커 3 + 분할 6 + dense 대 hybrid 2, 답 문구 | 11 | BM25 리랭커만 (0.026). hybrid 0.129, dense 0.347 |
| 위에 800자 조건의 리랭커 3 + dense 대 hybrid 2를 더함, 답 문구 | 16 | BM25 리랭커 두 개(800자 0.012, 기본 0.035). hybrid 800자 0.103 |

- 분할 효과와 dense 대 hybrid는 보정 전에도 유의하지 않다(p ≥ 0.79).
- 어느 묶음에서도 남는 결론은 **"BM25에 리랭커를 붙이면 맞힌 문항이 는다"** 하나다.
- 계획은 세 변수(골든셋, 분할, 리랭커)를 따로 보고하라고 정했다. 그래서 리랭커 질문만 한 묶음(3개)으로 읽는 것이 이 기록의 본문이고, 그 묶음에서는 답 문구 기준으로 세 검색기 모두 남는다. 다만 기본 검색기(hybrid)에 대한 결론은 묶음을 넓히면 남지 않는다는 점을 함께 적는다.

- VRAM은 GPU 전체 사용량의 실행 구간 최댓값이고, 바탕 사용량(실험 시작 때 665~667 MiB)과 색인 때 잡힌 메모리가 들어 있다. KURE가 더하는 양은 dense·hybrid에서 584 MiB로 [리랭커 기록](2026-11-11-reranker.md)과 같다.
- 800자 분할에서 dense·hybrid의 최대가 240 MiB 낮고 BM25 + KURE만 194 MiB 높다. 원인은 확인하지 않았다.
- 리랭커 지연은 분할하면 3~4% 준다(hybrid + KURE 400 → 387 ms). 쌍의 평균 길이가 짧아져서로 보이지만 토큰 수를 재지는 않았다.
- LLM(Ollama)과 함께 돌 때의 지연·VRAM은 [답변 기록](2026-11-12-answers-v1.md)에 있다.

## 구현 세션의 에이전트의 수치와 대조

- **같다:** 리랭커 맥니마(답 문구 기준 BM25 15 / 2, dense 10 / 2, hybrid 12 / 2와 p값), dense 대 hybrid(8 / 10, p ≈ 0.81, 리랭커 뒤 같음), 태그 수치(article_ref dense 1.000·MRR 1.000, hybrid MRR 0.903; product_name BM25 1.000, hybrid 0.917, dense 0.833), 분할 맥니마(리랭커와 함께 1 / 0, bank-042), 24개 보고서의 요약값과 실행 로그 표.
- **다른 점 1.** 리랭커 결과를 "라벨 기준도 함께" 유의하다고 보면 안 된다. 라벨 기준으로 dense는 8 / 2, p = 0.109로 유의하지 않다. BM25(12 / 0, p = 0.0005)와 hybrid(9 / 1, p = 0.021)는 라벨 기준으로도 유의하다.
- **다른 점 2.** 분할의 잘린 쌍 "8.7% → 0.1%"는 이 데이터의 값이 아니다. 8.7%(115 / 1,320)는 v0 44문항 [리랭커 기록](2026-11-11-reranker.md)의 값이고, 0.1%는 [Task 25 노트](../learning/task-25-article-split.md)에서 찾지 못했다(노트에는 "BM25 후보 30개(44문항)에서 잘린 부칙 쌍은 1쌍"만 있다). 이번 127문항 보고서로는 BM25 후보 369 / 3,810(9.7%) → 13 / 3,810(0.3%)이다. 분할 기록에는 이 값을 쓴다.
- 구현 세션의 에이전트의 집계 스크립트와 이 기록의 정의(맞힘 = Recall 1.0, 근거 있음 = 라벨 기준으로 상위 5개에 근거가 하나라도 있음)는 같다.

## 읽을 때 주의할 점

1. **비교가 많다.** 위 "여러 비교"를 보라. 같은 코퍼스·같은 문항으로 조합 24개를 재고 그중 좋은 것을 말하면 낙관 편향도 생긴다.
2. **골든셋은 에이전트가 만들고 다른 에이전트(같은 계열 모델)가 원문과 전수 대조했다. 사람 검수는 없다.** 저장소 주인이 판단을 에이전트에게 위임했다. 같은 오독을 둘 다 놓쳤을 수 있다.
3. **답 문구는 근거마다 하나이고 만든 에이전트가 골랐다.** 답이 여러 항에 걸치면 고른 항이 든 청크만 답 문구 기준 정답이다.
4. **역할 하나(`준법감시`)로만 검색을 쟀다.** `상담원` 역할은 답변 평가 한 번뿐이다.
5. **태그 행의 표본이 작다**(n = 8~26). 검정하지 않았고, 한두 문항으로 순서가 바뀐다.
6. **실행은 조합마다 한 번이다.** 검색은 결정적이라 반복해도 같지만, 문항 표본에서 오는 불확실성은 그대로다.
7. 보고서에는 상위 k개만 남아 11위 아래 순위와 리랭커 점수는 볼 수 없다.
