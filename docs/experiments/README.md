### 골든셋 v1로 다시 측정한 결과 (M-2 마무리)

자세한 내용은 실험 기록 [검색](2026-11-12-golden-v1.md), [긴 조항 나누기](2026-11-12-article-split.md), [답변](2026-11-12-answers-v1.md)에 있습니다. 결정은 [ADR 0002](../adr/0002-hybrid-rrf.md#갱신-2026-11-12-골든셋-v1)와 [ADR 0006](../adr/0006-reranker.md#갱신-2026-11-12-골든셋-v1)의 갱신 절, 그리고 [ADR 0007](../adr/0007-article-split.md)에 정리했습니다. 아래 [M-1 기준선](#결과-m-1-기준선)과 [M-2 축소판](#그-뒤의-실험-m-2-축소판) 절의 수치는 당시 기록을 그대로 두었습니다.

**조건.** 골든셋 v1은 150문항입니다. v0의 50문항에 새 문항 100개를 더했습니다. 유형별 문항 수는 다음과 같습니다.

| lookup | table | multi_doc | out_of_scope |
|---|---|---|---|
| 82 | 22 | 23 | 23 |

검색 평가는 근거가 있는 127문항만 채점하고, 여기서 한 문항은 Recall 0.008에 해당합니다. 범위 밖 23문항은 답변 평가에만 씁니다. 새 문항에는 조항 번호로 묻는 질문 18개와 정식 상품명으로 묻는 질문 12개가 들어 있습니다. 정답이 부정문인 질문도 26개 있습니다.

골든셋은 에이전트가 만들었고, 다른 에이전트가 원문과 전수 대조했습니다. 대조 과정에서 새 100문항 중 2문항을 고쳤습니다. 판단이 애매한 문항은 10개였습니다. 작성자(저)는 판단을 에이전트에게 위임했고, 사람 검수는 거치지 않았습니다. 자세한 과정은 [제작·대조 기록](../eval/golden-v1-build.md)에 있습니다. 코퍼스는 기준선과 같은 13개 문서, 945청크입니다. 역할은 `준법감시`이고 k = 5입니다.

**채점 기준 두 가지.** 라벨 기준은 근거 조항의 청크가 상위 k에 들면 정답으로 칩니다. M-1부터 써 온 지표입니다. 답 문구 기준은 여기에 더해, 그 청크 본문에 근거마다 달아 둔 원문 문구까지 들어 있어야 정답으로 칩니다. 이 원문 문구는 10~40자입니다. 라벨 기준은 두 경우에 후하게 채점합니다. 조항이 없는 상품설명서는 그 문서의 청크 6개 중 아무거나 나와도 정답입니다. 긴 조항을 나누면 답이 없는 조각에도 같은 라벨이 달립니다. 그래서 답 문구 기준을 주 지표로 씁니다.

**검색.** 127문항을 k = 5에서 답 문구 기준으로 측정했습니다. 각 칸은 Recall@5 / MRR입니다. 리랭커는 KURE-Reranker-nano이고 후보는 30개입니다. "맞힘"은 근거를 모두 찾은 문항을 뜻합니다.

| 검색기 | 리랭커 없음 | + 리랭커 | 리랭커로 새로 맞힘 / 새로 놓침 (정확 맥니마) |
|---|---|---|---|
| BM25 | 0.827 / 0.665 | 0.909 / 0.853 | 15 / 2, p = 0.002 |
| dense | **0.886 / 0.810** | **0.948 / 0.880** | 10 / 2, p = 0.039 |
| hybrid (기본) | 0.870 / 0.752 | 0.941 / 0.866 | 12 / 2, p = 0.013 |

라벨 기준으로 측정한 값은 다음과 같습니다. 각 칸은 위 표와 마찬가지로 Recall / MRR입니다.

| 검색기 | 리랭커 없음 | + 리랭커 |
|---|---|---|
| BM25 | 0.862 / 0.758 | 0.933 / 0.890 |
| dense | 0.921 / 0.889 | 0.971 / 0.917 |
| hybrid | 0.909 / 0.847 | 0.965 / 0.902 |

- **리랭커는 세 검색기 모두에서 맞힌 문항을 늘렸습니다.** 보정 전에는 셋 다 p < 0.05입니다. 하지만 Holm 보정을 하면 어떤 비교를 한 묶음으로 보느냐에 따라 결과가 달라집니다.

  | Holm 보정 묶음 | 보정 뒤에도 유의한 리랭커 효과 | 보정 p |
  |---|---|---|
  | 리랭커 비교 3개 | BM25, hybrid, dense | 0.007, 0.026, 0.039 |
  | 계획의 비교 11개 (리랭커 3, 분할 6, dense 대 hybrid 2) | BM25 | 0.026 |

  라벨 기준으로 채점하면 dense의 리랭커 효과는 8 / 2, p = 0.109로 유의하지 않습니다.
- **44문항에서 유의하지 않았던 것은 검정력이 부족했기 때문입니다.** 같은 보고서에서 v0의 44문항만 따로 볼 수 있습니다. 여기서는 세 검색기 모두 5 / 1이고 p = 0.219입니다. 효과가 새로 생긴 것이 아닙니다. 한쪽만 맞힌 문항이 늘어서 검정이 효과를 알아볼 수 있게 된 것입니다.
- **dense와 hybrid는 뚜렷한 차이가 없었습니다.** 리랭커 없이 비교하면 hybrid 쪽의 새로 맞힘 / 새로 놓침이 8 / 10이고 p ≈ 0.81입니다. 리랭커를 함께 쓰면 두 검색기가 맞힌 문항이 127문항 중 같은 117문항으로 완전히 일치합니다. BM25가 강할 만한 질의도 따로 측정했습니다. 조항 번호로 묻는 18문항에서는 dense만으로 Recall@5와 MRR이 모두 1.000이었습니다. hybrid는 1.000 / 0.903입니다. 상품명으로 묻는 12문항에서는 BM25의 Recall@5가 1.000이었습니다. hybrid는 0.917, dense는 0.833으로 둘의 차이는 한 문항입니다. 기본 검색기는 hybrid로 두었지만 **데이터가 hybrid를 지지하는 것은 아닙니다.** 바꿀 만큼 차이가 나지 않았고 사람이 검수한 표본도 없어서 그대로 둔 것입니다. 이 결정은 [ADR 0002](../adr/0002-hybrid-rrf.md#갱신-2026-11-12-골든셋-v1)에 정리했습니다.
- **긴 조항을 800자로 나누면 잘림은 거의 사라지지만, 검색 지표는 거의 그대로입니다.** 리랭커 입력은 512토큰을 넘으면 뒤가 잘립니다. hybrid + 리랭커에서 이렇게 잘린 (질문, 청크) 쌍이 10.0%에서 0.3%로 줄었습니다. 그런데 리랭커와 함께 썼을 때 새로 맞힌 문항은 bank-042 하나였고, 새로 놓친 문항은 없었습니다(1 / 0). 리랭커 없이 나누면 hybrid의 답 문구 MRR이 0.752에서 0.737로 내려갑니다. 그래서 기본값은 꺼짐이고, `AXB_MAX_CHUNK_CHARS=800`으로 켤 수 있습니다. 근거는 [ADR 0007](../adr/0007-article-split.md)에 있습니다.
- 질문당 평균 검색 시간은 LLM 없이 hybrid가 42 ms, hybrid + 리랭커가 400 ms입니다.

**답변.** hybrid 검색과 `qwen3.5:4b-q4_K_M` 모델로 150문항을 조건마다 두 번 실행했습니다. 각 칸은 1회차 · 2회차 값입니다.

| 조건 | 근거 기준 거절 정확도 | 인용 정밀도 | 근거가 없는데 답함 | 과잉 거절 | 질문당 지연 평균 |
|---|---|---|---|---|---|
| hybrid | 0.840 · 0.813 | 0.760 · 0.696 | 11 · 15 | 13 · 13 | 2.66 · 2.70초 |
| hybrid + 리랭커 | 0.900 · 0.880 | 0.749 · 0.729 | 6 · 7 | 9 · 11 | 3.19 · 3.18초 |

- **거절 쪽 지표는 나아졌지만, 나아진 크기가 실행 사이의 편차와 비슷합니다.** 같은 회차끼리 문항 단위로 비교하면 첫 회차는 20 / 11이고 p = 0.15입니다. 두 번째 회차는 17 / 7이고 p = 0.064입니다. 같은 조건을 두 번 실행해도 거절 여부가 바뀌는 문항이 14~24개입니다.
- **인용 정밀도는 오르지 않았습니다.** M-2 축소판에서는 50문항을 한 번 실행했습니다. 그때 본 0.670 → 0.827은 재현되지 않았습니다.
- **"근거가 없는데 답함" 건수를 환각 건수로 읽으면 안 됩니다.** 여섯 실행에서 나온 50건을 읽어 보면 47건은 판정기가 놓친 거절이었습니다. 근거 없이 실제로 답을 내놓은 것은 3건이었습니다.
- **정답이 부정문이면 과잉 거절이 많습니다.** 근거를 받고도 거절한 문항은 부정문 정답 문항에서 5~9 / 23~25였습니다. 나머지 문항에서는 4~6 / 95~99였습니다. 여섯 실행 모두 Fisher p ≤ 0.016입니다.

  시스템 프롬프트에 한 줄을 더해 보기도 했습니다. 자료가 "없다", "할 수 없다"고 분명히 적고 있으면 그것이 답이라는 내용입니다. 그러자 판정기 기준으로 부정문 과잉 거절이 5·7 / 25에서 2·2 / 25로 줄었습니다. 출력 원문으로 세면 3·3 / 25입니다. 그래도 이 한 줄은 채택하지 않았습니다. 이유는 다음과 같습니다.

  - 거절할 때 정해진 문구를 쓰지 않는 경우가 늘었습니다. 정해진 문구로 한 거절이 21·23에서 11·10으로 줄었습니다. 그 결과 판정기가 놓친 거절이 인용이 달린 채로 나갔습니다.
  - 과잉 거절이 풀린 18건 중 3건은 틀린 답이었습니다.
  - 문항 단위로 보면 순효과가 없었습니다(11 / 11, 12 / 10).
- **권한 검사에서 내부 문서가 새는 경우는 찾지 못했습니다.** public 문서만 볼 수 있는 `상담원` 역할로 150문항에 답하게 했습니다. 설정은 hybrid + 리랭커 + 800자입니다. 질문마다 검색 상위 5개를 모으면 모두 750칸입니다. 이 가운데 internal 청크는 0개였습니다. 인용 190개 중에도 internal은 0개였습니다. 내부 지침에만 있는 낱말 10개(`대외비`, `문진표` 등)가 든 출력도 0개였습니다. 같은 조건의 `준법감시` 실행에서는 그런 출력이 8·10개였습니다. 따라서 이 낱말 검사가 그런 출력을 실제로 잡아낼 수 있다는 것도 확인했습니다.

**주의.** 같은 127문항으로 검색 조합 24개를 측정했기 때문에, 그중 가장 좋은 값은 실제보다 높게 나왔을 수 있습니다. 놓친 거절인지, 맞는 답인지 틀린 답인지 같은 답변 판정과 분류는 평가 담당 에이전트가 출력 원문을 읽고 한 것입니다. 사람 검수는 거치지 않았습니다. 재현 명령은 각 실험 기록과 [평가 다시 실행하기](#평가-다시-실행하기)에 있습니다.

**조건.** 골든셋 v0의 50문항을 썼습니다. 유형별 문항 수는 다음과 같습니다.

골든셋은 에이전트가 문서를 보고 만든 초안이고, **사람 검수는 거치지 않았습니다.** 당시 만든 [15문항 표본 검수표](../eval/golden-v0-review-sheet.md)는 채워지지 않았고, 뒤에 만든 확인 목록의 판단도 2026-11-12에 에이전트에게 맡겼습니다. 코퍼스는 13개 문서, 945청크입니다. 역할은 public과 internal 문서를 모두 볼 수 있는 `준법감시`이고, k = 5입니다.

**검색.** 범위 밖 6문항을 뺀 44문항으로 측정했습니다.

| 구분 | n | BM25 R@5 | BM25 MRR | dense R@5 | dense MRR | hybrid R@5 | hybrid MRR |
|---|---|---|---|---|---|---|---|
| **전체** | 44 | 0.841 | 0.746 | **0.886** | **0.880** | 0.864 | 0.824 |
| 조항 단위 근거만 | 25 | 0.780 | 0.653 | 0.820 | 0.808 | 0.800 | 0.710 |
| 문서 단위 근거 포함 | 19 | 0.921 | 0.868 | 0.974 | 0.974 | 0.947 | 0.974 |

**답변.** hybrid 검색과 `qwen3.5:4b-q4_K_M`으로 50문항을 한 번 실행했습니다.

| 구분 | n | 근거 n | Recall@5 | MRR | 인용 n | 인용 정밀도 | 거절 정확도 |
|---|---|---|---|---|---|---|---|
| **전체** | 50 | 44 | 0.864 | 0.824 | 39 | 0.662 | 0.860 |
| out_of_scope | 6 | 0 | - | - | 1 | 0.000 | 0.333 |

**읽을 때 주의할 점**

- **dense가 hybrid보다 좋았습니다.** 하이브리드가 늘 낫다는 가정과는 반대입니다. RRF는 두 검색기에 모두 나온 청크를 앞에 둡니다. 두 후보 목록은 각각 30개입니다. 두 목록에 함께 나온 청크가 5개 이상이면, BM25 후보에 없는 정답은 dense가 1위로 찾아도 상위 5개에 들지 못합니다(bank-029). 반대로 dense가 놓치고 hybrid가 찾은 문항도 있습니다(bank-009). 다만 Recall@5 차이는 **한 문항**입니다. 44문항에서 한 문항은 약 0.023이라서 순위가 바뀔 수 있습니다. 관련 결정은 [ADR 0002](../adr/0002-hybrid-rrf.md)에 있습니다.
- **문서 단위 근거가 Recall을 부풀립니다.** 상품설명서는 조항이 없어서 근거를 문서 단위로 달았습니다. 그래서 그 문서의 청크 6개 중 아무거나 나와도 정답입니다. 반면 조항이 근거라면, 예를 들어 은행법에서는 청크 256개 중 1개만 정답입니다. 조항 근거만 있는 25문항은 R@5가 전체 수치보다 낮습니다. BM25, dense, hybrid 순서로 0.780 / 0.820 / 0.800입니다. "조항을 정확히 찾는 능력"은 이 행을 보고 판단해야 합니다.
- **거절 판정이 바꿔 말한 거절을 놓칩니다.** 판정은 답이 정해진 문구(`제공된 자료로는 확인할 수 없습니다.`)로 시작하는지를 글자로만 확인하는 규칙입니다. 범위 밖 6문항 중 4개는 모델이 문구를 바꿔 거절했고, 지표는 이것을 답변으로 셌습니다. 거절 정확도 0.333은 그래서 나온 값입니다. 출력 원문을 보면 6문항 모두 답을 피했습니다. 반대로 근거를 가져왔는데도 거절한 과잉 거절은 3/39입니다. out_of_scope 행의 인용 정밀도 0.000은 인용을 단 1문항(046)의 값입니다.
- **답변 지표는 한 번 실행한 값입니다.** 같은 설정의 다른 실행에서는 인용 정밀도가 0.707이었습니다. 릴리스 후 세 번째로 실행했을 때는 0.677이었습니다. 자세한 내용은 [실험 기록](2026-11-10-baseline.md)의 "릴리스 후 재현 확인"에 있습니다. 인용 정밀도는 인용한 위치만 봅니다. 그래서 맞는 조항을 인용하고 내용을 틀리게 옮긴 답(bank-030)은 잡아내지 못합니다.
- 답변 지연의 중앙값은 4,358.52 ms이고 평균은 6,988.64 ms입니다. 최댓값은 68,855.43 ms입니다. 검색만 할 때 질문당 평균 시간은 dense가 30.81 ms, BM25가 0.84 ms입니다. 측정 환경은 RTX 3070 Ti 8GB입니다.

#### 그 뒤의 실험 (M-2 축소판)

v0.2.0을 낸 뒤 평가에서 약했던 세 부분을 다시 살펴봤습니다([계획](../superpowers/plans/2026-11-11-m2-slim.md)). 위 기준선의 표와 문장은 고치지 않았고, 새로 측정한 값은 아래 기록에 따로 있습니다. 골든셋과 코퍼스, 역할은 기준선과 같습니다.

**1. 골든셋 전수 대조** → [대조 기록](../eval/golden-v0-audit.md), [수치에 주는 영향](2026-11-11-golden-audit.md)

- 골든셋을 만든 에이전트와 별도로 실행한 에이전트가 50문항을 원문과 하나씩 대조했습니다. **사람 검수가 아닙니다.** 명백한 오류를 찾지 못해 수정은 0건이고, 그래서 위 기준선 수치도 그대로입니다. "수정 0건"은 오류가 없다는 증명이 아닙니다. 같은 종류의 모델이 다시 읽어도 찾지 못했다는 뜻입니다.
- 판단이 엇갈릴 수 있는 6문항(bank-004, 006, 009, 032, 042, 043)은 고치지 않았습니다. 대신 무작위 표본 5문항과 함께 [확인 목록](../eval/golden-v0-owner-check.md)의 11문항에 넣었습니다. 작성자(저)는 2026-11-12에 이 판단을 에이전트에게 위임했습니다. 그 뒤 042·006·032는 골든셋 v1에서 고쳤고, 나머지는 그대로 두었습니다. 선택 결과는 [확인 목록](../eval/golden-v0-owner-check.md)에 있습니다.
- **bank-009에 대한 정정 방향.** 위에서 bank-009를 "dense가 놓치고 hybrid가 찾은 문항"의 예로 들었지만, 그 예로는 약합니다. 세 검색기 모두 같은 상품설명서 청크를 1~3위에 놓았고, 차이는 라벨이 달린 법 조항이 4위에 들었느냐뿐입니다. 확인 목록의 B처럼 그 상품설명서 문장도 정답으로 인정하면, dense는 이 문항을 1위로 찾은 셈이 됩니다. 그러면 dense와 hybrid의 Recall@5 차이는 한 문항(0.023)에서 두 문항(0.045)으로 벌어집니다. dense는 0.886에서 0.909로 오릅니다. hybrid는 0.864 그대로입니다. 이 값은 계산만 한 것이고 골든셋에는 반영하지 않았습니다. 지금 스키마에는 "이것을 찾아도 정답"이라는 칸이 없어서, B를 반영하려면 채점 규칙부터 더해야 합니다.

**2. 거절 판정** → [실험 기록](2026-11-11-refusal-detection.md), [라벨 기준](../eval/refusal-labels.md)

- 바꿔 말한 거절을 문장 단위 규칙으로 잡아내는 판정기를 더했습니다. 모델을 다시 실행하지 않고, 저장해 둔 실제 모델 출력 150개로 측정했습니다. 이 출력은 50문항을 3회씩 실행해 얻은 것이고, 라벨은 에이전트가 달았습니다. 정밀도는 **1.000**(30/30), 재현율은 **0.732**(30/41)입니다. 규칙을 다듬는 데 쓰지 않은 50개에서는 재현율이 0.538이었습니다. 이 묶음에 있던 바꿔 말한 거절 6개는 하나도 잡지 못했습니다. 이 정밀도는 실제 출력이 다룬 범위 안에서만 의미가 있습니다. PR 리뷰에서 "자료 [1]에 따르면 미성년자는 가입 대상에 포함되지 않습니다" 같은 부정문 정답을 거절로 잘못 보는 오탐이 나왔습니다. 그래서 규칙을 좁혔고, 재현율은 0.829에서 0.732로 내려갔습니다. 이런 부정문 정답은 합성 문장 41개로만 확인했습니다.
- 범위 밖 6문항의 거절은 기준선 실행에서 2/6 → 6/6이 됐습니다. 다른 두 실행에서는 각각 2/6 → 6/6, 4/6 → 4/6이었습니다.
- **전체 거절 정확도는 거의 오르지 않았습니다.** 세 실행의 값은 아래 표에 있습니다. 이 지표는 "범위 밖이면 거절, 아니면 답변"만 정답으로 봅니다. 그래서 검색이 근거를 못 가져와 모델이 "자료에 없다"고 한 것도 오답입니다. 옛 판정은 이런 거절을 알아보지 못해 답한 것으로 셌고, 새 판정이 거절로 알아보자 오답이 됐습니다. 범위 밖 문항에서 오른 점수의 일부가 여기서 상쇄됐습니다.
- 그래서 **근거 기준 거절 정확도**를 더했습니다. 검색 상위 k에 라벨된 근거가 있으면 답변이 정답이고, 없으면 거절이 정답입니다. 같은 세 실행의 값은 아래 표에 함께 적었습니다. 세 번째 실행이 낮은 것은 판정기가 놓친 거절 6개가 "근거가 없는데 답함"으로 세어졌기 때문입니다. 근거를 받고도 거절한 과잉 거절은 실행마다 2~3건이었고, 판정을 바꿔도 그대로였습니다. 판정기가 아니라 모델의 문제입니다.

| 실행 | 전체 거절 정확도 (옛 판정 → 새 판정) | 근거 기준 거절 정확도 |
|---|---|---|
| 첫 번째 | 0.860 → 0.900 | 0.920 |
| 두 번째 (기준선) | 0.860 → 0.880 | 0.900 |
| 세 번째 | 0.900 → 0.900 | 0.800 |

**3. 리랭커** → [실험 기록](2026-11-11-reranker.md), [ADR 0006](../adr/0006-reranker.md)

검색기가 고른 후보 30개의 순위를 크로스 인코더로 다시 매겼습니다. 44문항을 k = 5로 측정했습니다. 각 칸은 Recall@5 / MRR입니다.

| base | 리랭커 없음 | + KURE-Reranker-nano | + bge-reranker-v2-m3 |
|---|---|---|---|
| BM25 | 0.841 / 0.746 | 0.898 / 0.868 | 0.909 / 0.861 |
| dense | 0.886 / 0.880 | 0.966 / 0.921 | 0.955 / 0.889 |
| hybrid | 0.864 / 0.824 | 0.943 / 0.887 | 0.932 / 0.883 |

조항 단위 근거만 있는 25문항의 Recall@5는 다음과 같습니다.

| base | 리랭커 없음 | + KURE-nano | + bge-v2-m3 |
|---|---|---|---|
| BM25 | 0.780 | 0.840 | 0.860 |
| dense | 0.820 | 0.960 | 0.940 |
| hybrid | 0.800 | 0.920 | 0.900 |

질문당 평균 검색 시간은 다음과 같습니다. LLM 없이 측정한 값입니다.

| base | 리랭커 없음 | + KURE-nano | + bge-v2-m3 |
|---|---|---|---|
| dense | 48 ms | 403 ms | 797 ms |
| hybrid | 45 ms | 409 ms | 783 ms |

k = 5에서 두 리랭커의 Recall@5 차이는 여섯 쌍 모두 문항 수로 0.5문항, 즉 한 문항의 절반 정도에 그칩니다. 두 리랭커는 서로 다른 문항을 놓칩니다. MRR은 KURE-nano가 높습니다. bge-v2-m3는 지연이 약 2배입니다. 내려받는 크기도 2.29GB로 KURE-nano의 0.6GB보다 큽니다. 그래서 권장하는 리랭커는 KURE-nano이고, 기본값은 꺼짐입니다.

**이 표를 읽을 때 주의할 점**

- **리랭커 효과는 통계적으로 유의하지 않습니다.** 문항 단위 정확 맥니마 검정에서 base → 리랭커 12개 비교의 p값은 0.063~0.453입니다. 0.05보다 작은 값은 하나도 없습니다. 다만 방향은 12개 모두 같아서, 새로 맞힌 문항이 새로 놓친 문항보다 많았습니다. 골든셋 v1의 127문항에서는 세 검색기 모두 p < 0.05였습니다. 이 결과는 [M-2 마무리](#골든셋-v1로-다시-측정한-결과-m-2-마무리) 절에 있습니다.
- **새로 놓친 문항과 순위가 내려간 문항이 있습니다.** KURE-nano는 dense에서 bank-042를 새로 놓쳤습니다. bge-v2-m3는 BM25에서 bank-043을, hybrid에서 bank-043·044를 새로 놓쳤습니다. bank-012는 리랭커를 쓴 12개 조합 모두에서 정답 순위가 내려갔습니다. 1위였던 정답이 2위가 됐습니다.
- **리랭커 입력이 512토큰에서 잘립니다.** 리랭커에 넣은 (질문, 청크) 쌍의 8.7~18.0%는 뒤가 잘렸습니다. 답이 잘린 뒤쪽에 있던 네 문항(bank-005, 012, 042, 044)은 모두, 적어도 한 리랭커에서 순위가 내려가거나 5위 밖으로 밀렸습니다.
- **고른 값은 실제보다 높게 나왔을 수 있습니다.** 리랭커 조합 12개를 같은 44문항으로 실행하고 그중 좋은 값을 읽었습니다. 새 문항에서는 이보다 낮게 나올 가능성이 높습니다. 조합 사이의 0~1문항 차이로 순위를 매겨서는 안 됩니다.

**4. 답변까지** → [실험 기록의 답변 측정 절](2026-11-11-reranker.md#답변까지-측정-2026-11-12-50문항-한-번씩-실행)

50문항을 `qwen3.5:4b-q4_K_M`으로 실행했습니다. k = 5이고 리랭커 후보는 30개입니다. 아래 표의 인용 정밀도 0.670 → 0.827은 골든셋 v1에서 재현되지 않았습니다. 이 내용은 [M-2 마무리](#골든셋-v1로-다시-측정한-결과-m-2-마무리) 절에 있습니다.

| 조건 | 인용 정밀도 | 근거 기준 거절 정확도 | 근거가 없는데 답함 |
|---|---|---|---|
| hybrid, 리랭커 없음 | 0.670 | 0.860 | 5 |
| hybrid + KURE-nano | 0.827 | 0.940 | 1 |
| dense + KURE-nano | 0.791 | 0.900 | 1 |

- **조건마다 한 번씩만 실행했습니다.** 기준선에서는 같은 설정이라도 인용 정밀도가 실행에 따라 0.662~0.707이었습니다. dense + KURE-nano는 근거를 받고도 거절한 문항이 판정기 기준 4개로 가장 많았습니다. 출력 원문으로 세면 5개인데, bank-026의 거절을 판정기가 놓쳤기 때문입니다. 다른 두 조건은 2개였습니다. 이 차이가 조건의 효과인지 실행 간 편차인지는 한 번의 실행으로 가릴 수 없습니다. "근거가 없는데 답함"은 환각의 수가 아니며, 판정기가 놓친 거절이 섞여 있습니다.
- **표의 값은 좁힌 거절 규칙으로 다시 채점한 것입니다.** 모델을 다시 실행하지 않고, 보고서에 남은 모델 원문으로 판정했습니다. 처음 규칙으로 채점한 값은 다음과 같습니다.

  | 조건 | 인용 정밀도 | 근거 기준 거절 정확도 | 근거가 없는데 답함 |
  |---|---|---|---|
  | hybrid, 리랭커 없음 | 0.687 | 0.880 | 4 |
  | hybrid + KURE-nano | 0.827 | 0.940 | 1 |
  | dense + KURE-nano | 0.798 | 0.900 | 0 |

  달라진 세 문항은 모두 판정기가 새로 놓친 거절입니다.
- **8GB GPU에서 세 모델을 함께 실행하면 VRAM이 거의 가득 찹니다.** 임베딩 모델과 리랭커, Ollama를 함께 올리면 VRAM 사용량이 7.9GB까지 올라갑니다. 리랭커가 없는 실행도 같았습니다. 실패는 없었습니다. 대신 리랭커를 올린 두 실행에서 색인 시간이 22초에서 131~133초로 늘었습니다. 질문당 지연도 0.9~1.4초 길어졌습니다. 이것이 리랭커를 기본으로 켜지 않은 이유입니다. 다만 골든셋 v1에서 리랭커를 올린 일곱 실행에서는 색인 시간이 21~39초여서, 이 증가가 재현되지 않았습니다([ADR 0006 갱신](../adr/0006-reranker.md#갱신-2026-11-12-골든셋-v1)).

#### 평가 다시 실행하기

```bash
pytest -q                                  # 단위 테스트. 실제 모델·네트워크를 쓰는 테스트(slow)는 빠진다
python scripts/download_corpus.py bank     # 법령·고시 5개(국가법령정보센터), 표준약관 2개(공정위)를 받는다
python -m axbuilder.eval.run --workspace bank --retriever bm25 --k 5      # GPU 없이
python -m axbuilder.eval.run --workspace bank --retriever hybrid --k 5    # 임베딩 모델 필요(.[ml])
python -m axbuilder.eval.run --workspace bank --retriever hybrid --k 5 --with-llm   # Ollama 필요. 150문항, 확인한 PC에서 질문당 평균 약 2.7초
```

원문은 `data/workspaces/bank/raw/`에 저장되며 git에는 올리지 않습니다. 가상 문서 6개는 저장소에 들어 있습니다. 평가 결과는 표로 출력되고, `reports/bank/`에 JSON으로도 남습니다. `--retriever`에는 `bm25`·`dense`·`hybrid` 중 하나를 씁니다. 리랭커를 쓰려면 `--reranker kure-nano --candidates 30`을 더합니다. 이때 `.[ml]`이 필요하고, 처음 실행할 때 모델 0.6GB를 내려받습니다. 긴 조항 나누기는 `--max-chunk-chars 800`으로 켜고, 이때 보고서 이름은 `-m800`으로 끝납니다. 골든셋에 답 문구가 있으면 표에 `Recall@k(답 문구)`·`MRR(답 문구)` 열과 태그별 행이 추가됩니다.

답변 모델을 Claude로 바꾸려면 `AXB_LLM_MODE=cloud`와 `ANTHROPIC_API_KEY`를 설정하고 `--allow-cloud`를 더합니다. 이 경우 문항마다 유료 API를 호출합니다.

```python
import sys
from pathlib import Path

import httpx

from axbuilder.corpus import load_sources

sys.stdout.reconfigure(encoding="utf-8")  # Windows 콘솔에서 한글이 깨지지 않게
api = httpx.Client(base_url="http://127.0.0.1:8000", timeout=300)

# 1) 워크스페이스: 역할마다 볼 수 있는 문서 등급
api.post(
    "/workspaces",
    json={
        "id": "demo",
        "name": "AXB은행(가상)",
        "industry": "finance",
        "roles": {"상담원": ["public"], "준법감시": ["public", "internal"]},
    },
).raise_for_status()

# 2) 저장소에 있는 가상 문서 6개 업로드: 상품설명서 3개(public), 내부 지침 3개(internal)
fields = {"doc_id", "title", "source", "doc_type", "access_level"}
for s in load_sources(Path("corpus/bank/sources.yaml")):
    if s.path:  # url로 받는 법령·약관은 건너뛴다
        with open(s.path, "rb") as f:
            api.post(
                "/workspaces/demo/documents",
                data=s.model_dump(include=fields),
                files={"file": (Path(s.path).name, f)},
            ).raise_for_status()

# 3) 색인: BM25 + dense (첫 호출 때 임베딩 모델을 불러온다)
print(api.post("/workspaces/demo/index").json())

# 4) 질문: 역할이 다르면 검색되는 문서가 다르다
for role, question in [
    ("상담원", "AXB 든든 정기예금에 12개월 만기일시지급식으로 가입하면 기본금리는 몇 %인가요?"),
    ("상담원", "고령 고객의 대리인이 예금을 찾으려면 어떤 서류가 필요한가요?"),
    ("준법감시", "고령 고객의 대리인이 예금을 찾으려면 어떤 서류가 필요한가요?"),
    ("상담원", "AXB은행 신용카드의 연회비는 얼마인가요?"),
]:
    r = api.post("/workspaces/demo/ask", json={"question": question, "role": role}).json()
    print(f"\n[{role}] {question}\nrefused={r['refused']}\n{r['answer']}")
    for i, c in enumerate(r["citations"], 1):
        print(f"  [{i}] {c['title']} {c['article'] or ''}")
```
