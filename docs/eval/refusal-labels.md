# 거절 판정 검증용 라벨 (모델 출력 150개)

Task 20(바꿔 말한 거절 판정)의 판정기를 검증하려고 실제 모델 출력 150개에 단 정답 라벨이다.
데이터는 `tests/fixtures/refusal_outputs.jsonl`에 있다.

- **라벨을 단 주체: 에이전트(Claude)다. 사람 검수가 아니다.** 판정 규칙을 만든 것과 같은 에이전트가 라벨도 달았다. 그래서 아래 "주인이 확인할 항목"을 따로 뽑았다.
- **순서: 라벨을 먼저 확정하고 그 뒤에 판정기를 만들었다.** 라벨 파일과 이 문서를 판정기 코드보다 앞선 커밋으로 남겼다. 규칙에 맞춰 라벨을 고치면 평가가 무의미해지므로, 판정기를 만든 뒤에는 라벨을 바꾸지 않았다.

실행마다 골든셋 50문항이고, 검색 결과는 세 실행이 같고 LLM 샘플링만 다르다. 보고서(`reports/bank/*.json`)는 git에 없다.

fixture 한 줄: `{run, id, qtype, answer, label, ambiguous}`

- `answer`는 보고서 항목의 `answer`다. 즉 **기존 규칙으로 정규화한 뒤의 텍스트**다: 기존 규칙이 거절로 본 출력은 고정 문구(`제공된 자료로는 확인할 수 없습니다.`)로 바뀌어 있고, 그 밖의 출력은 인용 번호만 다시 매긴 모델 원문이다. 정규화 전 원문(`llm.text`)으로 판정해도 결과가 같은지는 `scripts/rescore_refusals.py`가 확인한다(실험 기록 참고).
- 질문은 넣지 않았다. 질문은 `corpus/bank/golden.jsonl`에서 `id`로 찾는다. 라벨을 달 때는 질문을 함께 읽었다.

## 라벨 기준

| 라벨 | 뜻 |
|---|---|
| `refusal` | 질문에 답하지 않았다. "자료에 없다 / 확인할 수 없다 / 답변하기 어렵다"는 말과 그 이유 설명(자료에 무엇이 있고 무엇이 없는지)뿐이다 |
| `answer` | 질문에 답했다. 앞이나 뒤에 망설이는 말, 묻지 않은 세부 사항이 자료에 없다는 단서가 붙어도 답이 있으면 `answer`다 |
| `partial` | 질문의 일부는 답하고 일부는 자료에 없다고 했다. 또는 답을 말한 뒤 스스로 "확인할 수 없다"고 뒤집었다 |

- 답이 **맞았는지는 보지 않는다.** 틀린 답도 답한 것이면 `answer`다. 정답 여부는 이 라벨의 대상이 아니다.
- 판정기 평가에서는 `refusal`만 거절 클래스이고 `answer`와 `partial`은 모두 "거절 아님"이다. 그래서 `answer`와 `partial` 사이의 경계는 정밀도·재현율에 영향이 없다. 영향이 있는 것은 `refusal`과 나머지의 경계뿐이다.
- 기존 규칙이 고정 문구로 바꾼 출력은 `refusal`이다. 과잉 거절(답해야 하는 문항을 거절)도 출력 자체는 거절이므로 `refusal`이다. 과잉 거절인지는 `qtype`으로 따로 본다.

## fixture에 넣어도 되는가 (저작권 확인)

- 출력이 요약·인용한 문서는 직접 쓴 가상 문서 6개, 법령·고시 5개(저작권법 제7조 비보호), 공정위 표준약관 2개다. 문제가 될 수 있는 것은 약관뿐이다(README "데이터와 라이선스": 재배포 권리 불명확).
- 확인 방법: 출력 150개(정규화 뒤 `answer`와 정규화 전 `llm.text` 모두)와 약관 2개의 본문을 공백을 뺀 뒤 견주어, 글자 그대로 겹치는 가장 긴 구간의 길이를 쟀다(`difflib.SequenceMatcher.find_longest_match`).
- 결과: 가장 긴 구간이 **62자**(공백 제외, 0110 bank-044의 한 문장)였고 그다음이 58자, 47자, 38자다. 모두 한 문장 이하의 인용이다. 약관 본문은 공백을 빼고 9,460자, 6,214자다.
- 기준("원문 한 문단 이상을 글자 그대로 담은 출력")에 해당하는 항목은 **0개**라서 `answer`를 뺀 항목은 없다.
